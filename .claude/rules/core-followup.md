# Core — 후속 제안 · Defer · ERD

작업이 끝난 뒤 **이번 범위 밖으로 넘길 코드·설계 개선**을 어떻게 알리고 미루는지 정한다. 하네스 자체의 결함은 여기가 아니라 `retro` 스킬 몫이다 — 같은 항목을 양쪽에 남기지 않는다.

## 💡 ERD 적극 제안

**[플래그: DB 마이그레이션 금지]**가 ☑이면 `{{스키마 SSOT}}`·엔티티는 언제든 바뀔 수 있다. "ERD에 있으니 못 바꿈"으로 더 나은 모델을 숨기지 않는다.

- **언제:** Entity·API·BR 작업 중, Must Have 완료 후, 사용자가 스키마를 물을 때
- **무엇을:** 컬럼 위치·nullable·상태 표현(enum vs 시각)·인덱스·예약어 rename·파생→저장 전환 — **아쉬운 점 → 권장 형태 → (선택) 스펙 amend**를 짧게
- **적용:** 승인 또는 Approved 스펙이 스키마를 바꾸면 엔티티 + `{{스키마 SSOT}}`를 최신 하나로 맞춘다 (lang 팩 "DB 스키마 정책" 절)
- **금지:** 제안 없이 임시·중복 컬럼 누적 · ERD drift를 코드 주석으로만 방치

## 💡 구현 후 후속 제안

| 조건 | 후속 제안 |
|------|-----------|
| 사용자가 "구현 후 최적화·제안 말해줘" 등 **명시 요청** | **필수** — `{{테스트 명령}}` 통과 후 |
| API·DB·3파일+ 변경 등 **Must Have급** 완료 | **권장** — 완료 요약 **뒤**에 절 추가 |
| 한 줄·단일 파일·핫픽스 | 생략 가능 |

**형식:** `## 후속 제안` 아래 **3~8개** bullet, 영향 큰 순. 각 bullet은 **무엇이 아쉬운지 → 권장 방향 → (선택) 별도 이슈·스펙 amend 필요**. 이번 PR·커밋에 포함하지 않는다 — 승인·이슈 확정 후 진행. 점검 축은 해당할 때만 골라 쓴다: ERD·스키마 · API 설계(파라미터 vs 리소스, 조회 API의 부수 write, 활동 시각 hook 누락) · DTO(목록 vs 상세, fat response) · 쿼리·성능(N+1, batch, pagination) · 패키지·레이어 · 인터셉터·필터(프로젝트에 이미 있는 권한 게이트 패턴 우선, 변환기·값 객체로 충분하면 추가 금지).

**금지:** 후속 제안을 핑계로 **같은 턴에** 스펙 밖 리팩터·추상화 구현 · 근거·우선순위 없는 장문 나열 · 검증 대신 제안만 하고 완료 선언.

**반복 주제:** 같은 후속 제안이 2회 이상 나오면 `.claude/rules/` 추가나 스펙 amend를 **사용자에게 제안**한다 (자동 추가 금지). 절차는 `retro` 스킬, 기록은 `{{문서 루트}}/audits/harness-retro.md`.

## ✅ 후속 작업 이슈 분리 (Defer)

사용자가 **"다른 이슈로 빼"·"후속 이슈로"·"이번 Milestone 밖"** 등으로 범위를 미루라고 하면 **이슈만 만들고 끝내지 않는다.** Draft 스펙 → Approved 스펙 amend → README 갱신 → 이슈 생성(먼저 확인) → 구현 트림 → 보고까지의 절차는 **`defer` 스킬**이 SSOT다.
