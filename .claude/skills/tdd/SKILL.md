# TDD — 승인 지점의 실패하는 테스트 먼저

**이 스킬이 기본 동작과 다른 단 하나:** 테스트가 **올바른 이유로 실패하는 것을 보기 전에는** 그 지점의 구현을 쓰지 않는다.

TDD(테스트 주도 개발)는 "이게 되면 성공"이라는 확인 장치를 먼저 만들고, 그 장치가 실패(RED)하는 것을 본 뒤, 통과(GREEN)할 만큼만 구현하고, 정리(REFACTOR)하는 방식이다. 이 하네스는 이 순서를 **모든 코드가 아니라 사람이 승인한 "테스트 먼저 지점"에만** 적용한다. 이 문서에서 "지점"은 그 승인된 항목 하나를 말한다. 무엇을 확인하는 테스트가 좋은 테스트인지는 `core-testing.md`(S1~S8)가 SSOT이고, 이 스킬은 **순서와 증거**만 맡는다.

**이 스킬은 `core-workflow.md` 사이클의 구현 단계다.** 지점은 G2에서 정해지고(A 트랙: `specify` 스펙의 "테스트 먼저 지점" 표 · C 트랙: `debug`의 원인 가설 승인), 증거는 G3 `preflight`가 대조한다.

## When to Use

- Approved 스펙의 "테스트 먼저 지점" 표에 "테스트 먼저"로 표시된 Must 항목을 구현할 때
- 버그를 고칠 때 — `debug` 스킬이 재현 테스트를 이 절차로 쓰게 한다

**쓰지 않는다:** 표에서 "아님"인 항목 · 표가 없는 작업 · 문서·설정만 바꾸는 작업. 이런 곳의 테스트는 `core-testing.md`의 "유의미한 테스트만"을 따라 평소대로 쓴다.

## 원칙

| # | 원칙 | 왜 |
|---|---|---|
| T1 | 승인된 지점은 실패하는 테스트부터 쓴다(RED, 빨간불) | 확인 장치가 먼저 있어야 구현이 무엇을 만족해야 하는지 고정된다 |
| T2 | 실패 사유가 "기능 없음"인지 확인한다 | 오타·설정·컴파일 오류로 실패한 테스트는 기능이 생겨도 의미 있게 통과하지 않는다 |
| T3 | 그 테스트를 통과하는 최소 구현만 쓴다(GREEN, 초록불) | 테스트가 요구하지 않은 코드는 확인되지 않은 코드다 |
| T4 | 정리는 전체 `{{테스트 명령}}`이 통과한 상태에서만 한다(REFACTOR) | 빨간불 상태에서 구조를 바꾸면 무엇이 깨뜨렸는지 가를 수 없다 |
| T5 | 테스트를 고쳐서 통과시키지 않는다 | 통과하지 않으면 구현을 고친다. 테스트가 틀렸으면 고치되 **이유를 보고한다** |
| T6 | 버그 회귀 테스트는 수정을 되돌렸을 때 실패해야 한다 | 되돌려도 통과하는 테스트는 그 버그를 잡지 못한다 |

## Steps

**0. 지점 목록을 확보한다.** A 트랙은 스펙의 "테스트 먼저 지점" 표에서 "테스트 먼저" 행만 뽑는다. C 트랙은 `debug`에서 승인된 원인 가설 하나가 지점 하나다. 목록이 비면 이 스킬은 할 일이 없다.

지점마다 1~6단계를 반복한다. 한 번에 지점 하나만 연다.

**1. 작성자를 정한다.**
- 지점이 `core-gates.md` §1 표의 **통제 영역 열**에 닿으면 `test-writer` 서브에이전트가 쓴다. 두 열에 걸치면 통제 쪽으로 본다
- 그 밖은 이 대화에서 직접 쓴다

`test-writer`에는 **경로와 문장만** 넘긴다(`core-workflow.md` "구현" 절의 서브에이전트 호출 규약). 무엇을 넘기는지는 트랙마다 다르다.

| 트랙 | 넘기는 것 | 넘기지 않는 것 |
|---|---|---|
| A | 스펙 파일 · 지점(Must 항목 문장 그대로) · lang 팩 테스트 규칙 · 테스트를 둘 위치 | 구현 계획 · 구현 코드 조각 · "이렇게 만들 예정" |
| C | 버그 보고(기대 동작과 실제 동작) · 재현 스텝 · lang 팩 테스트 규칙 · 테스트를 둘 위치 | 원인 가설 · 수정 범위 — 이것이 C 트랙의 구현 계획이다 |

테스트가 구현이 아니라 스펙·기대 동작을 따르게 하기 위한 분리다.

**2. RED — 실패를 본다.** `test-writer`가 "필요한 껍데기"를 돌려줬으면 그 빈 시그니처를 먼저 만든다. 그다음 그 테스트만 골라 실행한다(단일 테스트 실행법은 lang 팩 테스트 규칙). 실패 출력을 읽고 사유를 분류한다.

| 실패 사유 | 다음 |
|---|---|
| 기능이 없어서 (대상 없음·기대값 불일치) | 3단계로 |
| 오타·설정·컴파일 오류·준비 데이터 오류 | 테스트를 고치고 2단계를 다시 |
| **처음부터 통과 — A 트랙** | 테스트가 아무것도 확인하지 않거나 기능이 이미 있다. 어느 쪽인지 확인한다. 기능이 이미 있으면 증거 표 RED 사유 칸에 "처음부터 통과(기존 동작)"를 적고 다음 지점으로 간다 |
| **처음부터 통과 — C 트랙** | 테스트가 버그를 재현하지 못한 것이다. 재현 스텝과 대조해 테스트를 고치고 2단계를 다시 |

빈 껍데기(시그니처만 있는 함수·빈 클래스)를 만들어야 컴파일되는 언어는 그것까지는 써도 된다. 동작은 넣지 않는다.

**3. GREEN — 최소 구현.** 이 테스트가 요구하는 만큼만 구현한다. 다음 지점이 필요로 할 것을 미리 넣지 않는다. 그 테스트를 다시 돌려 통과를 본다.

**4. 전체 확인.** `{{테스트 명령}}` 전체를 돌린다. 다른 테스트가 깨지면 이번 구현이 원인이므로 3단계로 돌아간다.

**5. REFACTOR — 초록일 때만 정리.** 중복 제거·이름 정리처럼 동작을 바꾸지 않는 정리만 하고, 끝나면 4단계를 다시 돌린다. 정리가 필요 없으면 건너뛴다.

**6. 증거 한 줄을 남긴다.** 아래 "증거 표"에 행을 추가한다.

### C 트랙 추가 단계 — 되돌리면 실패하는가 (T6)

버그 지점은 4단계가 끝난 뒤 **수정한 줄만 손으로 잠시 되돌려** 그 테스트가 다시 실패하는지 본다. 실패를 확인하면 수정을 원래대로 복구하고 4단계를 한 번 더 돌린다. 되돌려도 통과하면 테스트가 버그를 잡지 못하는 것이므로 2단계로 돌아간다. 되돌리기는 편집으로 한다 — 작업 트리를 통째로 되돌리는 명령은 쓰지 않는다.

**테스트로 재현할 수 없는 버그**(운영 환경에서만 생김·타이밍에 따라 생김 등)는 이 스킬을 쓰지 않는다. `debug` G2에서 원인 가설과 함께 **재현 불가 사유**를 보이고 승인받은 재현 절차로 대신한다. 이 버그는 증거 표 행 대상이 아니고, 완료 보고에 승인된 사유를 적는다.

## 증거 표

지점마다 한 줄. 완료 보고(채팅)에는 항상 넣고, `{{문서 루트}}/reports/` 작업 보고서를 쓰는 작업이면 그 "TDD 증거" 절에도 옮긴다. 실패 출력 전문은 붙이지 않고 사유만 요약한다.

| 지점 (스펙 항목) | 테스트 | 작성자 | RED 사유 | GREEN | 되돌림(C) |
|---|---|---|---|---|---|
| (Must 문장 요약) | (테스트 표시 이름) | 직접 / `test-writer` | (예: 대상 없음 · 기대 403 실제 200 · 처음부터 통과(기존 동작)) | 통과 | 실패 확인 / 해당 없음 |

**테스트를 고친 지점**(T5)은 표 아래에 "무엇을 왜 고쳤는지"를 한 줄씩 적는다.

## 금지

- RED를 보지 않고 구현 시작 · 실패 사유를 읽지 않고 GREEN으로 넘어감
- 통과시키려고 단언을 느슨하게 고치기 · 고치고 보고하지 않기
- 지점 두 개 이상을 한 번에 열기
- 승인되지 않은 지점에 이 절차를 늘려 적용하기 — 지점 추가는 스펙 amend 후
- `test-writer`에 구현 계획·코드 조각 넘기기
- 증거 표 없이 "TDD로 했다"고 보고

## It's working if

- 증거 표의 행 수가 지점 수(재현 불가로 승인된 버그 제외)와 같고, 모든 행에 RED 사유가 있다
- "처음부터 통과"한 테스트가 조용히 넘어가지 않고 보고에 남는다
- 버그 수정의 회귀 테스트마다 되돌림 확인 결과가 있다
