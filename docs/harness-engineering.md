# AI 하네스 엔지니어링 기록

Superchaeyeons가 AI 코딩 에이전트(Claude Code)를 어떻게 통제하도록 설계됐는지, 왜 그렇게 만들었는지를 한 파일에 모은 서술이다. 에이전트에게 맡기고 결과만 확인하는 방식이 아니라, 에이전트의 실행 경로 자체를 규칙·스킬·훅·검사기로 제한해 결과를 일관되게 만드는 방식을 택했다. 근거는 이 저장소의 실제 파일·커밋·감사 결과로 남긴다.

이 문서는 서술형 총정리다. 에이전트가 실제로 참조하는 SSOT는 각 절이 링크하는 원본 파일이고, 이 문서와 어긋나면 원본이 맞다. 레이어별 실행 흐름은 [`docs/harness/`](harness/README.md), 구성 요소 목록은 [`.claude/rules/README.md`](../.claude/rules/README.md)가 갖는다. 이 저장소의 이력이라 새 프로젝트에 배달하지 않는다.

## 1. 하네스가 필요한 이유

AI 코딩 에이전트는 매 세션 기억 없이 시작한다. 지시만으로 일관성을 기대하면 이런 일이 생긴다.

- 이번엔 맞게 구현한 값(TTL·enum·환경 변수 이름)을 다음 세션엔 다르게 쓴다
- "더 나은 방법"이라며 문서와 다른 판단을 조용히 코드에 넣는다
- 방금 짠 코드를 같은 대화에서 스스로 리뷰해 자기 판단을 재확인한다(self-grading 편향)
- 파괴적 명령(`git push --force`, `rm -rf`)을 프롬프트 지시만 믿고 실행한다
- 테스트를 돌리지 않고 "완료했습니다"라고 말한다

이 저장소는 이런 실패를 **프롬프트 반복이 아니라 파일로 고정**해서 막는다. 멈출 조건은 규칙으로, 반복 절차는 스킬로, 되돌리기 어려운 동작은 훅으로, 저장소 상태는 검사기로 판정한다.

## 2. 부품 구조

하네스를 다른 저장소에 옮겨 붙이자 규칙 본문을 대거 고쳐야 했다. 13패키지 모노레포인 `baro-farm-be`에 붙일 때는 core 규칙을 포함해 하네스 파일 21개를 고쳤다. 규칙 본문에 한 프로젝트의 경로·스택·배포 방식이 박혀 있었기 때문이다. 이렇게 갈라진 사본은 개선을 함께 받을 수 없다.

그래서 하네스를 **부품**으로 다시 짰다(2026-09-05~06, [v2 스펙](specs/cross-cutting/harness-slot-system-v2.md)).

- **3층 구조** — core(`core-*.md`·스킬·에이전트·훅)는 고치지 않는다. map(`harness-map.md`)은 `adopt` 스킬이 채운다. local(`local-*` 파일)은 자유롭게 고친다.
- **슬롯** — core 규칙은 경로·명령을 `{{스펙 저장소}}`·`{{테스트 명령}}` 같은 역할 이름으로만 부른다. 실제 값은 `harness-map.md`의 슬롯 22개가 갖는다.
- **능력 플래그** — "DB 마이그레이션 금지"처럼 프로젝트 상황을 전제한 정책은 `[플래그: X]` 배지를 단 절로 두고, ☑/❌는 `harness-map.md` 플래그 표 8행이 정한다. 끄려고 절을 지우지 않는다 — 지우면 부품이 갈라진다.
- **축** — 붙일 때 실측하는 네 가지(lang·shape·deploy·stage). `adopt`이 무엇을 물을지 정하는 질문 목록이다.
- **씨앗** — 언어·프레임워크 규칙은 배달물에 넣지 않고 `examples/seeds/`에 둔다. `adopt`이 플래그를 보고 복사한다. 검증된 스택만 씨앗이 되고, 없는 스택은 `_template/`을 실측으로 채운다.

core에 프로젝트 사실이 새면 `scripts/check-portability.sh`가 커밋을 막는다(C1 고유명사 · C2 스택 식별자 · C3 경로 리터럴 · C4 팩 참조). 결과는 실측으로 확인했다. 성격이 다른 네 저장소에 `adopt` 실측을 돌렸고, 네 경우 모두 값 파일·훅 상수·씨앗만으로 표현됐으며 core 변경은 0건이었다([P7 보고서](reports/2026-09-06-p7-generality.md)).

무엇을 들일지 판단하는 잣대는 **부품성 원칙** 셋이다. 장치 하나는 bash 하나와 데이터 파일 하나를 넘지 않는다. 새 개념은 기존 개념을 대체해야 한다. 언어·프레임워크·도구에 묶이는 것은 전부 팩(씨앗)으로 보낸다.

## 3. 작업 사이클 — 4 트랙 × 4 게이트

작업 성격에 따라 트랙 하나를 고르고, 트랙이 달라도 게이트 넷은 공통으로 지난다. SSOT는 [`core-workflow.md`](../.claude/rules/core-workflow.md)다.

| 트랙 | 언제 | 입구 스킬 | G2에서 승인받는 것 |
|---|---|---|---|
| A 기능 | 새 기능·API·엔티티·정책 변경 | `specify` | 스펙 |
| B 감사·리팩터 | 기존 코드 품질 개선 | `safe-refactor` | 불변 조건 + 감사 항목 |
| C 버그 | 버그 리포트·테스트 실패 | `debug` | 원인 가설과 수정 범위 |
| D 하네스 이식 | 하네스를 붙일 때·map 재동기화 | `adopt` | 실측 근거가 붙은 축·슬롯·플래그 |

게이트는 G1 리서치(외부 지식 확인) → G2 승인(사람이 끊는 지점) → G3 검증(완료 보고 전 기계 확인) → G4 회고(남길 것 남기기)다. 트랙이 먼저 정해져야 G2에서 무엇을 승인받을지가 정해진다. 버그 수정과 새 기능이 같은 절차를 밟을 이유는 없다.

## 4. 규칙 — 싣는 시점과 예산

`paths:` frontmatter가 없는 규칙은 매 세션 실리고, 있는 규칙은 맞는 파일을 열 때만 실린다. 지금은 always-load 8개(`core-*` 7개 + `harness-map.md`)와 path-scoped 3개(`core-code-comments.md`·`doc-writing.md`·`README.md`)다.

매 세션 무조건 지불하는 always-load 합계에는 **예산**을 걸었다. `check-portability.sh`가 상한 52,000B와 대조하고, 상한은 줄일 수만 있는 래칫이다. 2026-09-06에 합계를 64,600B에서 약 20% 줄이며 상한을 65,000B에서 52,000B로 내렸다.

규칙이 멈춰 세우는 근거는 둘로 나뉜다. `core-guardrails.md`는 "문서와 어긋나면 멈춘다", `core-gates.md`는 "변경이 통제 영역(도메인 규칙·인증·과금·계약·스키마)에 닿으면 멈춘다"를 맡는다. 멈추는 이유가 표현의 모호함이 아니라 변경의 성격이어야 판정이 재현되고, 위임 영역에서는 덜 묻게 된다. 상세: [Layer 1](harness/layer1-human-gate.md).

## 5. 스킬·서브에이전트 — 자기 보고 불신

스킬 8개는 전부 "에이전트의 말 대신 기계의 출력"을 요구한다. `preflight`는 "통과했다"는 말 대신 `{{테스트 명령}}`의 실제 결과를, `safe-refactor`는 "안 바꿨다"는 말 대신 불변 조건마다 검증 결과를 요구한다. 돌리지 못한 검증은 숨기지 않고 `report.md` "검증하지 못한 것"에 남긴다 — 환경이 없어 못 돌린 것은 실패가 아니라 기록할 대상이다.

감사·리뷰는 신선한 서브에이전트에게 맡긴다. 같은 대화 맥락에서 자기 결과를 평가하면 편향이 생기기 때문이다. 반대로 `retro`는 메인 컨텍스트에서 돈다. 회고의 입력이 대화 이력 자체라서, 격리하면 입력이 사라진다. 컨텍스트 격리를 원칙이 아니라 트레이드오프로 다룬 지점이다.

서브에이전트는 `tools`에서 `Edit`/`Write`를 뺐지만 `Bash`가 있어 물리적으로 막혀 있지는 않다. 이 층을 결정론적 차단으로 오해하지 않도록 [`.claude/rules/README.md`](../.claude/rules/README.md)에 명시했다. 상세: [Layer 2](harness/layer2-workflow-skills.md).

## 6. 훅 — 프롬프트로 안 되는 하한선

훅 5개는 `settings.json`에 등록된 이벤트에서 exit code로 동작한다. 파괴 명령 차단, 범위 밖 쓰기 차단, 검증 없는 완료 선언 되돌림, 열린 요청 알림, 미결정 설정 경고다.

설계 결정 세 가지가 이 층을 받친다.

- **판정 불가도 차단한다.** `deny-*` 훅은 JSON이 깨졌거나 python3가 없어 판정할 수 없을 때도 exit 2다. 판정 실패를 통과시키면 입력을 망가뜨리는 것이 우회 경로가 된다. `scripts/test-hooks.sh`가 케이스 108개로 이 규약을 판정한다.
- **승인 통로를 두지 않는다.** 훅은 사용자의 구두 승인을 알 수 없고, 알게 만들면(환경 변수·마커 파일) 에이전트도 그 통로를 연다. 막힌 것을 푸는 방법은 사람이 설정 값과 훅 상수를 바꾸는 것뿐이다.
- **판단은 LLM에게, 불변식은 스크립트에게.** "경고만 하고 절대 막지 않는다"는 판단이 아니라 불변식이라 `agent`-type 훅에 맡기지 않는다.

상세: [Layer 3](harness/layer3-deterministic-hooks.md).

## 7. 기계 검증 — 저장소 상태 판정

훅이 에이전트의 한 동작을 막는다면, 검사기는 저장소 상태를 판정한다. 셋 다 bash 하나와 데이터 파일 하나다.

| 검사기 | 판정 |
|---|---|
| `check-portability.sh` | core에 프로젝트 사실이 없는가 · always-load 예산 |
| `test-hooks.sh` | 훅 공통 규약 · 훅이 전부 등록돼 있는가 |
| `check-doc-style.sh` | 문서 개요·깊이·번역투(오류) · 제목 길이·약어·깨진 링크(경고) |

`scripts/verify.sh`가 셋을 한 번에 돌리는 이 저장소의 `{{테스트 명령}}`이고, `Stop` 훅이 이 명령의 실행 기록과 결과를 본다. git `pre-commit`이 stage된 내용에 따라 같은 검사를, `commit-msg`가 커밋 메시지 형식을 판정한다. 오탐이 나면 스크립트가 아니라 데이터 파일(패턴·케이스)을 고친다. 판단이 필요한 항목은 검사기에 넣지 않는다 — 넣으면 오탐으로 커밋이 막히고, 막히는 검사기는 곧 우회된다.

## 8. 실제로 겪고 고친 것

이 저장소의 규칙·훅 상당수는 처음부터 예측해 넣은 것이 아니라, 실제로 한 번 터진 문제를 겪은 뒤 재발 방지로 넣은 것이다. 근거: 2026-09-06 행은 [v2 스펙](specs/cross-cutting/harness-slot-system-v2.md) 변경 이력과 [씨앗 README](../examples/seeds/java-spring/README.md), 2026-09-07 행은 [감사 보고서](reports/2026-09-07-harness-audit-baseline.md)와 [하네스 회고](audits/harness-retro.md).

## 9. 안 하기로 한 것

서드파티 워크플로 플러그인, 규칙을 훅으로 주입하는 방식, 모호성 점수 게이팅, 훅 승인 우회 통로, 검증되지 않은 스택의 씨앗 등을 검토하고 채택하지 않았다. 각각의 이유와 다시 볼 조건은 [`out-of-scope/README.md`](out-of-scope/README.md)에 있다. 기능이 있다는 이유만으로 쓰지 않는다는 것을 명시적 배제 조건으로 뒀다([`core-tools.md`](../.claude/rules/core-tools.md) "도구 우선순위").
