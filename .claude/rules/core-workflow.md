# Core — 워크플로 (4 트랙 × 4 게이트)

**어떤 순서로 일하는지**를 정의한다. 작업 성격에 따라 트랙 A(기능)·B(감사·리팩터)·C(버그)·D(하네스 이식) 중 하나를 고르고, 트랙이 달라도 G1 리서치 → G2 승인 → G3 검증 → G4 회고는 모두 통과한다.

**⛔ `core-guardrails.md`가 이 문서보다 우선한다** — 게이트를 진행하는 것보다 중단·질문이 먼저다. 경로·명령·플래그는 `harness-map.md`가 SSOT · Git 형식: `{{Git 컨벤션 SSOT}}` (없으면 이 문서의 G2·G4가 SSOT)

## 사이클 — 4 트랙 × 4 게이트

작업 성격에 따라 **트랙**을 고르고, 트랙이 달라도 **게이트 4개는 공통**으로 통과한다.

```
진입(트랙 분류) → G1 리서치 → G2 승인 → 구현 → G3 검증 → G4 회고
                    │
                    ├─ A 트랙: 기능·API·DB          → specify
                    ├─ B 트랙: 감사·무손실 리팩터    → safe-refactor
                    ├─ C 트랙: 버그·테스트 실패      → debug
                    └─ D 트랙: 하네스 이식·재동기화  → adopt (코드 불변)
```

**⛔ STOP은 모든 게이트보다 우선한다** — 게이트를 진행하는 것보다 **중단·질문이 먼저**다.

## 진입 — 트랙 분류 (시작 전 30초)

1. `{{우선순위 SSOT}}` 활성 Milestone(MVP 출시/출시 이후)·Must
2. GitHub 이슈 — 범위·완료 기준 확인/생성 (**브랜치용 `#n` 확정**, 새 이슈 생성은 G2 ⚠️ 절 확인 필수)
3. 트랙 판정

| 트랙 | 언제 | 진입 (스킬) | Claude Code 도구 |
|------|------|-------------|------------------|
| **A. 기능** | 새 기능·API·엔티티·정책 변경 | DB·인증·3파일+ → `specify` → `{{스펙 저장소}}` → **승인 후** 구현 · 그 외 → `AGENTS.md` + 관련 `{{제품 범위}}` 확인 후 바로 구현 | Approved 스펙이 없을 때만 `EnterPlanMode`로 탐색·설계. 스펙 형식을 Plan Mode로 대체하지 않고, Approved면 Plan Mode 생략 |
| **B. 감사·리팩터** | 기존 코드 품질 개선 (G2에서 확정한 불변 조건 유지) | `safe-refactor` — 작업 단위 1개씩, 매 단계 승인 | `Agent`(`Explore`/`general-purpose`, 읽기 전용)로 신선한 컨텍스트 감사 |
| **C. 버그** | 버그 리포트·`{{테스트 명령}}` 실패 | `debug` — 재현 → 원인 분리 → 최소 수정 (운영 전용 재현 절차 포함) | 재현 → `Explore`로 관련 코드 탐색 |
| **D. 하네스 이식** | 하네스를 새 저장소에 붙일 때 · `harness-map.md`가 실제와 달라졌을 때 | `adopt` — 실측 → 축·슬롯·플래그 제안(승인) → 채움(승인). 애플리케이션 코드는 바꾸지 않는다 | `Bash`·`Glob`·`Grep` 실측 (읽기 전용) |

4. 문서 확인 순서: `AGENTS.md` → `harness-map.md` → `{{아키텍처 개요}}` → `{{우선순위 SSOT}}` → `{{클라이언트 전제}}` → `{{결정 기록}}` → `{{제품 범위}}`

**스펙 신호(A 트랙):** DB 스키마, 3파일+, BR-*, 프로필/배포, **인증·푸시·딥링크·결제** 등 클라 연동 API

**`[미정]` 처리와 priority 라벨:** `core-scope.md` (⛔ 단정 금지)
**저장소 고유 릴리즈 사실(Milestone·심사 게이트·도메인 용어):** `local-release.md`처럼 `local-` 접두사 규칙 파일로 따로 둔다 — 부품(`core-*`)과 층이 다르므로 이식성 검사 대상이 아니다
> 채운 예: `examples/tripfit/tripfit-release.md`

## G1. 리서치 게이트 — 외부 지식 확인

외부 라이브러리·SDK·API(프레임워크 주 버전 차이, 소셜 로그인 provider 스펙 등)에 의존하거나 처음 다루는 프레임워크 기능이면 **구현 전에** 확인한다. 학습 데이터가 stale하거나 실제 설치된 버전과 다를 수 있다. 이미 아는 내부 코드·컨벤션 확인은 위 진입 4번으로 충분하며 이 게이트 대상이 아니다.

**소스 우선순위 (위에서 답이 나오면 멈춤):** ① 로컬 실물(의존성 선언 파일·`{{의존성 조회}}`·설치된 패키지 실물) → ② 공식 문서(**버전 고정 필수**) → ③ 릴리즈 노트·마이그레이션 가이드 → ④ provider 공식 문서. **블로그·StackOverflow는 근거로 인용 금지** — 힌트로만 쓰고 ①②로 재확인한다.

> **[플래그: 스택 함정 메모]** 이 프로젝트가 쓰는 프레임워크의 **주 버전 함정**은 lang 팩 규칙에 한 문단으로 적는다 — 웹 예제 대다수가 다른 주 버전 기준이라 그대로 쓰면 깨지는 경우, 공식 문서 URL로 버전을 고정할 수 없는 경우 등. 플래그가 꺼져 있으면 이 절을 무시한다(삭제하지 않는다).
> 채운 예: `examples/seeds/java-spring/rules/local-g1-stack-trap.md`

**도구 선택:** 2개 이상 문서를 비교해야 하면 **`researcher` 서브에이전트**([`.claude/agents/researcher.md`](../agents/researcher.md) — 소스 우선순위·출력 포맷 SSOT), 단일 페이지 확인이면 인라인 `WebFetch`(서브에이전트 오버헤드가 더 큼).

## G2. 승인 게이트 — 사람이 끊는 지점

- **트랙별 승인 대상:** A = 스펙(`{{스펙 저장소}}`) · B = 감사 문서(`{{감사 로그}}/{unit}/{NNN}-*.md`)의 A/B 항목 · C = 원인 가설과 수정 범위 · D = 실측 근거가 붙은 축·슬롯·플래그 제안. 승인은 `AskUserQuestion` 또는 채팅 확인
- **요청이 열려 있으면 `ask` 스킬 먼저** — 열린 표현·미명시 기본값·해석이 갈리는 범위(`core-gates.md` 멈추는 신호). 사실은 조사하고 결정만 라운드로 묻는다
- **불변 조건(Invariant) 확정** — 이번 작업 내내 깨지면 안 되는 조건을 트랙 기본값(A: 기존 테스트 통과·기존 API 계약 — 새 필드 추가는 예외 · B: 비즈니스 로직·관찰 가능한 최종 동작 · C: 이 버그와 무관한 기존 동작 · D: 코드 불변)에서 시작해 사용자와 고친다. 완료 기준과 다르다 — 완료 기준은 끝났다고 판정하는 조건, 불변 조건은 도중 어느 시점에도 참인 조건
- 가정 명시 · 해석이 여러 개면 질문 · 더 단순한 방법 있으면 말하기
- 모호·문서 충돌 → **STOP §1** (구현 시작 금지)
- 변경 파일 목록 확정 (drive-by 리팩터 금지)
- 다단계: `1. [단계] → verify: [확인]`

**브랜치:** `main`에서 `{{브랜치명 형식}}` — 이슈 번호 생략 금지. 형식 SSOT: `{{Git 컨벤션 SSOT}}` (없으면 이 절)

**⚠️ 새 이슈·새 브랜치·새 PR 생성은 항상 먼저 확인** — `gh issue create` · 새 브랜치 분기 · `gh pr create`는 사용자가 명시적으로 요청하지 않았으면 **실행 전 채팅으로 묻는다.** 형식 규칙과 별개로 **만들지 여부 자체**를 임의 판단하지 않으며, 이슈·브랜치·PR을 만들 수 있는 모든 지점(`defer` 스킬, G4 PR 단계)에 적용된다. **커밋 승인은 PR 승인을 포함하지 않는다** — 구현·커밋까지 요청받았어도 PR 전에 다시 묻는다.

## 구현 — 코딩 중 지킬 것

- 요청 범위만 · 인접 “개선”·깨지지 않은 리팩터 금지
- 요청 밖 기능·단일 사용 추상화·불필요 설정 금지
- STOP 재확인 — 스펙과 다른 수치·계약·env 금지
- **레거시**는 같은 변경에서 삭제(STOP §2) · **계약에 닿는 변경**은 에러 코드·스펙·스키마까지 같은 턴(STOP §1.7) — "나중에" 금지
- 기존 스타일 유지. 내 변경으로 생긴 unused만 정리
- 패키지 구조·DTO·enum 표기는 **lang 팩 규칙**(`harness-map.md` 스택 팩 표)을 따른다. 주석은 `core-code-comments.md` 원칙(실행 줄 위 단계 주석 · 필드·의존성 해설 · 실물 대조 · 이유) + lang 팩 표기
- 핵심 로직 변경 시 `{{테스트 명령}}`
- 변경한 모든 줄은 사용자 요청에 직접 연결

## G3. 검증 게이트 — "완료" 보고 전

절차 SSOT: [`preflight` 스킬](../skills/preflight/SKILL.md). 자기 보고를 믿지 않고 **기계적으로** 확인한다.

- 변경 요약 + `{{테스트 명령}}` — 실행 없이 "통과했을 것"이라고 보고 금지
- 스펙·이슈 완료 기준을 **실제 코드**와 대조 (STOP §1.5 — 문서 문구만 보고 단정 금지)
- **API 추가·변경:** `{{API 문서}}` 동기화 + 관련 GitHub 이슈 (`gh issue view` → `gh issue edit`) + **[플래그: API 계약 보호]**면 lang 팩 "API 계약 변경" 절을 기준으로 커밋에 사유 트레일러 포함·계약 diff가 의도한 것뿐인지 확인
- **보안·아키텍처 성격 변경:** STOP §3 대상(토큰·세션·결제·개인정보 저장 방식 등)이면 `{{현재동작 요약}}` 해당 절 갱신 확인
- **레거시 재점검:** 이번 변경이 대체한 구 경로·상수·문서 ‘현행’ 문구가 남았는지 확인 후 **삭제/amend**. 요청 밖·정책 무관 dead code만 언급. **정책 불일치·교체 잔존 → STOP §2 삭제**
- **문서 품질:** 새 문서 또는 **50줄 이상** 고친 문서는 **`doc-reviewer` 서브에이전트**(기준 `doc-writing.md`, advisory — 문체는 exit code로 판정할 수 없다). 오타·한 줄 수정은 대상 아님
- **[플래그: 스택 리뷰어]** 스택 코드 **3파일 이상**·API·DB 변경이면 lang 팩이 지정한 **스택 리뷰어 서브에이전트** — 정적 검사가 잡지 못하는 결함(트랜잭션 경계·N+1·권한 게이트 누락 등)이 대상. 단일 파일 수정은 대상 아님
- **규모 게이트:** Must Have급(3파일+·API·DB)이면 `code-review` 또는 `simplify`를 서브에이전트 컨텍스트에서 한 번 더 (`core-tools.md` "별도 컨텍스트 리뷰")

## G4. 회고 게이트 — 남길 것 남기기

- **프로젝트 문서 갱신 점검 (매 작업):** 새로 확정된 설계 결정·컨벤션·틀리기 쉬운 함정이 있으면 `AGENTS.md`·`.claude/rules/*.md` 갱신 수정안을 **제안**한다 — 자동 갱신 금지, 승인 후 반영. 배운 게 없으면 조용히 스킵
- 같은 실수 2회+ → `.claude/rules/` 추가 **제안** — 절차는 **`retro` 스킬**, 승인 후 `{{문서 루트}}/audits/harness-retro.md`에 append. 코드·설계 개선은 `core-followup.md` 몫
- **트랙별 기록:** B 트랙은 `{{감사 로그}}/refactor-log.md`에 append · Entity·스키마 후 ERD 개선과 Must Have급 후속 제안 → `core-followup.md` · 「다른 이슈로」 → `defer` 스킬
- **`report.md`** — Must Have급(3파일+·API·DB) 작업은 `{{문서 루트}}/reports/{YYYY-MM-DD}-{kebab-topic}.md`에 남긴다: 무엇을 · 어떤 결정 · 실행한 검증 → 결과 · **검증하지 못한 것과 이유** · 남은 것 (골격: `{{문서 루트}}/templates/reference-doc.md`). 환경이 없어 못 돌린 검증은 실패가 아니라 여기에 남기는 것이 정상 경로다
- **PR 전:** `Closes #n`·PR 체크리스트를 구현·테스트와 대조 (`[x]`만 실제 완료). 수동·미구현·`[제안]`·현재 Milestone 밖은 체크 금지. **`gh pr create` 실행 전 사용자에게 먼저 확인** — G2 "새 이슈·새 브랜치·새 PR 생성은 항상 먼저 확인" 절
- 커밋·PR: 메시지는 `{{커밋 메시지 형식}}`, base `main`, **merge commit 유지** (Squash 금지). 형식 SSOT: `{{Git 컨벤션 SSOT}}` (없으면 이 절)
- **커밋 분할안 제안:** 작업이 끝나면 **사용자가 묻지 않아도** 어떻게 나눌지 먼저 제안한다. 목적·주제별 **최대 5개**. 억지 분할 금지 — 한 주제면 1개
- **절대 마음대로 커밋하지 않는다** — 제안은 제안일 뿐이고, 실행은 사용자 승인 후
- **PR merge 확인 후:** 작업 브랜치 삭제 (원격+로컬). merge 안 된 브랜치는 삭제 금지
