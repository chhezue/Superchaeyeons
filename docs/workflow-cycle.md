# 하네스 한 사이클 따라가기

작업 하나가 시작부터 커밋 제안까지 어떤 순서로 흐르는지 10단계로 따라간다. 각 단계에서 무엇을 하고, 왜 그 자리에 있고, 무엇이 보이면 다음으로 넘어가도 되는지를 적었다. 하네스를 처음 여는 사람이 20분 안에 전체 그림을 잡는 것이 목표다. 지금 값·목록 하나를 확인하러 왔으면 [`harness/component-map.md`](harness/component-map.md)가 더 빠르다.

## 이 문서를 읽고 나면

- 새 작업을 받았을 때 어느 트랙으로 들어갈지 스스로 고를 수 있다
- 각 게이트에서 무엇을 승인받아야 하는지, 승인 없이 넘어가면 무엇이 막는지 안다
- "완료"라고 말하기 전에 무엇을 돌려야 하는지 안다
- 규칙·스킬·훅 중 어느 것이 각 단계를 맡는지 구분할 수 있다

## 사전 준비

- [`.claude/rules/harness-map.md`](../.claude/rules/harness-map.md)의 슬롯·능력 플래그가 채워져 있다. ⬜가 남아 있으면 `adopt` 스킬부터 돌린다
- `./scripts/install-git-hooks.sh`를 한 번 돌렸다
- 이 저장소의 검증 명령이 무엇인지 안다 — `scripts/verify.sh`

## 한 장으로 보는 흐름

트랙은 넷 중 하나만 고르고, 게이트 넷은 어느 트랙이든 전부 지난다.

```text
진입(트랙 판정) → G1 리서치 → G2 승인 → 구현 → G3 검증 → G4 회고
                    │
                    ├─ A 기능·API·DB    → specify
                    ├─ B 감사·리팩터     → safe-refactor
                    ├─ C 버그           → debug
                    └─ D 하네스 이식     → adopt
```

## 1. 진입 — 정해진 순서로 읽고 트랙을 고른다

문서를 읽는 순서가 고정돼 있다. `AGENTS.md` → `harness-map.md` → `{{아키텍처 개요}}` → `{{우선순위 SSOT}}` → `{{클라이언트 전제}}` → `{{결정 기록}}` → `{{제품 범위}}` 순이다. 매번 저장소를 새로 스캔하지 않으려고 `harness-map.md`가 실측 결과를 값으로 들고 있기 때문이다. 값이 실제와 달라졌으면 `adopt` 스킬이 다시 실측한다.

그다음 GitHub 이슈에서 범위와 완료 기준을 확인하고, 없으면 만들지부터 사용자에게 묻는다. 브랜치 이름에 넣을 번호가 여기서 확정된다.

마지막으로 작업 성격을 A(기능·API·DB) · B(감사·무손실 리팩터) · C(버그) · D(하네스 이식) 중 하나로 판정한다. 트랙이 정해져야 뒤의 G2에서 무엇을 승인받을지가 결정된다. 버그 수정과 신규 기능이 같은 절차를 밟을 이유가 없다.

**이러면 성공:** 트랙 한 글자와 이슈 번호를 말할 수 있다.

## 2. 요청 해석 — 결정만 골라 묻는다

"알아서·적당히·최적화·개선해줘" 같은 열린 표현, 명시되지 않은 기본값, 해석이 갈리는 범위가 있으면 `ask` 스킬로 인터뷰한다. 핵심은 사실과 결정을 가르는 것이다. 코드·설정으로 확인할 수 있는 사실은 직접 조사하고, 사람만 답할 수 있는 결정만 라운드 단위로 묻는다. 열린 요청을 스스로 해석해 구현하면 되돌리는 비용이 가장 크기 때문이다.

`ask-open-request` 훅이 프롬프트에서 열린 표현을 찾아 리마인더를 주입한다. 다만 이 훅은 막지 않는다 — 프롬프트 단계에서 차단하면 사용자가 쓴 프롬프트가 사라지기 때문이다. 건너뛰지 못하게 하는 장치가 아니라 알려 주는 장치다.

`core-workflow.md` 원문은 이 절차를 G2 승인 게이트 아래에 두는데, 여기서는 순서대로 읽히도록 앞당겨 설명한다.

**이러면 성공:** 남은 질문이 사람만 답할 수 있는 것뿐이다.

## 3. G1 리서치 — 외부 지식만 확인한다

외부 라이브러리·프레임워크 주 버전·외부 로그인 규격처럼 우리 코드 밖 지식에 의존하면 구현 전에 확인한다. 학습 데이터가 낡았거나 실제 설치된 버전과 다를 수 있다. 소스 우선순위는 로컬 실물 → 공식 문서(버전 고정) → 릴리즈 노트 → 서비스 제공자 문서 순이고, 위에서 답이 나오면 멈춘다. 블로그·질의응답 사이트는 힌트로만 쓰고 근거로 인용하지 않는다.

이미 아는 내부 코드·컨벤션 확인은 1단계로 충분해서 이 게이트 대상이 아니다. 문서를 둘 이상 비교해야 하면 `researcher` 서브에이전트, 한 페이지만 보면 인라인으로 가져온다.

**이러면 성공:** 근거로 붙인 링크가 버전이 고정된 공식 문서다.

## 4. G2 승인 — 불변 조건을 확정한다

사람이 끊는 지점이다. 여기서 둘을 확정한다.

- **불변 조건** — 작업 내내 어느 시점에도 참이어야 하는 조건. 트랙 기본값(A는 기존 테스트와 API 계약, B는 관찰 가능한 최종 동작, C는 이 버그와 무관한 기존 동작, D는 코드 한 줄도 바꾸지 않음)에서 시작해 사용자와 고친다
- **변경 파일 목록** — 하는 김에 옆을 고치는 일을 막는다

불변 조건은 완료 기준과 다르다. 완료 기준은 끝났다고 판정하는 조건이고, 불변 조건은 도중 어느 시점에도 깨지면 안 되는 조건이다.

승인이 필요한지는 변경이 닿는 영역으로 갈린다. 도메인 규칙·인증·과금·개인정보·외부 계약·마이그레이션은 통제 영역이라 트랙과 무관하게 승인 대상이고, 매핑 계층·상용구·문서 초안만 건드리면 짧게 지나간다. 무조건 묻는 마찰은 곧 무시당해서, 선택적 마찰이라야 실제로 지켜진다.

**이러면 성공:** 불변 조건 한 문장과 변경 파일 목록을 승인받았다.

## 5. 설계 기록 — A 트랙이면 스펙을 먼저 쓴다

되돌리기 비싼 변경일수록 승인 대상이 말이 아니라 문서여야 한다. 채팅으로 합의한 값은 다음 턴에 흐려지지만 스펙 파일은 남아서 나중에 구현과 대조할 수 있다. DB 스키마·세 파일 이상·인증·결제처럼 스펙 신호가 있으면 `specify`로 `{{스펙 저장소}}`에 스펙을 만들고 승인 후에 구현한다. 승인된 스펙이 있으면 탐색 모드를 생략하고, 스펙이 없을 때만 탐색한다. 새로 내린 아키텍처 결정은 사용자 승인을 받아 `{{결정 기록}}`에 결정 기록으로 남긴다.

⛔ STOP 1절은 첫 단계부터 모든 규칙보다 먼저 적용되지만, 값이 실제로 오가는 이 단계에서 가장 자주 걸린다. 문서와 다른 만료 시간·API 계약·enum·환경 변수 이름을 조용히 맞추는 것이 금지되고, 문서끼리 값이 다르면 한쪽을 임의로 고르지 않고 충돌을 목록으로 만들어 확인받는다.

**이러면 성공:** 승인된 스펙이 `{{스펙 저장소}}`에 있고, 그 값과 구현 계획이 같다.

## 6. 구현 첫 줄 전에 환경을 확인한다

`preflight` 스킬 사전 모드로, 코드를 쓰기 전에 지금 상태에서 빌드·테스트가 실제로 도는지 확인한다. "구현은 끝났는데 검증 환경이 죽어 있어 완료를 말할 수 없다"를 막는 자리다. 이 저장소에서는 `scripts/verify.sh` 하나가 그 명령이다.

**이러면 성공:** 검증 명령이 지금 상태에서 돌고, 실패한다면 그 실패가 내 변경과 무관하다는 것을 확인했다.

## 7. 구현한다 — 훅이 지켜본다

요청 범위만 고친다. 이번 변경이 대체한 구 경로·상수·문서 문구는 같은 커밋에서 지우고(STOP 2절), 계약에 닿는 변경은 에러 코드·스펙·응답 스키마까지 같은 턴에 끝낸다(STOP 1.7절). "다음 커밋에 정리"는 금지다.

다른 단계와 달리 여기에는 기계가 막는 층이 붙어 있다.

| 막는 것 | 막는 주체 |
|---|---|
| 위험한 셸 명령 — force push · 재귀 삭제 · hard reset · 검사 건너뛴 커밋 · `.env` 커밋 | `deny-dangerous-bash.sh` |
| `{{작업 범위}}` 밖 파일 쓰기 · 훅과 `settings.json` 수정 | `deny-out-of-scope-write.sh` |
| 테스트를 돌리지 않은 완료 선언 | `deny-unverified-completion.sh` |

훅이 막은 일은 다른 도구로 우회하지 않는다. 훅은 사람의 구두 승인을 알 수 없고, 알게 만들면 그 통로를 에이전트도 열 수 있어 판정이 흔들리기 때문이다. 막혔으면 무엇이 왜 막혔는지와 무엇을 바꾸면 되는지를 한 줄로 보고하고 멈춘다.

**이러면 성공:** 변경한 모든 줄이 요청에 직접 연결된다.

## 8. G3 검증 — 완료 전에 돌린다

`preflight` 사후 모드로 기계적으로 확인한다. 실행하지 않고 "통과했을 것"이라고 보고하는 것이 금지고, 스펙 체크박스가 아니라 실제 코드와 대조한다. 문서는 기능이 머지된 뒤 갱신이 누락되면 낡기 때문이다. `Stop` 훅은 코드를 고친 턴에 완료·통과를 선언하는데 검증 명령의 실행 기록이 없으면 턴을 되돌린다. 고치기만 하고 아직 완료라고 말하지 않았으면 걸리지 않는다.

이 저장소의 검증은 `scripts/verify.sh` 하나로 묶여 있다. 부품 이식성·훅 규약·문서 스타일 검사기 셋을 한 번에 돌린다.

**이러면 성공:** 검증 명령의 실행 결과를 보고에 그대로 붙였다.

## 9. 독립 리뷰 — 새 컨텍스트에서 본다

방금 짠 코드를 같은 대화에서 리뷰하면 자기 판단을 재확인하게 된다. 그래서 "객관적으로 봐 달라"는 부탁이 아니라, 새 서브에이전트 컨텍스트에서 변경분과 기준만 보고 판단하게 만든다. 새 문서나 50줄 이상 고친 문서는 `doc-reviewer`, 세 파일 이상·API·DB 변경은 `code-review` 또는 `simplify`가 맡는다. 한 줄 수정까지 매번 돌리지는 않되, 되돌리기 비싼 변경은 커밋 전에 돌린다.

**이러면 성공:** 리뷰 지적을 반영했거나, 반영하지 않은 이유를 적었다.

## 10. G4 회고 — 남길 것을 남긴다

이번 작업에서 배운 것을 다음 작업이 물려받게 만드는 단계다. 남기지 않으면 같은 실수를 같은 방식으로 다시 한다.

- 하네스 자체의 결함은 `retro` 스킬로 `{{문서 루트}}/audits/harness-retro.md`에 남긴다. 같은 실수가 두 번 이상 나오면 규칙 추가를 제안한다. 자동으로 추가하지 않는다
- 코드·설계 개선은 후속 제안 3~8개로 적고 같은 턴에 구현하지 않는다
- 미루기로 한 범위는 `defer` 스킬이 스펙 수정부터 이슈 생성까지 같은 턴에 처리한다
- 세 파일 이상·API·DB 작업은 `{{문서 루트}}/reports/`에 보고서를 남긴다. 환경이 없어 돌리지 못한 검증은 실패가 아니라 여기 "검증하지 못한 것"에 적는 것이 정상 경로다
- 커밋 분할안을 목적·주제별로 최대 다섯 개까지 제안한다. 한 주제면 하나다

커밋·이슈·브랜치·PR 생성은 사용자가 명시적으로 요청하지 않았으면 실행 전에 묻는다. 커밋 승인은 PR 승인을 포함하지 않는다.

**이러면 성공:** 분할안을 제안하고 승인을 기다리는 상태로 끝났다.

## 잘 됐는지 확인

한 사이클이 끝났으면 아래가 전부 참이어야 한다.

- `scripts/verify.sh`가 통과했고 그 결과를 보고에 붙였다
- 승인 없이 만든 커밋·이슈·브랜치·PR이 없다
- 훅이 막은 것을 다른 도구로 우회하지 않았다
- 새로 안 사실이 `harness-map.md` 값이나 `local-*.md`에 들어갔고, `core-*.md`는 그대로다
