# Improve Harness — 회고 후보 검토

회고 루프의 **검토** 단계다. 루프는 세 단계로 돈다 — 일하던 에이전트가 "회고할 때인가"를 스스로 판단하지 않아도 돌게 하기 위해서다(`{{문서 루트}}/specs/cross-cutting/harness-retro-loop.md`).

| 단계 | 누가 | 결과 |
|---|---|---|
| 기록 | 훅 `auto-correction-queue.sh` — 정정 기억이 저장될 때마다, 모델 비용 0 | `.claude/corrections/queue.tsv` |
| 분석 | `scripts/analyze-corrections.sh` — 사용자가 직접 또는 예약 실행으로 따로 돌린다 | `.claude/corrections/candidates.md` |
| 검토 | **이 스킬** — 세션 안에서 사용자와 | 장부(`{{문서 루트}}/audits/harness-retro.md`) |

세션 시작 알림(`auto-correction-notice.sh`)이 "검토할 후보 K건"을 띄우면 이 스킬을 쓸 때다. 이 스킬은 대화 이력을 다시 읽어 후보를 찾지 않는다 — 분석은 이미 별도 실행에서 세션별 사용자 메시지 요약을 보고 근거(세션 ID·메시지 번호)를 검사했다.

## 다루는 것과 다루지 않는 것

범위가 겹치면 같은 내용이 세 곳에 쌓인다. 아래 경계를 지킨다.

| 대상 | 담당 | 예 |
|------|------|-----|
| **하네스 자체의 결함** | **이 스킬** | 규칙이 못 걸러낸 실수 · 게이트를 건너뛴 지점 · 문서 SSOT가 stale해 잘못 답한 사고 · 훅으로 승격할 만한 반복 |
| 코드·설계 개선 | `verify-work` 마무리 후속 제안 | ERD·API 설계·쿼리 성능·패키지 구조 |
| 범위를 다음 이슈로 미루기 | `write-spec` 스킬 "범위를 미룰 때" | Draft 스펙 + 이슈 생성 |

## When to Use

- 세션 시작 알림에 검토할 후보가 있을 때
- 사용자가 "회고", "이번에 배운 거 정리" 등을 요청할 때

**생략:** 후보 파일에 `### ` 후보가 없을 때. 억지로 후보를 만들지 않는다 — 사용자가 회고를 요청했는데 후보가 없으면 마지막 분석 시각(`.claude/corrections/last-analysis`)과 분석 명령 `scripts/analyze-corrections.sh`를 알려 주고 멈춘다. 분석은 비용이 드는 별도 실행이라 사용자가 돌린다.

## Steps

1. **후보 읽기** — `.claude/corrections/candidates.md`에서 `### `로 시작하는 후보를 모두 읽는다. 후보마다 종류가 붙어 있다.

   | 종류 | 뜻 |
   |---|---|
   | `[새 행]` | 장부에 없는 증상. 근거 2건 이상 |
   | `[R-n 값 변경]` | 반영한 조치 뒤에 같은 증상이 다시 났다. `재발`과 `효과` 값 제안 |
   | `[R-n 되돌리기]` | `효과`가 `효과 없음`·`해로움`으로 확정된 조치가 더한 글을 지우자는 제안 |

   후보 아래 "버림:" 줄은 스크립트가 근거 부족으로 버린 것이라 검토하지 않는다. "장부 점검" 줄은 반영된 행마다 이번 분석에서 재발이 있었는지다.

2. **근거 확인** — 후보의 근거(`세션 ID #메시지 번호`)를 `.claude/corrections/digests/<세션 ID>.json`에서 열어 실제 사용자 말과 맞는지 본다. 원인으로 지목한 규칙·스킬도 열어, 이미 그 내용이 있는지 확인한다. 이미 있으면 "규칙이 없다"가 아니라 "규칙이 실리지 않았다·지켜지지 않았다"가 증상이다.

3. **층 확인** — 후보가 고르는 층이 맞는지 본다. 이 저장소는 강제력이 다른 4개 층을 쓴다.

   | 층 | 언제 | 예 |
   |----|------|-----|
   | 규칙(`.claude/rules/`) | 맥락 판단이 필요함 | STOP 절 추가·기존 절 보강 |
   | 스킬·에이전트 | 절차가 여러 단계임 | 새 게이트 절차 |
   | 훅(`.claude/hooks/`) | **exit code로 판정 가능함** | 금지 패턴 차단 |
   | 문서 SSOT | 값·계약이 어긋남 | 스펙·ERD amend |

   판정 불가능한 것을 훅으로 만들지 않는다 — 계약 변경 경고 훅을 LLM 판단(agent-type)에 맡겼다가 실패한 이력이 있다(`.claude/rules/README.md` "훅 공통 규약"). 항상 실리는 규칙에 더하는 후보는 예산(`scripts/check-portability.sh`)과 바이트를 함께 보인다.

4. **⛔ 하나씩 묻기** — 후보를 **한 메시지에 하나씩** 사용자에게 보이고 답을 받는다. 파일에 쓰기 전에 멈춘다.
   - 각 후보: **무엇이 문제였나 → 어느 층으로 → 근거(어느 세션의 어떤 말) → 토큰 비용**
   - 답은 셋 중 하나다: 장부에 올림 · 버림 · 보류(후보 파일에 남김)
   - `core-reporting.md` 적용 — 용어를 풀어 쓰고 결과 중심으로 쓴다

5. **기록** — 사용자가 고른 대로 장부를 고친다. 장부는 행을 더하거나 특정 행의 값만 고치고, 통째로 다시 쓰지 않는다.
   - `[새 행]` → 장부 표 끝에 다음 `ID`(`R-`와 세 자리 번호)로 행을 더한다. 상태는 `승인 대기 — 수정안 제시(날짜)`, `효과`는 `미확인`, `재발`은 `—`
   - `[R-n 값 변경]` → 그 행의 `재발`을 "세션 N개 · 마지막 날짜"로 누적하고, 사용자가 동의한 `효과` 값으로 바꾼다
   - `[R-n 되돌리기]` → 7단계처럼 별도 승인으로 글을 지운 뒤 상태를 `되돌림(날짜)`로 바꾼다
   - 검토를 마친 후보(올림·버림)는 `candidates.md`에서 그 `### ` 묶음을 지운다. 보류만 남긴다 — 세션 시작 알림의 후보 수가 이 파일에서 나온다

6. **효과 값** — `효과`는 근거가 있을 때만 고친다. 같은 실수가 그대로 났으면 `효과 없음`, 조치가 새 실수를 만들었으면 `해로움`, 같은 시기에 다른 규칙도 바꿨거나 관찰이 한 번뿐이면 `판정 불가`. 재발 없이 시간이 지났다는 것만으로 `도움됨`을 쓰지 않는다 — 효과가 없는 규칙이 계속 남는다.

7. **다듬기** — **[플래그: Gemini 다듬기]** ☑면 장부 기록을 마친 뒤 장부를 `write-spec` 9단계와 같은 방식으로 다듬는다.
8. **반영은 별도 승인** — 장부는 백로그일 뿐이다. `.claude/rules/`·스킬·`AGENTS.md`를 실제로 고치거나 지우는 것은 diff를 보이고 **다시 승인을 받고** 진행한다. 자동 갱신 금지(`core-workflow.md` G4 · `core-gates.md` §3). 반영하면 그 행의 상태를 `반영(날짜)`로 바꾼다.

## 금지

- 후보 파일에 없는 후보를 이 대화의 인상만으로 만들어 채우기
- 승인 없이 장부에 쓰거나 `.claude/rules/`를 고치기
- 장부를 통째로 다시 쓰거나 요약하기 — 행 추가와 값 변경만
- 코드·설계 개선을 여기 섞기 (G4 후속 제안 담당)
- exit code로 판정할 수 없는 것을 훅 후보로 분류
- 후보 여러 개를 한 메시지에 몰아 묻기

## It's working if

- 장부의 새 행마다 근거 2건(세션 ID와 메시지 번호)이 있고, 승인 전에는 규칙 파일이 한 줄도 바뀌지 않았다
- 검토를 마친 뒤 `candidates.md`에는 보류한 후보만 남고, 다음 세션 시작 알림의 후보 수가 그만큼 줄었다
