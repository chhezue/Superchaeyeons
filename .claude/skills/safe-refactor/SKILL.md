# Safe Refactor

**이 스킬이 기본 동작과 다른 단 하나:** 무엇을 지킬지 스킬이 정하지 않는다. **G2에서 사용자와 확정한 불변 조건(Invariant) 목록**을 읽고 그것만 지킨다. "API 계약 100% 동일"은 그 목록의 흔한 항목 하나일 뿐이고, 릴리즈 전 프로젝트는 목록에서 뺄 수 있다.

새 기능 개발이 아니라 **기존 코드 품질 개선**이 목적일 때 쓴다. `specify`가 "구현 전 스펙"을 강제하듯, 이 스킬은 "감사 → 승인 → 구현 → 기계 검증" 순서를 강제한다.

**이 스킬은 `core-workflow.md` 사이클의 B 트랙이다.** 아래 6단계는 트랙 공통 게이트와 이렇게 대응한다 — 게이트의 내용 자체는 `core-workflow.md`가 SSOT이며 여기서 중복 정의하지 않는다.

| 이 스킬 | 공통 게이트 |
|---------|-------------|
| 1. Audit | 진입 + **G1 리서치** — 외부 라이브러리·기술 선택 판단이 필요하면 `researcher` |
| 2. 승인 | **G2 승인** — 불변 조건 목록 + A/B 항목 확정 |
| 3. Implement | 구현 — 코딩 중 지킬 것 |
| 4. Verify | **G3 검증** — `preflight` 스킬 (불변 조건마다 기계 검증) |
| 5. Report | **G4 회고** — `refactor-log.md` append + 감사 문서 "구현 결과" 절 + 문서 갱신 점검 |
| 6. 다음 작업 단위 | 다음 사이클 진입 (승인 필요) |

점검 항목은 [`references/audit-checklist.md`](references/audit-checklist.md)가, A/B/C/D 분류 기준과 산출물 포맷은 [`references/audit-template.md`](references/audit-template.md)가, 불변 조건은 이 파일이 SSOT다.

## 불변 조건 (Invariant)

작업 내내 어느 시점에도 참이어야 하는 조건이다. 완료 기준("끝났다고 판정하는 조건")과 다르다. B 트랙 기본값은 아래 둘이고, G2에서 사용자가 추가·삭제한다.

| 기본 불변 조건 | 기계 검증 방법 |
|---|---|
| 비즈니스 로직·정책이 바뀌지 않는다 | 기존 `{{테스트 명령}}` 전부 통과 |
| 관찰 가능한 최종 동작이 바뀌지 않는다 | 계약 diff 도구가 있으면(lang 팩 "API 계약 변경" 절) diff 0, 없으면 테스트 통과로 대체 |

사용자가 "계약을 바꿔도 된다"고 하면 두 번째 항목을 빼고 그 대신 무엇을 지킬지 적는다. 감사 항목마다 **`불변 조건 영향`** 을 표시해, 승인 때 항목별로 고를 수 있게 한다.

`core-guardrails.md` ⛔ STOP은 이 스킬보다 항상 우선한다 — 특히 레거시 즉시 삭제(§2), 계약에 닿는 변경의 같은 턴 갱신(§1.7).

## When to Use

- 사용자가 "아키텍처 감사", "리팩토링 감사·정리" 등을 요청하거나 `safe-refactor {작업 단위}` 형태로 지정할 때
- 새 API·기능 추가가 아니라 기존 코드 내부 품질(중복·Dead Code·Legacy·프레임워크 관례·성능·구조) 개선이 목적일 때

## 작업 단위

감사·리팩터는 **작업 단위 하나씩** 진행한다. 작업 단위는 `{{스펙 저장소}}` README의 폴더↔패키지(모듈) 매핑 표가 정한다. 없으면 최상위 패키지·모듈 하나를 단위로 삼고, 어느 것부터 할지는 사용자에게 묻는다. 여러 단위를 동시에 감사·구현하지 않는다.

## Steps

### 1. Audit — 읽기 전용, 신선한 서브에이전트

- `Agent` 툴(`subagent_type: Explore` 또는 `general-purpose`, 읽기 전용)로 **새 서브에이전트**를 띄워 해당 작업 단위만 스캔한다. 방금 짠 코드를 같은 대화에서 스스로 평가하면 자기 판단을 재확인하는 편향이 생기기 쉽다(`core-tools.md`).
- 프롬프트에 반드시 포함: 대상 경로, `references/audit-checklist.md` 점검 항목 전체, A/B/C/D 분류 기준, `references/audit-template.md` 포맷, 기본 불변 조건, "코드 수정 금지 — 읽기·분석만".
- **G1 하위 단계:** 감사 중 "더 나은 라이브러리·패턴이 있는가"가 판단에 필요하면 `researcher`를 부른다. 그 결과는 감사 문서의 `## 근거`와 **물리적으로 분리된 `## 참고 — 외부 사례`** 절에 둔다. A/B 판정 근거는 여전히 코드에서 확인한 사실만 인정한다.
- **A 트랙 승격 신호:** 개선에 새 의존성·새 기술·계약 변경이 필요하다고 판단되면 항목을 "승격 후보"로 표시하고 멈춘다. 리팩터가 조용히 아키텍처 변경으로 번지는 것을 막으면서 길은 열어 둔다 — 승인되면 `specify`로 넘어간다.
- 산출물: `{{감사 로그}}/{unit}/{NNN}-{kebab-topic}.md` — 작업 단위 안에서 `001`부터 증가 (신규 작성, **코드는 건드리지 않음**). H1 아래 개요 한 문단 필수.

### 2. 승인 (G2)

- 불변 조건 목록을 먼저 확정한다 — 기본값을 보이고 추가·삭제를 묻는다.
- 감사 문서의 A/B 항목을 `불변 조건 영향`과 함께 요약 보고하고, 실제로 진행할 항목을 확인받는다. 승격 후보는 별도로 묻는다.
- 승인받지 않은 항목은 손대지 않는다. C/D는 이번 라운드에서 구현 대상이 아니다.

### 3. Implement

- 승인된 A/B 항목만, 우선순위(Critical → High → Medium → Low) 순으로 구현한다.
- `core-workflow.md` "구현 — 코딩 중 지킬 것" 절 전체 준수 — 요청 범위만, drive-by 리팩터 금지, 레거시는 같은 변경에서 삭제.
- 구현 중 불변 조건에 닿게 되면 **즉시 멈추고 사용자에게 확인** — 목록을 바꾸거나 항목을 미룬다.

### 4. Verify — 불변 조건을 기계로 증명

LLM의 "안 바꿨다"는 자기 보고를 신뢰하지 않는다. 절차 SSOT는 `preflight` 스킬이고, 불변 조건마다 위 표의 검증 방법을 실제로 돌린다. 하나라도 실패하면 "일단 커밋"하지 않고 원인 분석 → 재수정 → 재검증. 환경이 없어 돌릴 수 없는 검증은 `report.md` "검증하지 못한 것"에 남긴다.

### 5. Report (G4)

- 감사 문서 끝의 **`## 구현 결과 (YYYY-MM-DD)`** 절에 반영한 항목·검증 결과·미룬 항목을 적는다 (`audit-template.md`에 자리가 있다).
- `{{감사 로그}}/{unit}/refactor-log.md`에 append — 날짜, 반영 항목, 변경 파일·라인 수, 불변 조건별 검증 결과, 남긴 C/D와 이유. H1 아래 개요 문단 유지.
- 새로 만든 문서·50줄 이상 고친 문서는 `doc-reviewer`로 확인.
- 사용자 보고는 `core-reporting.md` 문체로.

### 6. 다음 작업 단위

- 사용자 승인 없이 다음 단위로 자동 진행하지 않는다.

## 금지

- 여러 작업 단위 동시 감사·구현
- 승인 없는 A/B 항목 구현, 또는 감사 문서 작성과 같은 턴에 바로 구현
- 불변 조건에 닿는 변경을 "개선"이라는 이유로 진행 · 스킬 본문에 취소선을 그어 원칙을 끄기 (불변 조건 목록을 바꾼다)
- 검증 전 "완료" 보고 · 돌리지 못한 검증을 숨김
- C/D 항목을 이유 없이 나열만 하고 넘어감

## It's working if

- 승인 요청 메시지에 불변 조건 목록과 항목별 영향이 함께 보인다
- 계약을 바꾸는 리팩터를 요청받아도 스킬 본문을 고치지 않고 목록만 바꿔 진행할 수 있다
- 감사 문서마다 "구현 결과" 절이 같은 자리에 있다
