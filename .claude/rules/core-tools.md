# Core — 도구 규약과 채택 기준

트랙·게이트마다 어떤 스킬·에이전트·도구를 쓰는지는 `core-workflow.md`의 트랙 표와 게이트 절이 직접 적는다. 이 파일은 그 표에 담기 어려운 셋만 갖는다 — 서브에이전트를 부르는 규약, 별도 컨텍스트 리뷰가 필요한 이유, 서드파티 도구를 들일지 판단하는 기준.

## 서브에이전트 호출 규약

**에이전트 지침에 이미 적힌 읽기 범위를 호출자가 덮어쓰지 않는다** — 비용을 지배하는 건 모델이 아니라 입력 크기다.

- 대상은 **경로 목록으로만** 넘기고, 어디까지 읽을지는 에이전트 지침에 맡긴다
- "전문을 읽어라"는 **신규 파일에만** 지시한다 (기존 파일은 diff로 충분)
- 대상이 10개를 넘으면 **나눠 부른다**
- 독립 작업의 병렬 탐색은 `Agent` 툴(`Explore`·`general-purpose`) — 중복되면 하나만

## 별도 컨텍스트 리뷰

PR·머지 전(요청 시), 그리고 **API·DB 등 Must Have급 변경은 커밋 전 기본으로** `code-review` 또는 `simplify`를 돌린다. 둘 다 새 서브에이전트 컨텍스트에서 diff와 기준만 보고 판단한다.

방금 짠 코드를 같은 대화에서 스스로 리뷰하면 자기 판단을 재확인하는 편향이 생긴다(생성과 평가가 같은 컨텍스트에 있을 때의 self-grading 편향). 한 줄·단일 파일 핫픽스까지 매번 강제하지는 않되, 되돌리기 비싼 변경은 커밋 전에 돌린다.

## 도구 우선순위

```
1. Claude Code 기본 기능
2. 서드파티 플러그인 (OMC · Superpowers 류)
3. 프로젝트 문서 (.claude/rules/, .claude/skills/)
```

상위 단계로 필요를 충분히 채우면 하위 단계로 내려가지 않는다. 서드파티 플러그인은 이 저장소에 설치돼 있지 않고, 설치는 새 의존성을 들이는 결정이므로 사용자 승인 없이 하지 않는다. **채택 조건(전부 만족):** 문서가 더 단순해진다 · 반복 작업이 사라진다 · 유지보수성이 오른다 · 토큰 또는 작업량이 준다. **배제 조건(하나라도):** 기능이 있다는 이유만으로 쓴다 · 기존 문서보다 복잡해진다 · 토큰만 는다 · 기본 기능으로 충분하다.

**현재 결론:** 검토한 서드파티 플러그인은 채택하지 않았다. 무엇을 왜 기각했고 언제 다시 볼지는 `{{문서 루트}}/out-of-scope/README.md`가 SSOT다 — 새 도구를 제안하기 전에 그 표를 먼저 본다.

## 금지

- Approved 스펙·decisions와 다른 값을 "더 나은 방법"으로 덮어쓰기
- `preflight` 스킬 없이 "테스트 통과"·"이슈 완료" 주장
- 스펙·이슈 없이 대형 기능 구현 시작 (Milestone·라벨 체계가 있는 프로젝트는 `local-priority.md`의 금지도 함께)
- 트랙을 건너뛰고 게이트만 형식적으로 통과 — 트랙이 정해져야 G2 승인 대상이 무엇인지 결정된다
