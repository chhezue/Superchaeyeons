# Layer 2 — 스킬과 서브에이전트

반복되는 작업 유형마다 단계와 승인 지점을 고정한 스킬, 그리고 서브에이전트(게이트에서 부르는 조사·리뷰 에이전트와 구현 단계에서 부르는 `test-writer`)를 설명한다. 읽고 나면 스킬이 규칙보다 강하고 훅보다 약한 이유, 어떤 일은 컨텍스트를 격리하고 어떤 일은 격리하지 않는 이유를 알 수 있다.

> 분류: **skill** (`.claude/skills/*/SKILL.md`) · **agent** (`.claude/agents/*.md`) · 강제 수단: 절차와 사용자 승인 게이트 · 현행 목록 SSOT: [`.claude/rules/README.md`](../../.claude/rules/README.md) Skills·Agents 절

## 스킬 레이어 소개

**스킬**은 여러 단계로 된 작업 절차서다. 중간에 사용자 승인을 받는 지점이 박혀 있다. 공통 명제는 하나다 — **에이전트의 자기 보고를 믿지 않는다.** "테스트 통과했습니다" 대신 `{{테스트 명령}}`의 실제 종료 코드를, "동작은 안 바꿨습니다" 대신 불변 조건마다 기계 검증 결과를 요구한다.

**서브에이전트**는 게이트에서 부르는 전담 인력이다. 별도 컨텍스트에서 돌기 때문에 조사 원문이 메인 대화를 채우지 않고, 방금 짠 결과를 같은 맥락에서 스스로 평가하는 편향도 피한다.

## 등장 배경

같은 종류의 작업을 매번 다른 순서로 하면 어느 단계를 건너뛰었는지 아무도 모른다. 특히 "승인받고 구현"과 "구현하고 검증"은 에이전트가 가장 쉽게 생략하는 단계다. 그래서 작업 성격을 트랙 넷으로 나누고, 트랙마다 스킬 하나를 입구로 정했다. 게이트 넷(G1 리서치 · G2 승인 · G3 검증 · G4 회고)은 모든 트랙이 공통으로 지난다.

게이트의 내용은 `core-workflow.md`가 SSOT다. 스킬 문서는 자기 단계가 어느 게이트에 대응하는지만 적는다 — 게이트를 두 곳에 정의하면 한쪽만 고쳐져 어긋난다.

## 스킬이 실리는 방식

스킬은 `name`과 `description` 한 줄만 항상 컨텍스트에 보이고, 에이전트가 그 작업을 알아보고 부를 때 `SKILL.md` 전문이 실린다. 규칙([Layer 1](layer1-human-gate.md))이 항상 켜진 배경이라면 스킬은 필요할 때 꺼내 읽는 절차서다.

그래서 **`description` 한 줄이 곧 트리거다.** frontmatter가 깨져 `description`이 읽히지 않으면 에러도 로그도 없이 스킬이 덜 불릴 뿐이라, 게이트가 작동하지 않는데도 아무도 모른다. 각 `SKILL.md`가 첫 줄에 "기본 동작과 다른 단 하나", 끝에 "It's working if"(파일을 열지 않고 확인 가능한 신호)를 두는 것도 이 때문이다 — 스킬이 실제로 돌았는지 밖에서 알아볼 수 있어야 한다.

`debug`가 규칙이 아니라 스킬인 이유도 같은 구조에서 나온다. 트리거가 "버그 리포트를 받았는가"라는 **상황**이라 파일 경로 기반 `paths:`로 표현할 수 없고, always-load 규칙에 넣으면 매 세션 토큰을 먹는다.

## `safe-refactor` 흐름

승인 지점이 가장 많고 검증이 가장 엄격한 스킬이라 대표로 풀어 쓴다.

```text
[1] Audit — 읽기 전용, 신선한 서브에이전트
     대상 경로 · 점검 항목 전체 · A/B/C/D 분류 기준 · 기본 불변 조건 · "코드 수정 금지"
     더 나은 라이브러리·패턴이 판단에 필요하면 researcher (G1 하위 단계)
     새 의존성·계약 변경이 필요하면 "A 트랙 승격 후보"로 표시하고 멈춘다

[2] 승인 (G2)
     불변 조건 목록을 먼저 확정 → 감사 A/B 항목을 "불변 조건 영향"과 함께 보고

[3] Implement — 승인된 항목만
     불변 조건에 닿게 되면 즉시 멈추고 확인

[4] Verify (G3) — preflight 스킬로 불변 조건마다 기계 검증

[5] Report (G4) — refactor-log.md append, 남긴 C/D와 이유 포함

[6] 다음 작업 단위 — 사용자 승인 없이 자동 진행 금지
```

**불변 조건(Invariant)** 은 작업 도중 어느 시점에도 참이어야 하는 조건이다. 스킬이 무엇을 지킬지 스스로 정하지 않고, G2에서 사용자와 확정한 목록만 지킨다. 완료 기준(끝났다고 판정하는 조건)과 다르다.

**1단계가 서브에이전트인 이유:** 방금 짠 코드를 같은 대화에서 평가하면 자기 판단을 재확인하는 **self-grading 편향**이 생긴다. 스킬은 여기서 한 발 더 나가, 이번 세션에서 건드리지 않은 코드라도 신선한 컨텍스트를 쓰라고 한다. 같은 대화 맥락 자체가 편향원이기 때문이다.

## `preflight` — 두 시점의 검증

`preflight`는 검증 절차의 SSOT다. 다른 스킬은 검증을 자체 정의하지 않고 이 스킬을 부른다.

- **사전 모드 (G2 직후):** 구현 전에 빌드·테스트가 **지금 상태에서** 도는지 먼저 확인한다. 기존 실패를 이번 작업 탓으로 착각하지 않기 위해서다. 환경이 없어 못 돌릴 검증은 이때 목록으로 적는다.
- **사후 모드 (완료 보고 전):** 테스트 실행 · 스펙 체크리스트를 **실제 코드**와 대조 · 불변 조건 · 계약 변경 · 레거시 잔존(고친 문서 안의 자기모순 포함) · 문서 품질 · 리뷰어 · 규모 게이트. 통과한 항목만 `[x]`로 보고하고, 못 돌린 검증은 숨기지 않고 `report.md` "검증하지 못한 것"에 이유와 함께 남긴다.

## 서브에이전트

| 에이전트 | 게이트 | 하는 일 |
|---|---|---|
| `researcher` | G1 | 외부 라이브러리·SDK 조사. 로컬 실물 버전 → 공식 문서(버전 확인) → 릴리즈 노트 순서. 블로그·StackOverflow는 근거로 인용하지 않는다 |
| `test-writer` | 구현 | `tdd` 지점이 통제 영역에 닿으면 구현 계획을 모르는 상태에서 스펙 문장만 보고 실패하는 테스트를 쓴다. 같은 대화에서 테스트와 구현을 함께 쓸 때의 편향을 끊는 장치다 |
| `doc-reviewer` | G3 | 소유권·유형 → 정보 구조 → 문장 3단계 리뷰(기준 `doc-writing.md`). advisory — 커밋을 막지 않는다 |
| `{스택}-reviewer` | G3 | **[플래그: 스택 리뷰어]** 씨앗에 있다. 정적 검사가 이미 잡는 규칙은 지적하지 않고, 트랜잭션 경계·N+1처럼 정적 규칙으로 표현할 수 없는 결함만 본다 |

`test-writer`를 뺀 셋은 `tools`에서 `Edit`/`Write`를 뺐다. 하지만 `Bash`가 있어 물리적으로는 파일을 고칠 수 있다 — 마지막 한 겹은 지침의 "수정하지 않는다" 규범이다. `test-writer`는 테스트를 써야 해서 `Write`/`Edit`가 있고 `Bash`가 없으며, "프로덕션 코드는 쓰지 않는다"가 같은 성격의 규범이다. 이 층을 결정론적 차단으로 오해하지 않는다.

**호출 규약** (`core-tools.md`): 대상은 경로 목록으로만 넘기고, 어디까지 읽을지는 에이전트 지침에 맡긴다. "전문을 읽어라"는 신규 파일에만 지시한다. 대상이 10개를 넘으면 나눠 부른다. 서브에이전트 비용을 지배하는 것은 모델이 아니라 **입력 크기**다 — 기존 파일까지 전문 읽기를 시키면 diff만 보면 될 일에 수배의 토큰이 든다. 판단이 필요한 리뷰어의 모델을 낮추는 것보다 입력을 줄이는 쪽이 효과가 크다.

## 격리가 손해인 작업

`retro`만 메인 컨텍스트에서 돈다. 회고의 입력이 세션 대화 이력 자체인데 서브에이전트는 그 이력에 접근할 수 없다. `safe-refactor`가 편향을 피하려 일부러 컨텍스트를 격리하는 것과 정반대다. 같은 저장소 안에서 "격리가 편향을 줄이는 작업"(감사·리뷰)과 "격리가 입력을 없애는 작업"(회고)이 갈린다 — 컨텍스트 격리는 원칙이 아니라 트레이드오프다.

## 이 저장소에서의 적용

**`adopt`로 범용성을 실측했다 (2026-09-06).** `adopt` 1단계 실측을 `scripts/adopt-probe.sh`로 만들고, 성격이 다른 네 저장소에 돌렸다 — 이 저장소, 원본 백엔드 프로젝트, 13패키지 모노레포(`baro-farm-be`), 마이그레이션이 있는 Node 가상 저장소. 네 경우 모두 `harness-map.md` 값·훅 상수·씨앗만으로 표현됐고 core 변경은 0건이었다([보고서](../reports/2026-09-06-p7-generality.md)).

**불변 조건을 문서 작업에도 썼다 (2026-09-06).** always-load 규칙을 약 20% 줄이는 작업에서 "규칙의 뜻은 바뀌지 않는다"를 불변 조건으로 두고, `doc-reviewer`가 diff를 대조해 확인했다([v2 스펙](../specs/cross-cutting/harness-slot-system-v2.md) 변경 이력). 리팩터 대상이 코드가 아니어도 같은 틀이 적용된다.

**리뷰어 기준을 사고에서 넓혔다 (2026-09-08).** 감사에서 다른 저장소 문서가 파일 단위로 남아 현재형으로 서술되는 문제가 나왔다. 값 하나가 틀린 것과 달리 문서 전체가 남의 것이라, 문장 단위 리뷰로는 잡히지 않았다. `doc-reviewer` 1단계에 **소유권 축**(이 문서가 이 저장소 것인가 · 이력인가 지시인가)을 넣었다([하네스 회고](../audits/harness-retro.md) 2026-09-08 행).

## 한계

스킬은 에이전트가 **부르기로 선택해야** 작동한다. 그래서 이 레이어는 [Layer 3 훅](layer3-deterministic-hooks.md)보다 한 단계 약하다. 절차로 되는 것과 절차로 안 되는 것을 나눈 것이 설계의 요점이다 — 완료 선언 전 검증은 `preflight` 스킬로도 요구하지만, 건너뛰면 `Stop` 훅이 되돌린다.
