# 하네스 레이어 설명 (`docs/harness/`)

하네스를 **강제력** 기준 4개 레이어로 나누고, 각 레이어가 언제 발동해서 무엇을 막는지 설명한다. 이 파일은 이 저장소의 `{{현재동작 요약}}`과 `{{아키텍처 개요}}`다 — 훅·규칙의 동작이 바뀌면 같은 턴에 아래 "지금의 실제 동작" 절을 쉬운 말로 고친다. 구성 요소 목록은 [`.claude/rules/README.md`](../../.claude/rules/README.md)가 SSOT이고, 이 폴더는 이 저장소의 기록이라 새 프로젝트에 배달하지 않는다.

## 4개 레이어

레이어는 "무엇으로 강제하는가"로 갈린다. 아래로 갈수록 에이전트의 판단과 무관해진다.

| 레이어 | 무엇으로 강제하나 | 파일 | 언제 |
|---|---|---|---|
| **L1 규칙** | 프롬프트 — 에이전트가 읽고 따른다 | `.claude/rules/` | 세션 시작(always-load) · 해당 종류 파일을 열 때(`paths:`) |
| **L2 스킬·서브에이전트** | 절차와 사람 승인 단계 · 별도 컨텍스트 | `.claude/skills/` · `.claude/agents/` | 에이전트나 사용자가 부를 때 |
| **L3 훅** | exit code — 도구 호출 직전·턴 종료 | `.claude/hooks/` · `.claude/settings.json` | Bash·파일 쓰기 직전, 턴 종료 |
| **L4 기계 검증** | 검사기 exit code — 완료 선언 전·커밋 직전 | `scripts/` · `scripts/git-hooks/` | `verify.sh` 실행 · `git commit` |

판단이 필요한 것은 L1·L2에 두고, 되돌리기 비싸면서 exit code로 판정할 수 있는 것만 L3·L4로 내렸다. 모든 것을 훅으로 막으면 오탐이 쌓이고, 오탐이 잦은 장치는 우회된다. L3과 L4의 차이는 대상이다 — 훅은 에이전트의 동작 하나를 막고, 검사기는 저장소 상태를 판정한다.

## 레이어와 사이클의 관계

실제 작업은 `core-workflow.md`의 트랙 × 규모 × 게이트를 따라 흐른다. 같은 게이트라도 강제하는 레이어가 다르다.

| 사이클 단계 | 담당 | 강제 레이어 |
|---|---|---|
| 진입 — 트랙(A 기능·B 감사·C 버그·D 이식)·규모(S·M·L) 판정 | `specify` · `safe-refactor` · `debug` · `adopt` | L1 |
| **G1 리서치** | `researcher` | L1·L2 — 강제 수단 없음 |
| **G2 승인** | 사람 (`ask` 인터뷰 → 트랙별 승인 산출물) | L1 `core-gates.md` · L2 스킬 승인 단계 |
| 구현 | 에이전트 · `tdd` · `test-writer` | **L3** `deny-dangerous-bash.sh` · `deny-out-of-scope-write.sh` |
| **G3 검증** | `preflight` · `doc-reviewer` · L 규모는 `code-review`/`simplify` | **L3** Stop 훅 + **L4** `scripts/verify.sh` |
| **G4 회고·커밋** | `retro` · `report.md` · 커밋 분할안 | L1·L2 · 커밋 시 **L4** `pre-commit`·`commit-msg` |

강제력이 가장 약한 곳은 G1과 G4다. 조사를 했는지, 배운 것을 남겼는지는 exit code로 판정할 수 없어 규칙과 절차에만 기댄다.

## 지금의 실제 동작

이 저장소에서 하네스가 실제로 하는 일이다. 정확한 조건은 각 훅·스크립트 머리 주석이 SSOT다.

- **세션을 열면** always-load 규칙과 `CLAUDE.md`·`AGENTS.md`가 자동으로 실린다. 다른 규칙은 해당 종류의 파일을 열 때만 실린다. 어느 파일이 어느 쪽인지는 `.claude/rules/README.md` 목록에 있다.
- **작업 크기를 먼저 정한다.** 오타·한 줄 수정 같은 작은 작업은 바로 고치고 검증 명령만 돌린다. 3개 이상 파일이나 API·DB를 건드리는 큰 작업은 별도 리뷰와 작업 보고서까지 남긴다.
- **"알아서", "최적화해줘"처럼 결정이 비어 있는 요청이면** 에이전트가 규칙에 따라 먼저 질문으로 범위를 좁힌다.
- **되돌리기 어려운 명령은 실행 전에 막힌다.** 강제 푸시, 폴더 통째 삭제, 커밋 기록 되돌리기, 커밋 전 검사 건너뛰기, 비밀값 파일(`.env`) 커밋, DB 테이블 삭제 같은 것들이다. 명령 문장에 그 글자가 들어 있기만 해도 막히는 오탐이 있는데, 놓치는 것보다 낫다고 보고 그대로 둔다.
- **작업 범위 밖 파일은 못 쓴다.** 이 저장소는 범위가 저장소 전체라 이 검사는 사실상 꺼져 있다. 파일 쓰기 도구 네 개(Write·Edit·MultiEdit·NotebookEdit) 모두에 걸린다.
- **에이전트가 하네스 자신(훅 스크립트·`settings.json`)을 고칠 수 있다.** 이 저장소는 하네스를 고치는 곳이라 허용했다. 새 프로젝트에 붙이면 기본으로 막히는데, 훅이 막는 것은 파일 쓰기 도구뿐이고 Bash로 고치는 것은 규칙으로만 막는다.
- **테스트를 먼저 쓰는 곳은 사람이 정한다.** 스펙을 쓸 때 에이전트가 "이 항목은 테스트 먼저"를 제안하고 사람이 고친다. 그 항목과 버그 수정은 실패하는 테스트를 먼저 보고 구현하며, 완료 보고에 "어느 테스트가 왜 실패했다가 통과했는지" 표를 붙인다. 인증·결제처럼 중요한 곳은 구현 계획을 모르는 별도 에이전트가 테스트를 쓴다. 이 순서를 지켰는지 기계로 막지는 않는다 — 검증 단계에서 표를 대조할 뿐이다.
- **파일을 고친 뒤 검증(`scripts/verify.sh`)을 돌리지 않고 "완료"라고 하면** 대화가 끝나지 않고 되돌아온다. 돌렸는데 실패했어도 같다. 한 번만 되돌리므로 무한 반복은 없다. 검증이 통과하면 단계마다 한 줄만 출력하고, 실패한 단계만 전체 출력을 보인다.
- **커밋할 때** 규칙에 프로젝트 고유 이름이 섞였는지, 지운 규칙·훅·스킬을 가리키는 문장이 남았는지, 훅이 약속대로 동작하는지, 문서 형식이 맞는지를 검사한다. 커밋 메시지 형식(`{Type}: {한글}`)이 틀려도 막힌다.
- **훅이 막은 것을 풀어 달라고 말로 승인해도 훅은 모른다.** 푸는 방법은 사람이 설정 값 표(`harness-map.md`)와 훅 상수를 직접 바꾸는 것뿐이다. 에이전트가 풀 수 있는 통로를 만들면 에이전트도 그 통로를 연다.
