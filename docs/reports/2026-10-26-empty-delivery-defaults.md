# 배달본에서 프로젝트 값 비우기 — 작업 보고서

새 프로젝트로 복사되는 배달본에 원본 프로젝트와 이 저장소의 값이 기본값으로 남아 있어서 비웠다. core의 Git 운영 정책 세 가지를 슬롯으로 뺐고, 커밋 형식 훅 상수와 CONTRIBUTING 견본을 빈칸으로 바꿨다. 테스트 명령 훅 상수는 하네스 공통 `scripts/dev.sh test`만 허용하고, 배달되는 `scripts/dev.conf`도 빈칸으로 바꿔 이 저장소 값은 루트 `dev.conf`로 옮겼다. 같은 값이 다시 들어오면 검사기가 막는다.

## 무엇을 했나

- **core 슬롯화:** `core-workflow.md` G2·G4의 base 브랜치 `main`, "merge commit 유지(Squash 금지)", "PR 본문은 `Closes #n`", "이슈 번호를 빼지 않는다", merge 뒤 브랜치 삭제를 슬롯 `{{기본 브랜치}}`·`{{머지 방식}}`·`{{이슈 연결}}`로 바꿨다. `core-guardrails.md` §1.5의 `gh issue view`는 "트래커에서 본다"로, `preflight` 2·4단계의 `gh issue` 호출은 `{{이슈 연결}}`로 바꿨다. 슬롯 정의와 이 저장소 값은 `harness-map.md`에 있다
- **커밋 형식 훅 상수 비우기:** `commit-msg`의 `COMMIT_RE`를 빈 값으로 바꿨다. 빈 값이면 검사하지 않는다. 오류 안내에 박혀 있던 형식 예시도 지우고 실제 정규식을 보여 준다
- **테스트 명령 훅 상수:** `deny-unverified-completion.sh`의 `TEST_CMD`는 원격에 먼저 들어온 대로 `scripts/dev.sh test`다. 프로젝트마다 다른 실제 명령은 `scripts/dev.conf`가 갖고, 이 줄은 모든 프로젝트에서 같다
- **dev.conf 비우기:** 이 저장소 값을 배달되지 않는 루트 `dev.conf`로 옮기고(`git mv`), `scripts/dev.conf`는 `_template` 씨앗과 같은 `{…}` 빈칸으로 바꿨다. `dev.sh`는 `DEV_CONF` → 루트 `dev.conf` → `scripts/dev.conf` 순으로 찾고, 엔진 테스트에 이 순서를 확인하는 케이스 3건을 더했다. 검사기는 하네스 원본에서만 `scripts/dev.conf`를 보고 채워진 값을 잡는다. `pre-commit`은 루트 `dev.conf`가 stage돼도 엔진 테스트를 돌린다
- **엔진 테스트 실패 수정:** 헬스 시간 초과 케이스가 원격에서도 늘 실패했다. bash 3.2가 끈 앱 작업을 `Terminated: 15` 줄로 출력 맨 앞에 알렸기 때문이라, 앱을 띄운 직후 작업 표에서 뺐다(`disown`). 이 수정이 없으면 `dev.sh`를 stage한 커밋이 `pre-commit`에서 막힌다
- **CONTRIBUTING 견본 비우기:** 기본 브랜치·브랜치 type·커밋 type 표·머지 정책·이슈 연결·라벨 체계·리뷰 등급을 슬롯이나 "(프로젝트가 채운다)" 빈칸으로 바꿨다
- **검사기 패턴 5개:** `portability-patterns.txt`의 C1에 머지 방식 · 이슈 트래커·연결 문법 · 기본 브랜치 이름 · 커밋 메시지 형식 · 값이 채워진 훅 상수 패턴을 넣었다. `TEST_CMD`는 `check-portability.sh`가 `scripts/dev.sh test` 한 줄만 건너뛴다. 붙여 쓰는 프로젝트에서는 훅 상수의 값이 검사 밖이라 마지막 패턴이 걸리지 않는다
- **훅 테스트:** `test-hooks.sh`의 scope 열에 `;test=CMD` 치환을 더하고, `TEST_CMD`가 빈 값이면 막지 않는 케이스를 하나 추가했다
- **adopt:** 배달본이 값을 비워 둔다는 전제로 바꾸고, 실측 항목과 체크리스트에 기본 브랜치·머지 방식·이슈 트래커와 `COMMIT_RE` 채움을 넣었다. `adopt-probe.sh`가 이모지 커밋 형식 · `{type}/{key}-{n}-{desc}` 브랜치 · 첫 부모 merge 커밋 수 · 이슈 흔적을 함께 뽑는다
- **기록:** 슬롯 스펙 §5 amend와 변경 이력, `harness-engineering.md` 인시던트 표, `docs/harness/README.md` 현재 동작을 고쳤다

## 결정

| 결정 | 근거 | 대안 |
|------|------|------|
| `TEST_CMD`는 비우지 않고 `scripts/dev.sh test`로 둔다 | 실제 명령이 `dev.conf`로 옮겨 가 훅 값은 모든 프로젝트에서 같다. 프로젝트 값이 아니고, 이 저장소의 Stop 훅도 살아 있다 (2026-10-26 사용자 결정) | 빈 값 — 이 저장소에서 미검증 완료 선언을 막는 검사가 꺼진다 |
| 이 저장소도 `COMMIT_RE`를 비운다 | 배달본과 이 저장소의 git 훅이 같은 파일이라, 이 저장소 값을 두면 그대로 배달된다 | 복사 스크립트가 배달할 때만 비우기 — 파일에는 값이 남아 "배달본은 빈칸"을 검사로 지킬 수 없다 |
| `harness-map.md`의 이 저장소 값은 남긴다 | 이 파일은 프로젝트 값을 적는 자리이고 `adopt`이 실측으로 덮어쓴다. 검사기도 이 파일을 검사하지 않는다 | 이 파일까지 비우기 — 이 저장소 규칙이 `{{테스트 명령}}`을 찾지 못해 멈춘다 |
| `HARNESS_SELF_EDIT="1"`은 남긴다 | 0으로 두면 이 저장소에서 훅을 고칠 수 없다. `adopt`은 붙여 쓰는 프로젝트에서 이미 ❌가 기본이라고 정해 둔다 | 비우기 — 같은 이유로 자기 수정이 막힌다 |
| 이 저장소 `dev.conf`는 루트에 둔다 | `scripts/`는 통째로 배달된다. 루트는 배달되지 않고, 에이전트가 치는 명령은 그대로 `scripts/dev.sh test`라 Stop 훅 판정이 바뀌지 않는다 (2026-10-26 사용자 결정) | `DEV_CONF` 환경 변수 — 매 호출에 접두어가 필요하고 Stop 훅 판정을 다시 봐야 한다 |
| 브랜치 삭제는 `{{머지 방식}}`에 묶고 슬롯 설명을 짧게 쓴다 | always-load 예산이 원격 변경과 합쳐 199B만 남았다 | 별도 슬롯 `{{브랜치 정리}}` — 예산을 넘는다 |

## 검증하지 못한 것

| 무엇 | 왜 못 했나 | 누가·언제 확인하나 |
|------|-------------|------------------|
| 루트에 다른 용도의 `dev.conf`가 있는 프로젝트 | 그런 저장소에 붙여 보지 않았다. `adopt` 체크리스트에 "루트에 `dev.conf`가 없다"를 넣어 두었다 | 다음에 붙일 때 `adopt` 체크리스트로 |
| 빈 배달본을 새 저장소에 복사해 `adopt`을 끝까지 돌리기 | 이번 작업 범위가 배달본 수정까지였다 | 다음에 실제 저장소에 붙일 때 `adopt` 체크리스트로 |
| 이 저장소에서 `commit-msg`가 꺼진 영향 | 꺼진 상태로 커밋해 보지 않았다. 설치된 옛 훅은 그대로라 재설치 전까지는 검사가 남는다 | 사용자 — `install-git-hooks.sh`를 다시 돌릴 때 |
| 기록 문서 속 원본 프로젝트 값 | 스펙 §4 "기본값" 열과 옛 보고서는 이력이라 고치지 않았다 | — |

## 남은 것

- 이 저장소에서 커밋 형식 검사를 되살리려면 배달되지 않는 자리의 값을 훅이 읽게 해야 한다. 새 개념이 하나 늘어나므로 따로 결정한다
