# Claude Code와 Codex 하네스 공동 지원

기존 Claude Code 플러그인과 기능을 보존하면서 로컬 Codex 앱·CLI(명령줄 도구) 연결을 추가한다. 정책 원본은 하나로 유지하고 도구별 설치·이벤트·승인·기록만 분리한다. 2026-11-10 사용자가 최종 검수 후 진행을 승인했다. 단계별 파일·훅·설정 변경은 아래 절차로 검토한다.

> 상태: Approved (2026-11-10 사용자 승인)
> MVP: In scope
> 관련 BR: N/A
> 트랙·규모: A · L

## 목표

두 도구에서 같은 하네스 정책을 사용하면서 Claude의 기존 기능을 보존한다. 기존 Claude 기능 확인 → 공통 내용을 유지하며 Codex 연결 추가 → 초기화에서 도구 선택 → 양쪽 실제 검증 순서로 진행한다. Codex 제약 때문에 Claude 기능을 낮추지 않는다.

## 배경

이전 초안의 Codex 전용 전환은 사용자 의도를 잘못 해석한 미승인 계획이었다. Claude 지원 종료와 파일 삭제 계획은 철회한다. 기존 [Claude 플러그인 스펙](harness-plugin-delivery.md)의 계약은 유지하며, 공동 지원 관계를 추가한다. AGENTS.md의 하네스 유지보수 범위에 포함된다.

2026-11-10 설치본은 `codex-cli 0.167.0-alpha.3.2`다. 현재 PATH(실행 파일 검색 경로)에는 `claude`가 없다. 버전 출력만으로 플러그인 설치·활성화·훅 신뢰·실제 실행을 확인했다고 보지 않는다.

## 설계

현재 `plugin/`을 유지한다. 규칙 7개, 스킬 8개의 절차, 검사 도구를 복제하지 않는다. 기존 Claude 진입점은 보존하고 Codex 입력을 연결하는 작은 경계부터 검증한다. 공통 판정 추출은 중복이 실제 생기는 지점에 한정한다.

- 입력 연결: Claude Edit 등의 파일 경로와 Codex `apply_patch`의 `tool_input.command`를 공통 작업 목록으로 변환한다. 작업은 추가·수정·삭제·이동과 원본·대상 경로를 가진다. 명령 입력도 별도 변환한다.
- 공통 판정: 정규화한 경로·명령·프로젝트 설정을 받아 허용·차단·승인 필요와 이유를 반환한다. 입력 오류는 안전하게 거절한다.
- 출력 연결: Claude는 기존 승인 창과 차단 응답을 유지한다. Codex는 검증된 차단 응답만 사용하고 `permissionDecision: "ask"`를 등록하지 않는다.
- 프로젝트 값: 첫 단계에서는 `.claude/harness.conf`를 양쪽이 읽는 단일 원본으로 유지한다. 이름만을 위해 이동하지 않는다. Codex 설치 안내에 이 위치가 공통 설정임을 밝힌다. `dev.conf`도 복제하지 않는다.
- 기록: Claude의 `.claude/corrections/`·`.claude/polish/`를 유지하고 Codex 기록은 `.codex/corrections/`·`.codex/polish/`로 분리한다. 분석·다듬기 절차는 공유하되 저장 위치와 입력 형식은 연결부가 제공한다. 개인 대화·메모리를 자동 이관하지 않는다.

아래 경로 중 새 Codex 등록 파일의 정확한 형식은 설치 실험 결과로 정한다. 확정되지 않은 등록 형식을 현행 계약으로 배포하지 않는다.

## 승인 방식

Claude는 기존 훅 승인 창을 그대로 쓴다. Codex에서는 실행할 변경·명령·영향을 구체적으로 보여 주고 사용자의 명시적 답을 기다린다. 커밋·원격 명령은 공식 명령 승인 규칙의 `prompt`를 적용할 수 있는 범위를 실험한다. 플랫폼 권한 승인과 하네스 정책 승인은 별개다. 명령 규칙을 모든 파일 편집 승인으로 일반화하지 않는다.

명시적 확인은 행동 규칙이므로 Claude 승인 창과 같은 강제력을 보장하지 않는다. Codex 기본 승인이 자동 허용되는 환경에서도 이를 숨기지 않는다. 승인 필요 판정을 출력하고 호출이 계속되는 구현은 보호 성공으로 인정하지 않는다. 실제 차단을 보장할 수 없는 기능은 대체·미검증으로 보고한다.

2026-11-10 사용자의 “응 마지막으로 검수 후 바로 진행해줘”로 스펙과 Codex 승인 대체 방식을 승인받았다. `write-spec`의 “Approved 스펙이 없으면 코드를 쓰지 않는다” 조건을 충족했다. 이후 단계별 이동·삭제 목록과 훅·설정 diff 승인은 별도로 유지한다. 승인받은 범위를 반복해서 묻지 않는다.

## 차단 연결 계약

2026-11-10 사용자는 “Claude 기능은 유지하면서 Codex에도 위험 명령과 범위 밖 수정을 막는 안전장치를 추가”하는 다음 단계에 “응, 추가해줘”로 승인했다. [설치 실험 보고서의 등록 diff](../../reports/2026-11-10-dual-harness-phase1.md#승인받아-적용한-등록-diff)를 적용한다. 이동·삭제·Claude 설정 변경은 없다.

Codex 입력은 cwd(존재하는 작업 디렉터리), tool_name(Bash 또는 apply_patch), tool_input.command(비어 있지 않은 문자열)다. 실제 루트는 cwd의 git 최상위(없으면 cwd)다. 패치 전체를 먼저 해석하고 추가·수정·삭제·이동 양쪽 경로를 검사한다. 명령·경로의 기존 판정은 Claude 스크립트에 정규화한 JSON을 전달해 재사용한다. 허용 exit 0, 차단·판정 불가 exit 2이며 예상 밖 하위 판정 오류도 차단한다.

Codex 파일 패치는 저장소 밖 대상도 거절한다. Claude의 세션 파일 쓰기 예외는 바꾸지 않는다. HARNESS_SELF_EDIT=0이면 Codex의 config.toml·hooks.json·rules/·agents/도 자기 수정 보호 대상이다. 공통 설정의 변경 승인은 M5에서 다루며 이번 차단 연결이 임의로 승인됐다고 판단하지 않는다.

## 등록 검사 계약

설치 실험 결과에 따라 Codex는 `plugin/.codex-plugin/plugin.json`을 사용하고 skills는 `./skills/`, hooks는 `./hooks/codex.json`을 참조한다. 실제 훅 등록 적용 전에는 단계별 diff를 제시한다.

## 후속 연결 계약

2026-11-10 사용자의 “응 계속 쭉 진행해줘”에 따라 승인된 M5~M9 연결을 계속한다. 이동·삭제와 Claude 훅 등록 변경은 없다. Codex 등록에는 SessionStart·SubagentStart·UserPromptSubmit·PostToolUse·Stop용 연결을 추가한다. 프로젝트 실제 settings·전역 설정·훅 신뢰는 자동 변경하지 않는다.

승인 사전 검사는 `plugin/scripts/check-codex-approval.py`다. 표준 입력으로 공통 Bash·Write·Edit JSON을 받고, 작업 디렉터리의 공통 설정과 기존 ask-approval.sh 판정을 재사용한다. 출력 decision은 allow/confirm/deny이고 종료 코드는 각각 0/3/2다. confirm은 실제 실행 전에 사용자에게 구체적인 제안과 이유를 보이고 답을 기다리라는 뜻이다. 이 도구가 승인 필요 행동을 실행하지 않는다. 패치를 제안할 때는 변경 후 파일 내용으로 Write 검사를 하고, 추적 파일 삭제는 Bash git rm 검사로 확인한다. 런타임 훅 강제 승인을 대신하지 않는 행동 절차이며 Codex 명령 규칙은 지원하는 권한 경계에서만 보조한다.

Codex 세션 연결은 `plugin/hooks/codex-context.py`에서 이벤트별로 동작한다. 공통 규칙·설정과 Codex 승인 차이 안내를 세션에 넣고, 패치 경로의 조건부 규칙·포맷을 연결한다. 테스트 증거와 기록은 프로젝트 `.codex/` 아래 도구별 상태에 둔다. Stop은 last_assistant_message와 자체 PostToolUse 기록을 사용하며 transcript 형식에 의존하지 않는다. 실패하거나 해석할 수 없을 때 기록·알림은 경고 후 통과하고, Stop도 무한 반복을 막는다.

완료 증거는 프로젝트 루트에서 실행한 단독 TEST_CMD를 PreToolUse의 updatedInput으로 감싸 실제 종료 코드·물리 작업 폴더를 호출별 표식으로 확인한다. Bash의 문자열 출력에 있는 OK나 임의 Exit code 문구는 성공으로 보지 않는다. apply_patch만 실제 확인한 Exit code·Wall time·Output 응답 머리를 해석한다. 테스트 명령의 PreToolUse 시작 ID와 편집 세대를 기록하고, 같은 ID의 PostToolUse 최종 결과와 대조한다. 시작 뒤 새 편집이 있으면 결과가 늦게 성공해도 무효다. 성공 exit 0이라도 공통 실패 요약이 있으면 성공으로 세지 않는다. Bash 편집·완료 문구·실패 요약 판정도 completion-policy.py 한 원본을 양쪽이 사용한다.

초기화의 설치 설정 작성은 init-harness가 호출하는 `plugin/scripts/configure-harness.py`로 수행한다. 명령 계약은 `--project <경로> --target claude|codex|both`로 변경안을 JSON으로 출력하고, 승인 후 `--apply`를 붙여 제안된 파일만 반영한다. 다른 도구 선택의 기존 파일은 삭제하지 않는다. 공통 harness.conf·dev.conf는 이미 있으면 보존하고, 없을 때만 키 목록·견본으로 빈칸 골격을 만든다. 실제 값 채움은 기존 init-harness 실측·승인 절차다. 기존 사용자 설정을 덮어쓸 충돌이 있으면 제안만 출력하고 적용을 거절한다.

Claude는 기존 marketplace·enabledPlugins 설정, Codex는 프로젝트 marketplace·enabled 설정을 합친다. Codex 역할 3개는 공통 agents/*.md의 본문·description으로 `.codex/agents/*.toml`을 생성하며 모델은 상속한다. test-writer에는 features.shell_tool=false를 선언한다. 기존 다른 내용의 역할은 충돌로 처리한다. Codex 명령 규칙은 `.codex/rules/harness.rules`에 git commit·git push·gh pr create·gh pr merge의 prompt를 넣는다. 이 규칙은 샌드박스 밖 실행 승인에만 적용되며 일반 편집 승인·프로젝트 신뢰·훅 신뢰를 대신하지 않는다. 생성 파일은 재동기화 대상이며 정책 원본은 플러그인 한 곳이다.

회고 루프는 도구별 기록 수집과 분석기를 분리한다. 기존 분석기(Claude 실행기·MODEL·BUDGET=1)는 유지하고 Codex 기록도 전용 JSONL 형식에서 공통 근거로 바꿔 같은 분석기를 사용한다. Codex 실행기로 바꿔 비용 상한을 낮추지 않는다. Codex만 설치된 프로젝트는 분석용 Claude 실행기가 별도로 필요하며, 없으면 실패 원인을 알리고 분석 시각을 옮기지 않는다. 자동 기록·알림은 분석 실행기 없이도 동작한다. 최초 정기 분석은 기존처럼 사용자가 실행하고, 그 뒤 AUTO_ANALYZE·기존 7일 간격·잠금을 사용한다. 이 작업에서 실제 유료 분석을 실행하지 않는다.

도구 선택은 공통 스크립트 호출의 HARNESS_RUNTIME=claude|codex로 전달하며 기본값 claude는 보존한다. Codex는 현재 프로젝트의 UserPromptSubmit 메시지를 type=harness_user_message로, 사용자가 확인한 feedback 문서의 description·본문은 type=harness_feedback으로 자체 JSONL에 기록한다. 두 유형 모두 text·timestamp를 가지며 메시지의 정정 여부는 분석 단계에서 판단한다. 모든 해당 사용자 메시지의 원문 기록은 버전 관리에서 제외한 로컬 파일에 두며 수집 훅은 모델을 호출하지 않는다. 분석 실행 시에는 추출·길이 제한한 메시지를 기존 Claude 분석기로 전달한다. Claude 개인 메모리·transcript를 Codex 형식으로 재사용하지 않는다. Gemini도 같은 스크립트를 재사용하며 기준판 경로만 도구별로 바꾼다.
