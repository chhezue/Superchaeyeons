# 하네스 회고 루프

> 상태: Approved (2026-10-28 사용자 승인) · 구현됨 — 첫 실행(모델·비용 상한 결정) 대기
> MVP: In scope
> 관련 BR: N/A

이 스펙은 회고(`improve-harness`)를 "일하던 에이전트가 할지 말지 정하는 절차"에서 "기록 → 분석 → 효과 확인"이 저절로 도는 루프로 바꾼다. 읽고 나면 무엇이 자동으로 기록되는지, 분석을 누가 언제 얼마의 토큰으로 돌리는지, 효과 없는 규칙을 어떻게 지우는지 알 수 있다.

## 목표

사용자가 같은 지적을 되풀이하지 않아도 하네스의 결함이 기록되고, 따로 실행한 분석이 개선 후보를 근거와 함께 올리며, 반영한 조치의 효과를 재발 횟수로 확인해 효과 없는 규칙은 지운다.

## 이 스펙의 용어

같은 "기록"이 여러 뜻으로 읽히지 않도록 이 문서에서는 아래 이름만 쓴다.

| 이름 | 뜻 |
|---|---|
| 장부 | [`harness-retro.md`](../../audits/harness-retro.md) — 승인된 회고 후보와 그 효과를 적는 표 |
| 대화 기록 파일 | Claude Code가 세션마다 남기는 `.jsonl` 파일 |
| 요약 | 분석 때 대화 기록 파일에서 세션마다 뽑은 사용자 메시지와 신호 횟수 |
| 정정 기억 | 에이전트 기억 중 머리가 `type: feedback`인 것 — 사용자가 일하는 방식을 고친 기록 |
| 정정 대기열 | 정정 기억이 저장될 때 훅이 한 줄씩 쌓는 파일 |
| 후보 파일 | 분석이 낸, 사람이 아직 검토하지 않은 개선 후보 |
| 실행 기록 | 분석을 돌릴 때마다 비용과 결과를 한 줄씩 남기는 파일 |

## 배경

- **회고가 돌지 않았다.** [`harness-retro.md`](../../audits/harness-retro.md)의 2026-10-27 행들에 따르면, 같은 지적("다른 사례를 찾지 않고 아는 선택지만으로 묻는다")을 세 번 받는 동안 회고는 한 번도 저절로 돌지 않았다. 세 번째에 사용자가 "왜 자동으로 안 하냐"고 물은 뒤에야 돌았다
- **원인은 조건이 아니라 구조다.** 지금 회고는 일하던 에이전트가 "L 규모인가 · 같은 지적을 두 번 받았나"를 스스로 판단해야 시작된다. 일하는 도중에는 그 판단을 잊는다. 조건을 넓혀도(장부의 2026-10-27 "회고가 묶여 돌지 않는다" 행 수정안) 판단하는 주체가 같아서 같은 방식으로 빠진다
- **장부가 둘로 갈렸다.** 하네스에 대한 지적이 에이전트 기억 파일에만 남아 장부의 횟수가 쌓이지 않았다(장부의 2026-10-27 "기억 파일에만 남는다" 행)
- **규칙은 더하기만 하면 손해일 수 있다.** 항상 실리는 규칙이 이미 예산 25,000B 중 24,727B다. 2026년 AGENTS.md 효과 평가 논문은 맥락 파일이 성공률을 대체로 올리지 않고 비용만 20% 넘게 늘렸다고 보고했다. 지우는 길이 있어야 루프가 닫힌다

### 조사로 확인한 것 (2026-10-27~28)

공식 문서·논문·다른 제품에서 확인한 사실과 그것이 설계에 주는 영향이다.

| 사실 | 이 스펙에 주는 영향 | 근거 |
|---|---|---|
| 조사한 논문 넷(ACE(Agentic Context Engineering) — 장부를 조금씩 고쳐 쌓는 방식 · Reflexion — 실패 뒤 반성문을 다음 시도에 넣는 방식 · ExpeL — 경험에서 뽑은 규칙에 찬반 표를 세는 방식 · Dynamic Cheatsheet — 풀이 중 쓸모 있던 요령을 메모장에 모으는 방식)과 제품은 모두 회고를 기록 · 분석 · 효과 확인으로 나누고, 기록은 실행 결과에서 기계적으로 모은다 | 사용자가 쓰는 표현이나 일하던 에이전트의 판단에 기대지 않는다 | 2026-10-27 `researcher` 조사 |
| ACE는 분석 모델이 장부를 통째로 다시 쓰면 내용이 줄어드는 현상(collapse)을 보고했다. ExpeL은 항목마다 찬반 표를 세서 0이 되면 지운다 | 장부는 행을 더하거나 고치기만 하고 통째로 다시 쓰지 않는다. 행마다 재발 횟수를 센다 | 같은 조사 |
| 세션 대화 기록은 `~/.claude/projects/<프로젝트>/<세션 ID>.jsonl`에 남는다. 경로는 공식 문서에 있지만 줄 형식은 버전마다 바뀔 수 있다 | 추출기를 쓸 수 있다. 형식이 바뀌면 조용히 빈 결과를 내지 않고 "추출 실패"를 남겨야 한다. `improve-harness` 스킬의 "경로가 공식이 아니다"는 틀린 말이 됐다 | 2026-10-27 `researcher` 조사(공식 문서) |
| 클라우드 예약 실행은 이 컴퓨터의 대화 기록을 읽지 못한다. 데스크톱 예약 작업은 읽는다 | 분석은 직접 실행하거나 데스크톱 예약 작업으로 돌린다 | 같은 조사 |
| `claude plugin eval`은 플러그인 안의 스킬·훅·에이전트만 평가한다. `.claude/rules/`는 평가하지 못한다 | 규칙의 효과는 재발 횟수로만 본다. 스킬 평가는 [플러그인 배달](harness-plugin-delivery.md) 뒤에 쓸 수 있다 | [Plugin evals](https://code.claude.com/docs/en/plugin-evals) |
| `--bare`는 훅을 건너뛰지만 인증을 `ANTHROPIC_API_KEY`로만 받는다. 로그인(OAuth)은 읽지 않는다 | 분석 실행에 `--bare`를 쓰지 못한다 | Claude Code 2.1.304 `claude --help` |

### 실험으로 확인한 것 (2026-10-28)

임시 폴더에 세션 시작·종료 훅을 단 프로젝트를 만들고 Claude Code 2.1.304로 확인했다.

| 확인한 것 | 결과 | 이 스펙에 주는 영향 |
|---|---|---|
| 대화 기록 추출 시간 | 13.6MB 기록에서 0.05초 · 10.8MB에서 0.04초 | 시간 제한은 문제가 아니다 |
| 사용자 메시지 요약 크기(메시지마다 500B 상한, 메타 줄·요약 글·시스템 알림 제외) | 세션 하나에 0.4~5.1KB | 세션 10개를 넣어도 약 30KB다 |
| 상한 없이 사용자 메시지만 모은 크기 | 최근 10세션 합 약 166KB. 가장 큰 94KB는 긴 대화의 앞부분 요약 글이 사용자 메시지로 들어간 것이다 | 요약 글(`isCompactSummary`)을 빼고 메시지마다 상한을 둬야 한다 |
| `claude -p`로 분석을 돌리면 프로젝트 훅이 도는가 | 세션 시작·종료 훅이 모두 돈다. 분석 세션 자기 자신이 기록되고 알림이 실린다 | 그대로 두면 분석이 자기 기록을 다시 분석한다 |
| `--setting-sources user --no-session-persistence`를 붙이면 | 프로젝트 훅이 하나도 돌지 않고 대화 기록도 남지 않는다 | 환경 변수 같은 우회 통로 없이 반복을 막는다 |
| `--max-budget-usd`가 로그인 사용자에게도 걸리는가 | 걸린다. 상한을 넘으면 `error_max_budget_usd`로 멈추고 `total_cost_usd`를 돌려준다. 다만 한 차례 응답이 끝난 뒤에 확인해서 상한을 조금 넘을 수 있다(상한 0.0001달러에 0.0019달러) | 비용 상한과 실제 비용 기록을 쓸 수 있다. 상한은 "대략"으로 본다 |
| 세션 종료 훅이 대화형 세션을 Ctrl+C·창 닫기로 끝낼 때도 도는가 | 확인하지 못했다(대화형 조작 실험이 막힘) | 세션 종료 훅에 기대지 않는다 — 아래 "설계 선택" |

### 설계 선택 — 세션 종료 훅을 쓰지 않는다

처음 안은 세션이 끝날 때 요약을 만드는 것이었다. 실험에서 추출이 0.05초로 충분히 빨랐고, 비정상 종료 때 도는지는 확인하지 못했다. 그래서 요약은 **분석을 돌릴 때 한꺼번에** 만든다. 대화 기록 파일은 세션이 어떻게 끝나든 남으니, 마지막 분석 이후에 바뀐 기록을 모두 읽으면 빠지는 세션이 없다.

## 요구사항

### Must Have

**기록 — 모델 비용 0**

- [x] `PostToolUse` 훅 `auto-correction-queue.sh`(`Write`·`Edit`·`MultiEdit`)가 에이전트 기억 폴더(`~/.claude/projects/<프로젝트>/memory/`)에 머리의 `type: feedback`인 파일이 쓰이면 정정 대기열에 한 줄을 더한다 — 날짜 · 세션 ID · 기억 파일 이름 · 그 파일의 `description`. 같은 파일이 다시 쓰이면 새 줄을 더하지 않고 횟수를 올린다
- [x] 정정 대기열 · 요약 · 후보 파일 · 실행 기록 · 분석 상태는 저장소 안 `.claude/corrections/`에 두고 `.gitignore`에 넣는다(2026-10-28 사용자 결정). 대화 원문 일부가 들어가므로 커밋하지 않는다. 사람이 읽는 문서가 아니라 스크립트가 만드는 데이터라서 산출물 등록부(`docs/templates/README.md`)에 넣지 않는다
- [x] `SessionStart` 훅 `auto-correction-notice.sh`가 "마지막 회고 분석(날짜) 뒤 세션 N개 · 정정 기억 M건 · 검토할 후보 K건"을 한 줄로 `systemMessage`(사용자 화면)와 `additionalContext`(Claude)에 함께 낸다. 세 값이 모두 0이면 아무것도 내지 않는다. 대화 기록 파일의 수정 시각과 상태 파일만 보고, 기록 내용은 읽지 않는다
- [x] 두 훅은 [플러그인 배달 스펙](harness-plugin-delivery.md)의 주입 훅과 같이 bash 3.2 내장 기능과 macOS 기본 명령만 쓴다. 수정 시각 비교는 `find -newer`로 한다
- [x] 두 훅은 실패해도 작업을 막지 않는다(종료 코드 0). 대신 정정 대기열에 쓰지 못하면 `systemMessage`로 "정정 대기열에 쓰지 못했다"를 알린다

**분석 — 따로 실행, 사람이 승인**

- [x] `scripts/analyze-corrections.sh`가 아래 순서로 돈다
  1. 마지막 분석 뒤에 바뀐 이 프로젝트의 대화 기록을 찾아 세션마다 요약을 만든다. 요약에는 사용자 메시지(메시지마다 500B 상한), 승인 거절 · 훅 차단 · Stop 훅 되돌림 · 작업 중단 횟수, 해석하지 못한 줄 수가 들어간다. 메타 줄(`isMeta`) · 요약 글(`isCompactSummary`) · 시스템 알림은 뺀다
  2. 줄이 있는데 사용자 메시지를 하나도 뽑지 못한 기록은 "추출 실패"로 실행 기록에 남기고 사용자에게 보여 준다. 조용히 빈 요약으로 넘어가지 않는다
  3. 요약 · 정정 대기열 · 장부를 하나의 입력으로 묶어 `claude -p`로 분석한다. 붙이는 옵션은 아래와 같다. 분석 세션에는 읽기 도구만 허용하고, 파일 쓰기는 스크립트가 결과를 받아서 한다
     - `--setting-sources user --no-session-persistence` — 프로젝트 훅을 돌리지 않고 분석 세션의 대화 기록 파일을 남기지 않는다
     - `--output-format json` — 토큰과 `total_cost_usd`를 받는다
     - `--max-budget-usd <상한>` · `--model <모델>`
  4. 결과를 후보 파일에 쓰고, 실행 기록에 날짜 · 세션 수 · 입력 크기 · 입력·출력 토큰 · `total_cost_usd` · 결과 종류를 한 줄로 남긴다
  5. 분석이 성공했을 때만 "마지막 분석" 시각을 옮긴다. 실패하거나 비용 상한에 걸리면 옮기지 않아, 다음 실행이 같은 세션을 다시 본다
- [x] 분석 지시문은 `improve-harness` 스킬 아래 참조 파일(`references/analyze.md`)에 둔다. 후보마다 아래를 요구하고, 근거가 없는 후보는 스크립트가 버린다
  - 증상 — 다른 작업에서도 알아볼 수 있는 상황으로
  - 근거 — 세션 ID와 사용자 메시지 번호 2건 이상(같은 증상 2회). 기존 장부 행과 같은 증상이면 그 행 ID
  - 고칠 층 — 규칙 · 스킬·에이전트 · 훅 · 문서
  - 토큰 비용 — 항상 실리는 글 · 호출될 때 실리는 본문 · 실행 비용 중 무엇이 얼마나 늘거나 주는지
- [ ] 분석 모델은 첫 실행에서 정한다(2026-10-28 사용자 결정). 기준 사례(2026-10-27 세션)를 넣고 Sonnet과 Opus로 한 번씩 돌린다. 둘 다 그 증상을 후보로 내면 Sonnet, Sonnet만 놓치면 Opus로 정하고 `analyze-corrections.sh`의 기본값으로 적는다
- [ ] 비용 상한(`--max-budget-usd`)은 첫 실행 2달러, 그 뒤로는 실행 기록에 남은 실제 비용의 2배로 낮춰 `analyze-corrections.sh`의 기본값으로 적는다(2026-10-28 사용자 결정). 상한은 응답 하나가 끝난 뒤 확인해 조금 넘을 수 있다
- [ ] 첫 실행은 사용자가 직접 한다. 그 뒤로는 이 컴퓨터의 예약 실행(데스크톱 예약 작업 등)으로 주 1회 돌린다(2026-10-28 사용자 결정). 마지막 분석 뒤 새 세션이 없으면 스크립트는 모델을 부르지 않고 끝난다

**검토 — 세션 안에서, 사람이 승인**

- [x] `improve-harness` 스킬의 일은 "후보를 찾는 것"에서 "검토할 후보를 사용자와 하나씩 확인하는 것"으로 바뀐다. 승인된 후보만 `harness-retro.md`에 쓰고, 규칙·스킬을 실제로 고치는 것은 지금처럼 다시 승인받는다
- [x] `improve-harness` "When to Use"는 "세션 시작 알림에 검토할 후보가 있을 때 · 사용자가 회고를 요청할 때"로 바꾼다. L 규모 · 같은 지적 2회를 스스로 알아챔 조건은 지운다
- [x] `verify-work` 마무리 2번 "회고"는 "세션 시작 알림에 검토할 후보가 있으면 `improve-harness`를 제안한다"로 바꾼다
- [x] `improve-harness`의 "서브에이전트로 돌리지 않는다" 절과 "트랜스크립트 경로는 공식이 아니다" 문장을 지운다 — 분석은 이제 일부러 별도 실행에서 한다
