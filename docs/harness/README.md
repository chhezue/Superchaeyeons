# 하네스 레이어 설명 (`docs/harness/`)

하네스를 **강제력** 기준 4개 레이어로 나누고, 각 레이어가 언제 발동해서 무엇을 막는지 설명한다. 이 파일은 이 저장소의 `{{현재동작 요약}}`과 `{{아키텍처 개요}}`다 — 훅·규칙의 동작이 바뀌면 같은 턴에 아래 "지금의 실제 동작" 절을 쉬운 말로 고친다. 구성 요소 목록은 [`.claude/rules/README.md`](../../.claude/rules/README.md)가 SSOT이고, 이 폴더는 이 저장소의 기록이라 새 프로젝트에 배달하지 않는다.

## 4개 레이어

레이어는 "무엇으로 강제하는가"로 갈린다. 아래로 갈수록 에이전트의 판단과 무관해진다.

| 레이어 | 무엇으로 강제하나 | 파일 | 언제 |
|---|---|---|---|
| **L1 규칙** | 프롬프트 — 에이전트가 읽고 따른다 | `plugin/rules/`(주입 훅이 넣음) · `.claude/rules/`(map) | 세션 시작·`/clear`·요약 뒤·서브에이전트 시작 · 해당 종류 파일을 다룰 때 |
| **L2 스킬·서브에이전트** | 절차와 사람 승인 단계 · 별도 컨텍스트 | `plugin/skills/` · `plugin/agents/` | 에이전트나 사용자가 부를 때 |
| **L3 훅** | exit code — 도구 호출 직전·턴 종료 | `plugin/hooks/` · `plugin/hooks/hooks.json` | Bash·파일 쓰기 직전, 턴 종료 |
| **L4 기계 검증** | 검사기 exit code — 완료 선언 전·커밋 직전 | `plugin/scripts/` · `scripts/` | `dev.sh test` 실행 · `git commit` |

판단이 필요한 것은 L1·L2에 두고, 되돌리기 비싸면서 exit code로 판정할 수 있는 것만 L3·L4로 내렸다. 모든 것을 훅으로 막으면 오탐이 쌓이고, 오탐이 잦은 장치는 우회된다. L3과 L4의 차이는 대상이다 — 훅은 에이전트의 동작 하나를 막고, 검사기는 저장소 상태를 판정한다.

## 레이어와 사이클의 관계

실제 작업은 `core-workflow.md`의 트랙 × 규모 × 게이트를 따라 흐른다. 같은 게이트라도 강제하는 레이어가 다르다.

| 사이클 단계 | 담당 | 강제 레이어 |
|---|---|---|
| 진입 — 트랙(A 기능·B 감사·C 버그·D 이식)·규모(S·M·L) 판정 | `write-spec` · `refactor-safely` · `fix-bug` · `init-harness` | L1 |
| **G1 리서치** | `researcher` | L1·L2 — 강제 수단 없음 |
| **G2 승인** | 사람 (`ask-decisions` 인터뷰 → 트랙별 승인 산출물) | L1 `core-gates.md` · L2 스킬 승인 단계 |
| 구현 | 에이전트 · `test-first` · `test-writer` | **L3** `deny-dangerous-bash.sh` · `deny-out-of-scope-write.sh` |
| **G3 검증** | `verify-work` · `doc-reviewer` · L 규모는 `code-review`/`simplify` | **L3** Stop 훅 + **L4** `plugin/scripts/dev.sh test` |
| **G4 회고·커밋** | `verify-work` 마무리 절 · 회고 루프(기록 훅 → `plugin/scripts/analyze-corrections.sh` → `improve-harness` 검토) · `report.md` · 커밋 분할안 | **L3** `auto-correction-queue.sh`·`auto-correction-notice.sh`(기록·알림만, 막지 않음) · 커밋·push·PR은 **L3** 승인 창 훅 `ask-approval.sh`(메시지 형식·문서 스타일·`COMMIT_CHECK` 검사 뒤 창) |

강제력이 가장 약한 곳은 G1이다. 조사를 했는지는 exit code로 판정할 수 없어 규칙과 절차에만 기댄다. G4 회고도 같은 처지였지만, 이제 기록과 알림은 훅이 맡아 일하던 에이전트의 판단에 기대지 않는다. 무엇을 고칠지는 여전히 사람이 검토해 정한다.

## 지금의 실제 동작

아래는 Claude Code 연결 기준의 현재 동작이다. Codex의 호출·승인·기록 차이는 뒤의 Codex 연결 절에서 설명한다. 정확한 조건은 각 훅·스크립트 머리 주석이 SSOT다.

- **세션을 열면 하네스 플러그인의 훅이 core 규칙 4개를 넣는다.** 플러그인은 규칙 파일을 배달할 수 없어서, 세션 시작·`/clear`·대화 요약 뒤에 훅이 플러그인 `rules/`의 원문을 그대로 대화에 넣는다. 맨 앞 한 줄은 플러그인 폴더의 실제 경로다 — 규칙과 스킬이 말하는 `scripts/dev.sh` 같은 도구를 그 경로로 부른다. 서브에이전트가 시작될 때도 같은 글을 넣는데, 규칙 없이 시작하도록 만든 하네스 에이전트 셋(`doc-reviewer`·`researcher`·`test-writer`)은 뺀다. `CLAUDE.md`·`AGENTS.md`는 Claude Code가 직접 싣고, `.claude/harness.conf`는 설정 주입 훅이 읽어 넣는다. 테스트·소스·마크다운 규칙은 그 종류의 파일을 읽거나 고칠 때 훅이 넣고, 규칙마다 세션에 한 번만 넣는다(요약 뒤에는 다시 넣는다). 어느 파일이 어느 규칙에 맞는지는 각 규칙 머리의 `paths:`가 정한다.
- **규칙을 싣지 못하면 사용자 화면에 경고가 뜬다.** 규칙 파일이 없거나 일부만 읽혔거나 훅 입력을 해석하지 못하면, 반쪽 규칙을 넣지 않고 "하네스 규칙을 싣지 못했다 — 이 세션은 가드레일 없이 진행된다"를 사용자 화면과 Claude 양쪽에 띄운다. 훅이 실패해도 세션은 그대로 진행되므로, 이 경고가 없으면 규칙이 조용히 빠진다. bash가 아예 없거나 훅이 시간 초과되면 이 경고도 뜨지 않는다(스펙 리스크 6). 경로 규칙을 싣지 못해도 경고만 띄우고 작업은 막지 않는다.
- **프로젝트마다 다른 값은 `.claude/harness.conf` 한 파일에 있다.** 문서 경로·테스트 명령 같은 슬롯, 플래그, 훅이 막을지 정하는 값(쓰기 범위·자기 수정 허용·위험 명령 묶음)을 `키=값`으로 적고, 훅은 값을 본문이 아니라 이 파일에서 읽는다. 세션을 열면 슬롯·플래그 값이 표로 대화에 들어온다. 파일이 없거나 값이 빈칸(`{…}`)이면 표 대신 "하네스 설정이 비어 있다"는 알림이 화면에 뜨고, 에이전트가 `init-harness`를 먼저 제안한다. 파일이 없을 때 막는 훅들은 가장 엄격한 값으로 판단한다 — 자기 수정은 막고 위험 명령 묶음은 모두 막는다. 다만 `init-harness`가 설정을 만들 수 있게 `.claude/harness.conf`·`.claude/settings.json` 쓰기만은 막지 않는다. 파일이 깨졌으면(키=값이 아닌 줄, 0/1 자리에 다른 값) 판단할 수 없으니 막는다.
- **작업 크기를 먼저 정한다.** 오타·한 줄 수정 같은 작은 작업은 바로 고치고 검증 명령만 돌린다. 3개 이상 파일이나 API·DB를 건드리는 큰 작업은 별도 리뷰와 작업 보고서까지 남긴다.
- **"알아서", "최적화해줘"처럼 결정이 비어 있는 요청이면** 에이전트가 규칙에 따라 먼저 질문으로 범위를 좁힌다.
- **되돌리기 어려운 명령은 실행 전에 막힌다.** 위험 명령은 6묶음이고, 묶음마다 훅이 막을지 Claude Code 기본 권한 체계에 맡길지를 훅 맨 위 상수(`BLOCK_*`)로 정한다. 이 저장소의 값은 다음과 같다.
  - 막는다: 강제 푸시 · 커밋 기록과 작업 중인 파일 버리기(`git reset --hard`·`git clean -f`·브랜치 강제 삭제 등) · 커밋 전 검사 건너뛰기와 비밀값 파일(`.env`) 커밋 · DB 테이블·컨테이너 볼륨 삭제 · 시스템 위험(원격 스크립트 바로 실행·권한 전체 개방·디스크 직접 쓰기)
  - 맡긴다: 폴더 통째 삭제(`rm -rf`·`find -delete`). 막힌 일의 대부분이 임시 폴더 정리였고, 그만큼 작업이 늦어졌기 때문이다. 맡겨도 루트·홈·현재 폴더·`.git`을 통째로 지우는 명령은 막는다. 하네스를 새 프로젝트에 붙일 때는 설치 절차(`init-harness`)가 이 묶음을 막을지 한 번 묻는다
- **명령 중 실제로 실행되는 부분만 본다.** 따옴표 안 글자(`grep "git reset --hard"`·`echo`), 주석, 파일 내용을 명령 안에 바로 적어 넘기는 부분(heredoc — 커밋 메시지·문서)은 검사하지 않는다. 대신 그 글자가 실행되는 자리는 다시 검사한다. 예를 들면 `bash -c '…'`·`eval` 안, `ssh`로 서버에 보내는 명령, 셸로 넘기는 파이프다. 전체 목록은 훅 머리 주석에 있다. 명령을 해석하지 못하면(닫히지 않은 따옴표 등) 예전처럼 문장 전체를 검사하고, 훅이 고장 나거나 시간을 넘기면 명령을 막는다. 변수에 담은 명령이나 별도 스크립트 파일 안의 명령은 보지 못해 규칙으로만 금지한다.
- **작업 범위 밖 파일은 못 쓴다.** 이 저장소는 범위가 저장소 전체라 이 검사는 사실상 꺼져 있다. 파일 쓰기 도구 네 개(Write·Edit·MultiEdit·NotebookEdit) 모두에 걸린다.
- **에이전트가 하네스 자신(훅 스크립트·`settings.json`)을 고칠 수 있다.** 이 저장소는 하네스를 고치는 곳이라 허용했다. 새 프로젝트에 붙이면 기본으로 막힌다. 막는 곳은 플러그인 폴더(훅·검사 스크립트가 실제로 있는 곳 — 저장소 밖 플러그인 캐시도 포함)와 프로젝트의 `.claude/hooks/`·`.claude/settings.json`이다. 저장소 밖이라고 통과시키면 에이전트가 플러그인 캐시의 훅을 고쳐 잠금을 풀 수 있어서다. 훅이 막는 것은 파일 쓰기 도구뿐이고 Bash로 고치는 것은 규칙으로만 막는다.
- **테스트를 먼저 쓰는 곳은 사람이 정한다.** 스펙을 쓸 때 에이전트가 "이 항목은 테스트 먼저"를 제안하고 사람이 고친다. 그 항목과 버그 수정은 실패하는 테스트를 먼저 보고 구현하며, 완료 보고에 "어느 테스트가 왜 실패했다가 통과했는지" 표를 붙인다. 인증·결제처럼 중요한 곳은 구현 계획을 모르는 별도 에이전트가 테스트를 쓴다. 이 순서를 지켰는지 기계로 막지는 않는다 — 검증 단계에서 표를 대조할 뿐이다.
- **파일을 고친 뒤 검증(`plugin/scripts/dev.sh test`)을 돌리지 않고 "완료"라고 하면** 대화가 끝나지 않고 되돌아온다. 돌렸는데 실패했어도 같다. 한 번만 되돌리므로 무한 반복은 없다. 명령이 글자 그대로 일치해야 검증으로 친다(앞에 붙은 폴더 경로는 상관없다) — `dev.sh build`나 테스트 일부만 돌린 `dev.sh test --tests X`는 검증이 아니다. 되돌릴 때 알려 주는 명령에는 플러그인의 실제 경로가 붙는다. 커밋 메시지처럼 `<<EOF`로 넘긴 글이나 따옴표로 감싼 글(`-m "…"`) 안의 `>` 기호는 파일 쓰기로 보지 않는다. 단 `bash -c "…"`처럼 셸에 넘겨 실행하는 글 안의 `>`는 파일 쓰기다. `sed -i`는 바꿀 내용을 적은 식이 아니라 고치는 파일만 보고, 저장소 밖(스크래치 폴더·`/tmp`·홈 아래 메모리 폴더)에 쓴 파일은 고친 것으로 치지 않는다. 같은 명령에서 `S=/tmp/…`처럼 변수에 넣은 경로는 따라가 보고, 값을 알 수 없는 변수(`for f in …`의 `$f` 등)로 쓴 파일은 고친 것으로 본다. 한 명령 안에서 파일을 고치고 이어서 검증을 돌렸으면 검증한 것으로 치고, 검증 뒤에 고쳤으면 검증하지 않은 것으로 친다.
- **빌드·테스트·실행은 플러그인의 `scripts/dev.sh` 하나로 한다.** 이 스크립트는 모든 프로젝트에서 같고, 프로젝트마다 다른 명령·서비스·확인 주소는 `scripts/dev.conf`에 적힌다. 출력은 성공이면 한 줄, 실패면 원인 몇 줄로 줄이고 전체는 로그 파일에 남긴다. `dev.conf`에 적힌 명령도 실행 전에 위험한 명령 차단 검사를 받는다. `dev.sh`는 현재 폴더의 git 최상위를 프로젝트로 보고 그 프로젝트의 설정을 읽는다. 붙인 프로젝트는 `init-harness`가 골격을 복사해 `scripts/dev.conf`를 채우고, 이 저장소는 루트 `dev.conf`에 값을 둔다. 그래서 이 저장소에서는 `plugin/scripts/dev.sh test`가 `scripts/verify.sh`를 부르고, 검증이 통과하면 단계마다 한 줄만 출력한다.
- **되돌리기 어려운 일은 사용자 승인 창을 거친다.** Claude가 커밋·push·PR 생성·머지를 하려 하거나, git이 추적하는 파일을 지우거나(덮어쓰는 `mv` 포함), 의존성 선언 파일을 고치거나 설치 명령을 돌리거나, 설정에 적은 민감한 경로에 쓰거나, 스펙을 `Approved`로 바꾸거나 `[미정]`을 지우거나, 채워진 `.claude/harness.conf`를 고치려 하면 훅이 화면에 승인 창을 띄운다. 창에는 무엇을 승인하는지 한 줄로 적힌다(예: "커밋 — 파일 3개 · `Fix: …`"). 창이 승인이라 같은 일을 채팅에서 따로 묻지 않는다. 자동 모드에서도 창이 뜨고, 비대화형 실행(`-p`)에서는 창을 띄울 수 없어 거절된다. 읽기·스테이징(`git status`·`git add`)이나 추적하지 않는 임시 파일 삭제에는 창을 띄우지 않는다. 범주마다 설정의 `ASK_*` 값으로 끌 수 있다.
- **커밋하기 전에 먼저 검사한다.** 승인 창을 띄우기 전에 커밋 메시지 첫 줄이 설정 `COMMIT_RE` 형식에 맞는지, 바뀐 마크다운에 문서 스타일 오류가 없는지, 설정 `COMMIT_CHECK` 명령(이 저장소는 `scripts/verify.sh`)이 통과하는지 본다. 하나라도 실패하면 창 없이 이유와 함께 막는다. 사람이 터미널에서 직접 하는 커밋은 검사하지 않는다 — git 훅은 버전마다 바뀌는 플러그인 경로를 따라갈 수 없어 없앴다. 같은 명령 안의 `git add`는 아직 반영되기 전이라 창에 적히는 파일 수는 그 시점 기준이다.
- **사용자가 에이전트의 일하는 방식을 고치면 그 사실이 자동으로 기록된다.** 에이전트가 그 지적을 정정 기억(종류가 "정정"인 기억 파일)으로 저장하는 순간, 훅이 저장소 안 `.claude/corrections/queue.tsv`에 날짜·세션·기억 이름 한 줄을 남긴다. 같은 기억이 다시 저장되면 줄을 늘리지 않고 횟수만 올린다. 이 폴더는 대화 원문 일부가 들어가 git이 무시하게 해 두었고, 빠지면 검증이 실패한다. 이 기록은 모델을 부르지 않아 비용이 없다.
- **세션을 열면 회고할 거리가 쌓였는지 한 줄로 알려 준다.** "마지막 회고 분석 뒤 세션 몇 개 · 정정 기억 몇 건 · 검토할 후보 몇 건"이다. 셋 다 0이면 아무것도 띄우지 않는다. 대화 기록 파일은 수정 시각만 보고 내용은 읽지 않는다.
- **회고 분석은 일주일에 한 번 저절로 돈다.** 첫 분석은 사람이 직접 돌린다. 그 뒤로는 세션을 열 때 알림 훅이 마지막 분석에서 7일이 지났고 새 세션이 있는지 보고, 그러면 분석을 세션과 끊긴 별도 프로세스로 띄운다. 훅은 분석을 기다리지 않아 세션 시작이 느려지지 않고, 진행 내용은 `.claude/corrections/auto.log`에 남는다. 세션 두 개를 함께 열어도 한 번만 띄운다. 분석은 세션마다 사용자 메시지를 모으는데, 에이전트가 일하는 도중에 보낸 메시지도 넣는다. 이런 메시지에 일하는 방식을 고치라는 지적이 몰리는 일이 많아서다. 다른 Claude 세션이 보낸 메시지와 배경 작업 알림은 넣지 않는다. 운영체제의 예약 기능을 쓰지 않아 하네스를 복사한 어느 환경에서나 같게 돈다. 분석을 한 번도 돌리지 않은 프로젝트는 저절로 돌지 않으니, 하네스를 붙인 프로젝트가 모르는 사이 돈을 쓰지 않는다. 끄려면 훅 상수 `AUTO_ANALYZE`를 `0`으로 바꾼다.
- **분석 내용:** `plugin/scripts/analyze-corrections.sh`가 마지막 분석 뒤의 대화 기록에서 사용자 메시지만 짧게(메시지마다 500바이트) 뽑아, 정정 대기열·장부와 함께 별도 Claude 실행에 넘긴다. 이 실행은 파일을 읽기만 하고, 프로젝트 훅을 돌리지 않으며, 자기 대화 기록도 남기지 않는다.
- **분석이 실패하면 아무것도 넘어가지 않는다.** 비용 상한을 넘거나 실패하면 후보를 쓰지 않고 "마지막 분석" 시각도 옮기지 않아 다음 실행이 같은 세션을 다시 본다. 대화 기록 형식이 바뀌어 사용자 메시지를 하나도 못 뽑으면 "추출 실패"를 띄우고 모델을 부르지 않는다. 근거(세션과 메시지 번호 2건)가 없는 후보는 버린다. 복제된 세션에 든 같은 메시지는 한 건으로 세고, 이미 반영한 조치의 재발은 반영한 날 뒤의 메시지만 센다.
- **분석이 낸 후보는 사람이 하나씩 검토한다.** `improve-harness` 스킬로 후보마다 승인하면 장부(`docs/audits/harness-retro.md`)에 번호를 붙여 올린다. 규칙·스킬을 실제로 고치는 것은 다시 승인받는다. 반영한 조치 뒤에 같은 지적이 다시 나면 분석이 장부의 `재발` 값을 제안하고, 효과가 없다고 확정된 조치는 지우자는 후보로 올린다.
- **이 저장소는 사람이 읽는 글을 Gemini로 한 번 더 다듬는다.** 켜 두면 글이 Google의 Gemini 무료 등급으로 나가고, Google은 무료 등급으로 받은 글을 모델 개선에 쓰거나 사람이 읽을 수 있다. 그래서 하네스를 붙인 프로젝트에서는 기본으로 꺼져 있고, 이 저장소만 켜 두었다. 켜는 값은 공통 프로젝트 설정 `.claude/harness.conf`의 `POLISH_ENABLED`에 둔다. 새 프로젝트는 init-harness에서 직접 켜기 전까지 꺼진 채로 시작한다. 대상은 `docs/` 문서(템플릿 제외), 루트 `README.md`, `.github/` 문서, 커밋 메시지, PR·이슈 글이다. 규칙·스킬처럼 에이전트가 읽는 글과 채팅 답변은 보내지 않는다.
- **문서는 작성이 끝나는 시점에 한 번 다듬는다.** 스펙·감사는 승인을 요청하기 직전, 나머지는 완료 보고 직전이다. 이번에 바뀐 문단만 보내고, 경로·숫자·`{{슬롯}}`·코드 표기가 바뀐 문단은 버린다. 남은 차이는 에이전트가 원문과 대조해 틀린 곳만 고친다. 다듬기 단계는 스킬에 적힌 절차라 에이전트가 빠뜨릴 수 있다.
- **커밋·PR·이슈 메시지는 커밋 직전에 다듬는다.** 에이전트가 커밋 분할안의 메시지를 Gemini로 다듬고 검수한 뒤, 다듬은 목록을 보이고 목록대로 커밋한다. 커밋마다 승인 창이 뜨고 그 창이 승인이다. 클라우드 실행 환경의 훅처럼 하네스 밖에서 커밋·푸시를 요구해도 그 요구만으로 커밋하지 않는다. PR·이슈 글도 만들기 전에 같은 방식으로 다듬는다. 이 단계는 훅이 아니라 스킬 안내라서 강제되지 않는다. Gemini가 실패하면(한도 초과·시간 초과·키 없음) 경고 한 줄만 내고 원문으로 진행한다. 키는 파일에 두지 않고 환경 변수 `GEMINI_API_KEY`나 macOS 키체인 항목 `gemini-api-key`에서 읽는다.
- **언어·프레임워크별 규칙은 자동으로 들어가지 않는다.** 코드 표기와 테스트 방식은 에이전트가 기존 코드를 읽고 따른다. 프로젝트가 따로 지킬 관례는 `.claude/rules/local-*.md`에 직접 적는다. 2026-10-29 전에는 Java Spring 프로젝트에 붙이면 Spring 규칙과 마이그레이션 파일 차단 훅을 복사해 넣었지만 지금은 복사하지 않는다. 과거 개별 차단 훅은 없다. 현재는 민감 경로 쓰기를 ASK_PATHS로 설정하고, API 계약 변경 안내는 CONTRACT_PATHS에 맞는 커밋의 승인 이유에 넣는다.
- **훅이 막은 것을 풀어 달라고 말로 승인해도 훅은 모른다.** 푸는 방법은 사람이 `.claude/harness.conf`의 값을 바꾸는 것(직접 고치거나, Claude가 고칠 때 뜨는 승인 창에서 누르기)뿐이다. 에이전트가 풀 수 있는 통로를 만들면 에이전트도 그 통로를 연다. 이 안내는 규칙 글이 아니라 막힐 때 훅이 내는 차단 메시지에 들어 있다 — 매번 읽히는 규칙을 줄이려고 2026-10-28에 옮겼다.

## Codex 차단 연결

공동 지원 작업 중이다. Claude 기능과 설정은 유지하고, Codex는 별도 매니페스트와 훅 등록으로 같은 위험 명령·쓰기 범위 판정을 호출한다. Codex 파일 패치는 추가·수정·삭제·이동 경로를 모두 검사하며 저장소 밖을 거절한다. 자기 수정이 꺼져 있으면 Codex 설정·명령 규칙·역할도 보호한다.

Codex의 설치·활성화만으로 훅이 실행되는 것은 아니다. 신뢰되지 않은 훅은 실행되지 않으므로, 훅 신뢰와 실제 차단 검증을 별도로 해야 한다. 현재 단계에서는 Claude 승인 창과 같은 Codex 승인 강제력을 제공하지 않는다. 규칙 주입·역할 생성·후처리·init-harness 도구 선택도 연결하며, [공동 지원 스펙](../specs/cross-cutting/codex-harness-delivery.md)과 [설치 실험 보고서](../reports/2026-11-10-dual-harness-phase1.md)에서 진행 상태를 확인한다.

Codex 세션 연결은 공통 규칙·설정·경로 규칙·포맷과 승인 사전 검사 안내를 제공한다. 단독 `TEST_CMD`를 프로젝트 루트에서 감싸 실행하고 호출별 종료 코드·물리 작업 폴더를 확인한다. 테스트 시작 ID와 편집 세대·최종 결과를 기록해, 테스트 중 재편집과 실패 요약을 성공으로 인정하지 않는다. 완료 검증은 대화 원문에 의존하지 않고 `.codex/harness-state/`에 최소 증거를 둔다. Claude Stop의 완료·편집·실패 판정은 같은 공통 정책을 사용하되 기존 대화 기록 해석을 유지한다.

초기화는 Claude·Codex·양쪽을 선택하고 공통 값은 `.claude/harness.conf` 한 개로 관리한다. 생성 역할은 공통 원본에서 만들며 사용자 수정이 있으면 충돌로 알린다. Codex 프로젝트 신뢰·실제 플러그인 설치·훅 신뢰와 설정 생성은 각각 별도로 확인한다.

Codex 회고는 현재 프로젝트의 UserPromptSubmit 메시지 원문과 확인한 feedback을 로컬 `.codex/corrections/`에 기록한다. 기록은 버전 관리에서 제외한다. 분석 시 추출·길이 제한한 메시지가 기존 Claude 분석기로 전달되며 정정 여부를 판단한다. 대기열·후보·장부도 도구별로 분리하고, 분석은 기존 Claude 실행기와 1달러 상한을 재사용한다. 기록·알림은 분석 실행기 없이도 동작한다. 최초 분석은 사용자가 실행하고 이후 기존 AUTO_ANALYZE·7일 간격·잠금을 따른다. 분석 실행기가 없거나 실패하면 원인을 알리고 마지막 분석 시각을 옮기지 않는다. Gemini 기준판도 도구별 폴더로 분리한다.
