# Core — 테스트 원칙 (언어 무관)

**적용 범위:** 테스트 코드 전부 — `tdd` 스킬로 쓰는 승인 지점의 테스트와, 그 밖에서 쓰는 평소 테스트 모두.

테스트가 **무엇을 어떻게 확인하는지** 정한 규칙이다. 목표는 코드를 다듬어도 깨지지 않고, 진짜 결함은 놓치지 않으며, 목록만 읽어도 무엇을 보장하는지 알 수 있는 테스트다. 언어별 표기(이름 짓는 문법·단언 라이브러리·가짜 객체 도구·실행 명령)는 lang 팩의 "테스트 규칙" 절이 정하고, 여기는 어느 언어에도 같은 **원칙**만 둔다. 주석은 `core-code-comments.md`가 같은 방식으로 나눈다.

**테스트를 언제·어떤 순서로 쓰는지는 이 파일 밖이다.** 어느 항목을 테스트 먼저 쓸지는 G2에서 사람이 승인하고(`specify` 스킬 "테스트 먼저 지점" 표), 실패하는 테스트부터 쓰는 순서는 `tdd` 스킬이 SSOT다. 테스트 먼저 지점이 아닌 곳은 "유의미한 테스트만" 쓴다 — 무엇이 유의미한지가 아래 S1~S8이다.

## S1. 결과를 확인하고, 과정은 확인하지 않는다

반환값·응답·저장된 상태처럼 **바깥에서 관찰할 수 있는 결과**를 단언한다. 내부 협력 객체를 몇 번·어떤 순서로 불렀는지는 단언하지 않는다.

- 과정을 단언한 테스트는 동작이 같아도 구현을 다듬는 순간 깨진다. 그런 테스트는 리팩터를 막고 결함은 잡지 못한다
- 가짜 대역(아래 S3) 도구를 쓰더라도 호출 검증이 아니라 입력을 고정하는 데만 쓴다
- 기대값은 스펙의 값이나 손으로 계산한 값으로 적는다. 구현이 내놓은 값을 그대로 옮겨 적은 단언은 아무것도 확인하지 않는다

## S2. 흐름은 실제 경로로, 계산만 떼어서

비즈니스 흐름은 **실제 진입점부터 저장소까지** 거쳐 확인한다. 진입점의 인증·검증·변환, 저장 계층의 매핑·쿼리가 그 경로에서 함께 확인된다. 떼어서 단위로 확인하는 것은 입력과 출력만으로 판정되는 **순수 계산**(규칙 판정·금액 계산·버전 비교·문자열 조립)이다.

- 계층 하나만 띄우고 나머지를 가짜 대역으로 채운 테스트는 기본값이 아니다. 실제 경로 테스트가 실측으로 너무 느리다고 확인됐을 때만 쓴다
- 단순한 데이터 전달·연결 코드는 따로 테스트하지 않는다. 그 코드를 지나는 흐름 테스트가 이미 확인한다

## S3. 통제할 수 없는 경계만 가짜로

**가짜 대역**(실제 대상 대신 테스트에서 쓰는 대체물)으로 바꾸는 대상은 **우리가 통제할 수 없는 것**뿐이다 — 외부 서비스 API, 현재 시각, 비동기 실행, 난수. 우리 코드끼리는 실제로 연결한다.

- 가짜 대역은 상태를 가진 작은 대체물(응답을 미리 정해 두는 가짜 서버, 앞으로 돌릴 수 있는 시계, 붙잡았다 놓을 수 있는 실행기)으로 만들고, 테스트마다 초기화한다
- 외부 서비스의 실패(시간 초과·오류 응답)도 이 대역으로 재현해 확인한다

## S4. 테스트 이름은 "조건이면 결과" 문장

테스트 하나의 표시 이름은 **"무엇을 하면 어떻게 된다"** 문장으로 쓴다. 테스트 목록이 그대로 기능 명세서로 읽혀야 한다.

- 실패 케이스는 결과에 거절 사유를 넣는다 — "권한 없는 사용자가 조회하면 403과 접근 거부 코드를 반환한다"
- 대상 기능·진입점·메서드 단위로 묶어, 같은 대상의 테스트가 한곳에 모이게 한다
- 표시 이름과 코드상 이름을 따로 두는 언어라면 그 표기는 lang 팩이 정한다

## S5. 실패도 계약이다

성공 케이스만이 아니라 **거절하는 경우**도 확인한다. 상태 코드만 보지 않고 프로젝트가 정의한 에러 코드까지 단언한다. 에러 코드는 문자열을 다시 적지 않고 코드에 정의된 상수에서 꺼내 비교한다 — 그래야 코드 값이 바뀔 때 테스트가 함께 따라간다.

## S6. 응답 뒤에 남는 변화까지

응답이 맞는 것으로 끝내지 않는다. 그 요청이 **남기기로 한 상태 변화**(저장된 기록·차감된 잔액·발행된 이벤트)가 실제로 남았는지 함께 확인한다. 동시 요청처럼 순서가 섞일 수 있는 동작은 실제로 경합을 만들어 확인한다.

## S7. 테스트끼리 섞이지 않게

테스트마다 **서로 다른 데이터**(식별자·이름)를 써서, 실행 순서가 바뀌거나 일부만 돌려도 결과가 같게 한다. 전체 개수·전체 삭제처럼 공유 상태 전체를 보는 테스트만 시작할 때 그 상태를 비운다. 두 방식 중 무엇을 쓸지는 lang 팩이 기준으로 정한다.

## S8. 느리거나 비용이 드는 테스트는 분리한다

실제 외부 서비스를 호출해 돈이 들거나, 느리거나, 외부 상태에 따라 결과가 흔들리는 테스트는 **기본 실행(`{{테스트 명령}}`)에서 빼고** 별도 명령으로 돌린다. 기본 실행은 언제 돌려도 같은 결과가 나와야 한다 — 그래야 G3에서 "통과"를 판정할 수 있다.

## 검증

원칙 준수는 exit code로 판정할 수 없어 **advisory**다. 코드 리뷰(`code-review` · 스택 리뷰어)가 다음을 본다.

- 내부 호출 횟수·순서를 단언하는 테스트가 있는가
- 기대값이 구현 출력을 그대로 옮긴 것인가
- 우리 코드끼리의 연결을 가짜 대역으로 대신한 곳이 있는가
- 실패 케이스가 에러 코드까지 확인하는가
- 기본 실행에 외부 호출 테스트가 섞여 있는가

## 금지

- 내부 협력 객체의 호출 횟수·순서 단언
- 구현이 내놓은 값을 기대값으로 옮겨 적기
- 테스트를 통과시키려고 단언을 느슨하게 고치기 — 테스트를 바꿔야 하면 이유를 보고한다
- 상수 값을 다시 적어 비교하기만 하는 테스트, 프레임워크 자체 동작을 확인하는 테스트
- 테스트 사이에 데이터를 공유해 실행 순서에 따라 결과가 바뀌게 두기
