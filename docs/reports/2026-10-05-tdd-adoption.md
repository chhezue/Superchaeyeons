# TDD 도입 — 작업 보고서

사람이 승인한 지점에서만 실패하는 테스트를 먼저 쓰는 TDD(테스트 주도 개발)와, 모든 테스트에 적용되는 스택 무관 테스트 원칙을 하네스에 넣은 작업의 보고서다. 스펙 [`tdd-adoption.md`](../specs/cross-cutting/tdd-adoption.md)의 Must Have를 모두 반영했고 `scripts/verify.sh`가 통과한다. 실제 프로젝트에서 이 절차를 한 번도 돌려 보지 못한 점은 "검증하지 못한 것"에 남겼다.

## 무엇을 했나

- **새 파일 3개:** `.claude/skills/tdd/SKILL.md`(순서 T1~T6 · 지점별 루프 · 증거 표) · `.claude/agents/test-writer.md`(통제 영역 지점의 테스트를 구현 계획 없이 작성, `Write`/`Edit` 있음 · `Bash` 없음) · `.claude/rules/core-testing.md`(원칙 S1~S8, 테스트 파일 접근 시에만 로드)
- **연결:** `specify`(7단계 "테스트 먼저 지점" 제안 + 스펙 템플릿 표) · `preflight`(증거 표 행 수 대조, 재현 불가 버그 제외) · `debug`(재현 실패 테스트를 `tdd` 절차로, "TDD 메모" 절 삭제) · `core-workflow.md`(G2 승인 대상 · 구현 절) · 작업 보고서 골격("TDD 증거" 절)
- **씨앗:** Java `local-testing.md`의 충돌 5줄을 원칙에 맞춤 · `_template` 테스트 절을 원칙별 표기 칸으로 바꿈
- **검사기 패턴:** C4 `testing\.md` → `local-testing\.md` · C1 단독 `S3` → 제품 문맥(`Amazon S3`·`S3 버킷`·`s3://` 등)
- **목록·지도:** `AGENTS.md` · `CLAUDE.md` · `README.md` · `.claude/rules/README.md` · `docs/harness/` 4개 · `harness-engineering.md` · `references.md` · `out-of-scope/README.md`

## TDD 증거

이 스펙의 "테스트 먼저 지점" 표는 전부 "아님"이다. 문서·지침 변경이라 깨뜨릴 동작이 없고, 판정은 `scripts/verify.sh`가 맡는다.

## 검증하지 못한 것

| 무엇 | 왜 못 했나 | 누가·언제 확인하나 |
|------|-----------|-------------------|
| `tdd` 절차를 실제 코드 저장소에서 한 사이클 돌리기 | 이 저장소에 애플리케이션 코드가 없다 | 하네스를 붙인 첫 프로젝트에서 Must 항목 하나로 시험. 결과는 `retro`로 |
| `test-writer` 에이전트가 실제로 호출·등록되는지 | 에이전트 파일은 세션을 다시 열어야 목록에 뜬다 | 다음 세션에서 에이전트 목록 확인 |
| `core-testing.md`의 `paths:` 패턴이 각 언어 테스트 파일에서 실제로 로드되는지 | 이 저장소에 테스트 파일 이름을 가진 파일이 없다 | 붙인 프로젝트에서 테스트 파일을 열어 확인 |
| 문서 문체 경고 4건(RED·GREEN 약어) | 경고 등급이고 본문에서 뜻을 풀어 썼다 | 필요하면 `doc-style-patterns.txt` ALLOW에 추가 |
