# Core — 워크플로 (트랙 × 규모 × 게이트)

**어떤 순서로 일하는지**를 정한다. 시작할 때 트랙(무슨 일인가)과 규모(얼마나 큰가)를 하나씩 고르고, 규모가 정한 게이트만 거친다. **`core-guardrails.md`가 이 문서보다 우선한다.** 경로·명령·플래그 값은 `harness-map.md`, Git 형식은 `{{Git 컨벤션 SSOT}}`(없으면 이 문서 G2·G4).

## 진입 — 트랙과 규모

1. 범위·완료 기준을 이슈에서 확인한다(브랜치용 `#n`). `{{우선순위 SSOT}}`가 있으면 활성 Milestone도 본다
2. 트랙을 고른다

| 트랙 | 언제 | 진입 스킬 |
|------|------|-----------|
| **A 기능** | 새 기능·API·엔티티·정책 변경 | 스펙 신호(DB 스키마 · 3파일+ · BR-* · 프로필/배포 · 인증·푸시·딥링크·결제 같은 클라 연동 API)가 있으면 `specify` → 승인 후 구현. 없으면 `{{제품 범위}}` 확인 후 구현. Approved 스펙이 없을 때만 Plan Mode로 탐색 |
| **B 감사·리팩터** | 기존 코드 품질 개선 | `safe-refactor` — 작업 단위 하나씩, 단계마다 승인 |
| **C 버그** | 버그 리포트·`{{테스트 명령}}` 실패 | `debug` — 재현 → 원인 분리 → 최소 수정 |
| **D 하네스 이식** | 하네스를 붙일 때·`harness-map.md`가 실제와 다를 때 | `adopt` — 실측 → 제안 승인 → 채움. 애플리케이션 코드 불변 |

3. 규모를 고른다 — 걸치면 큰 쪽

| 규모 | 조건 | 거치는 것 |
|------|------|-----------|
| **S 단순** | 오타·문구·로그 한 줄·단일 파일 핫픽스이고, `core-gates.md` §1 통제 영역에 닿지 않음 | 바로 구현 → 코드를 고쳤으면 `{{테스트 명령}}` → G4 커밋 분할안 |
| **M 표준** | S도 L도 아님 | 트랙 스킬 · G2 · 구현 · G3 · G4 |
| **L 강화** | 3파일 이상 · API · DB 변경 | M + G3 별도 컨텍스트 리뷰 + G4 보고서·후속 제안·`retro` 검토 |

4. 문서 확인 순서: `AGENTS.md` → `harness-map.md` → `{{아키텍처 개요}}` → `{{우선순위 SSOT}}` → `{{클라이언트 전제}}` → `{{결정 기록}}` → `{{제품 범위}}`

## G1. 리서치 — 외부 지식에 기댈 때만

외부 라이브러리·SDK·API나 처음 쓰는 프레임워크 기능에 기대면 구현 전에 확인한다. 로컬 실물(의존성 선언·`{{의존성 조회}}`·설치본)을 먼저 보고, 그다음 버전을 확인한 공식 문서를 본다. 블로그·StackOverflow는 근거로 인용하지 않는다. 문서 2개 이상을 비교하면 `researcher` 서브에이전트(소스 우선순위·출력 형식 SSOT), 한 페이지면 인라인 `WebFetch`. **[플래그: 스택 함정 메모]** 주 버전 함정은 lang 팩에 있다.

## G2. 승인 — 사람이 끊는 지점

- **승인 대상:** A = 스펙(테스트 먼저 지점 포함) · B = 감사 문서의 A/B 항목 · C = 원인 가설과 수정 범위 · D = 실측 근거가 붙은 슬롯·플래그 제안. `AskUserQuestion` 또는 채팅
- 요청이 열려 있으면(`core-gates.md` §2) `ask` 스킬부터 — 사실은 조사하고 결정만 묻는다
- **불변 조건**(작업 도중 어느 시점에도 참이어야 하는 조건 — 완료 기준과 다르다)을 트랙 기본값에서 시작해 확정한다. A: 기존 테스트 통과·기존 API 계약(새 필드 추가는 예외) · B: 비즈니스 로직·관찰 가능한 최종 동작 · C: 이 버그와 무관한 기존 동작 · D: 코드 불변
- 가정을 적는다. 해석이 갈리면 묻고, 더 단순한 방법이 있으면 말한다. 모호함·문서 충돌은 STOP §1
- 변경 파일 목록을 확정한다. 다단계면 `1. [단계] → verify: [확인]`
- 브랜치는 `main`에서 `{{브랜치명 형식}}` — 이슈 번호를 빼지 않는다

## 구현

- 요청 범위만 — 인접 개선·깨지지 않은 리팩터·요청 밖 기능·단일 사용 추상화·불필요한 설정을 넣지 않는다. 바뀐 모든 줄이 요청에 연결된다
- 레거시는 같은 변경에서 삭제(STOP §2), 계약에 닿는 변경은 같은 턴에 끝낸다(STOP §1.7)
- 기존 스타일을 따르고 내 변경으로 생긴 unused만 정리한다. 패키지 구조·표기는 lang 팩, 주석 원칙은 `core-code-comments.md`, 테스트 원칙은 `core-testing.md`
- G2에서 승인된 테스트 먼저 지점과 버그 수정은 `tdd` 스킬
- 서브에이전트에는 대상을 경로 목록으로만 넘긴다. 읽기 범위는 에이전트 지침에 맡기고, "전문을 읽어라"는 신규 파일에만, 대상이 10개를 넘으면 나눠 부른다

## G3. 검증 — 완료 보고 전

절차 SSOT는 `preflight` 스킬이다(S는 `{{테스트 명령}}`만). 자기 보고 대신 명령 결과로 확인하고, `{{테스트 명령}}`을 돌리지 않고 "통과했을 것"이라고 하지 않는다 — 코드 편집 뒤 미실행·실패인데 완료를 말하면 Stop 훅이 턴을 되돌린다. 돌릴 수 없는 검증은 숨기지 않고 "검증하지 못한 것"에 이유와 함께 남긴다.

- **L은 별도 컨텍스트 리뷰를 커밋 전에 한 번 더**(요청이 있으면 PR 전에도) — `code-review` 또는 `simplify`. 방금 짠 코드를 같은 대화에서 리뷰하면 자기 판단을 재확인하게 된다
- **[플래그: API 계약 보호]** · **[플래그: 스택 리뷰어]** — `preflight`가 lang 팩 절과 리뷰어를 부른다
- 보안·아키텍처 성격 변경이면 `{{현재동작 요약}}` 갱신 확인 (STOP §3)

## G4. 회고·커밋

- **커밋 분할안**을 사용자가 묻지 않아도 작업 완료 보고와 같은 턴에 제안한다 — 목적·주제별 최대 5개, 한 주제면 1개. 파일 단위로 쪼개지 않고, 중간 커밋도 `{{테스트 명령}}`을 통과해야 한다. 메시지 `{{커밋 메시지 형식}}`, base `main`, merge commit 유지(Squash 금지)
- **커밋은 사용자 승인 뒤에만 실행한다.** 이슈·브랜치·PR은 사용자가 명시적으로 요청하지 않았으면 만들기 전에 묻는다. 커밋 승인은 PR 승인을 포함하지 않는다. PR 본문은 `Closes #n`, 체크리스트는 실제로 끝낸 것만 `[x]`
- 새로 확정된 결정·컨벤션·함정이 있으면 `AGENTS.md`·`.claude/rules/` 수정안을 **제안**만 한다. 같은 실수나 같은 후속 제안이 2회 이상이면 `retro` 스킬
- **L이면 보고서** — `{{문서 루트}}/reports/{YYYY-MM-DD}-{kebab-topic}.md`. 무엇을 · 결정 · 실행한 검증과 결과 · **검증하지 못한 것과 이유** · 남은 것을 적는다(골격 `{{문서 루트}}/templates/reference-doc.md`)
- **L이면 후속 제안** — 완료 요약 뒤 `## 후속 제안` 3~8개(무엇이 아쉬운지 → 권장 방향, 영향 큰 순). 같은 턴에 구현하지 않는다. 사용자가 제안을 요청하면 규모와 무관하게 쓴다
- B 트랙은 `{{감사 로그}}/refactor-log.md`에 append. 범위를 다른 이슈로 미루라는 지시는 `specify` 스킬 "범위를 미룰 때" 절
- PR merge를 확인한 뒤 작업 브랜치를 원격·로컬에서 지운다. merge 안 된 브랜치는 지우지 않는다
