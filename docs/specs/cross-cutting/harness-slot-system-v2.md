### 원인 3개

**① 옵션을 끄는 유일한 방법이 규칙 파일 삭제였다.**
`harness-map.md` 규칙 1은 "규칙 파일은 건드리지 않는다"인데, 스택 옵션 표는 "끄면 §5 삭제, 훅 해제"라고 지시한다. baro는 `core-guardrails.md` §5 본문 15줄을 실제로 삭제했다. 옵션 하나를 끌 때마다 부품이 영구히 갈라진다.

**② 고정 경로라 믿었던 것이 사실은 슬롯이었다.**

현재 `harness-map.md`는 "하네스와 함께 배달되는 문서는 슬롯이 아니다 — 경로가 고정이므로 규칙이 직접 부른다"고 적고 있다. baro에서 이 전제가 세 곳에서 깨졌다.

`.github/CONTRIBUTING.md`는 5인 공용 저장소 루트에 있어 하네스가 파일을 만들 권한이 없었다. 브랜치·커밋·PR 규칙을 담을 자리가 사라졌고, baro는 `core-workflow-git.md`를 새로 만들어 하네스 안으로 들여왔다. 문서 루트도 저장소 루트의 `docs/`가 아니라 `baro-ai/docs/`였는데, 이건 규칙 본문이 `docs/specs/`처럼 짧게 부르던 경로를 전부 무효로 만든다 — baro가 `{{문서 루트}}` 슬롯을 새로 판 이유다. 그리고 `docs/harness/`·`docs/templates/`·`docs/audits/harness-retro.md`도 전부 그 문서 루트 밑이므로 함께 옮겨갔다.

## 부품성 원칙 (지배 제약)

외부 참조를 반영할수록 하네스가 무거워지는 것이 이 스펙의 가장 큰 위험이다. 참조한 도구들은 규모가 다르다 — 한 플러그인은 훅 이벤트 11종에 Node 스크립트 20여 개를 물리고, 다른 하나는 스킬 30여 개를 버킷으로 나눠 관리한다. 그 규모를 그대로 가져오면 "새 프로젝트에 복사해 붙인다"는 이 저장소의 목적이 깨진다.

그래서 무엇을 가져올지 판단하는 잣대를 셋으로 고정한다.

1. **장치 하나는 bash 하나 + 데이터 파일 하나를 넘지 않는다.** 별도 런타임(Node 등)·상태 파일·플러그인 매니페스트를 요구하는 장치는 채택하지 않는다. 붙이는 프로젝트가 그 런타임을 갖고 있으리라 가정할 수 없다.
2. **새 개념은 기존 개념을 대체해야 한다.** 더하기만 하는 개념은 받지 않는다. Invariant를 받으면서 `{{계약 동결 수준}}` 슬롯을 지우는 것이 이 규칙의 실제 적용이다.
3. **언어·프레임워크·도구에 묶이는 것은 전부 팩으로.** core에 남는 것은 넷 중 무엇을 골라도 성립하는 것뿐이다.

### 팩 인터페이스 — `pack.md`

**하네스는 팩을 배달하지 않는다.** 팩은 붙이는 시점에 그 프로젝트를 실측해 **생성**된다. 하네스가 배달하는 것은 축의 정의와 아래 계약, 그리고 빈 `packs/` 디렉터리뿐이다.

이유는 카탈로그가 완성될 수 없기 때문이다. Go 서비스, Django 모놀리스, 서버리스 배포처럼 카탈로그에 없는 조합을 만나는 순간, 사용자는 다시 core 규칙을 고치게 된다 — 이 스펙이 막으려는 바로 그 실패다. 불완전한 카탈로그는 없는 카탈로그보다 나쁘다. 있으면 맞는 줄 알고 고르기 때문이다.

`pack.md`는 생성된 팩이 만족해야 하는 계약이다. 표 넷으로 고정한다.

```markdown
# pack: {축}-{이 프로젝트가 정한 이름}

| 항목 | 값 |
|------|-----|
| 축 | lang | shape | deploy | stage 중 하나 |
| 대상 | 이 팩이 전제하는 실제 상황 (실측 근거와 함께) |
| 같은 축 배타 | 축마다 팩은 하나 |

## 채우는 슬롯
| 슬롯 | 이 프로젝트의 값 |

## 켜는 능력 플래그
| 플래그 | 이 팩이 제공하는 구체 |

## 추가하는 부품
| 파일 | 역할 · `paths:` 범위 |
```

**참조 방향은 단방향이다.** 팩은 core를 참조할 수 있고, **core는 어떤 팩도 참조하지 못한다.** core가 프로젝트 사정을 알아야 하는 지점은 슬롯과 능력 플래그로만 표현하며, 둘 다 core가 소유한 고정 어휘다. core가 팩 **이름**을 부르는 일은 없다 — 이름은 프로젝트가 정하므로 core가 알 수 없다.

### 고정 어휘 — 축과 능력 플래그

프로젝트마다 달라지는 것은 **답**이고, 하네스가 배달하는 것은 **질문**이다.

| 하네스가 배달 (고정) | 프로젝트가 결정 (유동) |
|---|---|
| 축 4개 — 무엇을 물을지 | 축마다 팩 1개 — 이 프로젝트의 답 |
| 능력 플래그 — core 절이 참조하는 배지 어휘 | 각 플래그를 켤지, 켜면 어떻게 구현할지 |
| 슬롯 이름 — 규칙이 부르는 역할 | 슬롯 값 — 이 프로젝트의 경로·명령 |
| `pack.md` 계약 | 팩 이름·내용·부품 |

능력 플래그는 현행 스택 옵션 7개를 그대로 쓴다(마이그레이션 금지, 에러코드 동시갱신, 권한·활동 어노테이션, API 계약 보호, 생성 문서 검증, 스택 함정 메모, 스택 리뷰어). 플래그를 새로 늘리는 데는 슬롯과 같은 문턱을 적용한다 — `core-*.md`에서 실제로 그 배지를 다는 절이 있을 때만 추가한다.

축을 5개로 늘리는 것도 같은 문턱을 따른다. 넷은 저장소 두 개를 관찰해 뽑은 것이라 완전하다는 보장이 없다. 다섯 번째 축이 필요하다고 판단되면 `harness-map.md`에 근거와 함께 적고, 그 축을 실제로 참조하는 core 절이 생길 때 어휘로 승격한다.

## 설계

### 1. 디렉터리 — 3층

```
.claude/
├── rules/
│   ├── core-*.md          ← 부품. 수정 금지. 세 저장소에서 바이트 단위 동일
│   ├── core-gates.md      ← 신설: Stop & Ask 트리거 표 + 자동화 금지 목록
│   ├── harness-map.md     ← 프로젝트가 고치는 유일한 파일
│   └── local-*.md         ← 프로젝트 고유 (baro-ai-performance-refactor 같은)
├── (packs/ 없음)          ← 2026-09-05 결정: 축은 adopt의 질문 목록, 산출물은 harness-map 값 + rules/local-*.md
├── skills/  (specify safe-refactor debug preflight defer retro + ask adopt)
├── agents/  (researcher doc-reviewer — 스택 리뷰어는 lang 팩으로)
└── hooks/   (deny-dangerous-bash · ask-open-request · deny-unverified-completion · warn-unfilled-map)
```

접두사(`core-`/`local-`)로 층이 구분되므로 이식성 검사가 기계적으로 가능하다.

**층마다 수정 권한이 다르다.** 이 구분이 3층 분리의 실제 목적이다.

| 층 | 수정 | 이유 |
|---|---|---|
| `core-*.md` | **금지** | 세 저장소에서 바이트 단위로 같아야 개선이 함께 전파된다 |
| `packs/` | **자유** | 프로젝트 소유. 갈라지는 것이 팩의 일이다 |
| `local-*.md` | 자유 | 이 저장소에서만 사는 사실 |
| `harness-map.md` | 채우기 | 축·슬롯·플래그의 값 |

지금 하네스가 갖고 있는 Java·Spring 규칙 5개는 **팩이 아니라 씨앗**이다. `examples/`로 옮겨, Java 프로젝트가 `adopt` 중 복사해 시작할 수 있게 한다. 복사한 뒤 그 프로젝트의 팩 안에서 자유롭게 고쳐도 core는 갈라지지 않는다.

### 2. 부품 계약 — core에 없어야 하는 것

| 금지 | 대신 |
|------|------|
| 고유명사 (프로젝트·회사·제품·도메인 용어) | 슬롯 또는 `local-*.md` |
| 언어·프레임워크 식별자 (`@Schema`·`./gradlew`·JPA·`@Aspect`) | lang 팩 |

| **팩 이름 · 팩 파일 참조** | 능력 플래그 또는 슬롯 |

`scripts/check-portability.sh`가 1~4를 금지어 grep으로, 5를 링크 스캔으로 판정한다. exit 1이면 지속적 통합(CI) 파이프라인과 `pre-commit` 훅이 막는다.

### 3. 배지 판정 — 옵션이 꺼져도 절을 지우지 않는다

배지는 **능력 플래그**를 부른다. 팩 이름은 프로젝트가 정하므로 core가 알 수 없고, 알아서도 안 된다.

```markdown
### 5. API 계약 변경 — Breaking-Change-Reason 트레일러

> **[플래그: API 계약 보호]** `harness-map.md`에서 이 플래그가 꺼져 있으면 **이 절 전체를 무시한다.** 절을 삭제하지 않는다 — 삭제하면 부품이 갈라져 이후 개선을 받을 수 없다.
```

`harness-map.md`에 규칙 4를 추가한다: **"옵션을 끄려고 규칙 파일을 수정하지 않는다."**

배지가 무시될 위험은 harness-map이 always-load라 축 선택 표가 항상 컨텍스트에 있다는 점으로 완화한다. 또 `core-guardrails.md` 금지 요약 표의 해당 행에 `(축 판정)` 표시를 남긴다.

### 8. `ask` 스킬 — 라운드 방식 소크라테스 인터뷰

질문을 하나씩 던지면 응답 횟수가 질문 수만큼 늘고, 전부 한 번에 던지면 앞 답이 뒤 질문을 무효로 만든다. 그 사이를 가르는 개념이 **프론티어**다.

**프론티어** = 선행 결정이 전부 끝난 질문의 집합. 한 **라운드**는 프론티어를 통째로 묻는다. 같은 라운드에 서로 의존하는 질문이 들어가지 않으므로, 라운드 안의 어떤 답도 같은 라운드의 다른 질문을 무효로 만들지 못한다. 답이 오면 프론티어가 바깥으로 이동하고, 다음 라운드는 그것이 풀어준 것을 묻는다. 질문 13개가 3라운드에 끝난다.

**사실과 결정을 가른다.** 환경이 답할 수 있는 것(코드·설정·의존성 버전)은 묻지 않고 직접 조사한다. 사용자를 기다리는 것은 **결정뿐**이다. 자기 질문에 스스로 답하는 것은 이 스킬을 느슨하게 해석한 게 아니라 깨뜨린 것이다.

**질문 형식** — 라운드를 번호로 답할 수 있어야 한다.

```
❓ 1. {한 줄 제목}
   {무엇을 왜 묻는지}
   ➡️ {권장 답}
```

**끝나는 시점** — 프론티어가 비어도 끝이 아니다. **사용자가 "이해가 공유됐다"고 확인해야** 끝난다. 질문 수 상한은 두지 않는다 — 어떤 계획은 3개로, 어떤 계획은 30개로 끝나므로 고정 상한은 어려운 쪽을 자르거나 쉬운 쪽에서 자의적이다. 길어지면 범위가 컸다는 뜻이니 쪼개서 다시 묻는다.

**남용 방지** — 오타·한 줄 수정·명확한 버그 핫픽스·이미 Approved 스펙이 있는 구현에는 쓰지 않는다. 질문은 답을 유도하는 것이 아니라 전제를 드러내는 것이다.

**한 번에 하나 옵션** — 천천히 읽는 사람, 제2언어로 일하는 사람에게는 순차 방식이 낫다. `harness-map.md`에 한 줄로 끌 수 있게 둔다.

### 12. Invariant — 계약 동결 슬롯을 대체하는 일반 개념

하네스에는 "이번 작업 내내 절대 깨지면 안 되는 조건"이라는 개념이 없었다. `safe-refactor`의 "API 계약 100% 동일"은 사실 그 개념의 특수 사례 하나였고, 그것만 슬롯으로 빼려던 것이 v1 설계의 우회였다. 일반 개념을 도입하면 슬롯 하나가 줄고, 세 트랙 전부가 같은 장치를 쓴다.

**G2 승인 시 Invariant 목록을 확정한다.** 트랙별로 기본값이 다르다.

| 트랙 | 기본 Invariant |
|---|---|
| A 기능 | 기존 테스트 통과 · 기존 API 계약(새 필드 추가는 예외) |
| B 감사·리팩터 | 비즈니스 로직·정책 · 관찰 가능한 최종 동작 |
| C 버그 | 이 버그와 무관한 기존 동작 |
| D 인수 | 코드를 바꾸지 않음 (문서만 만든다) |

Invariant는 **완료 기준과 다르다.** 완료 기준은 "끝났다고 판정하는 조건"이고, Invariant는 "작업 도중 어느 시점에도 참이어야 하는 조건"이다. 그래서 스펙 템플릿에서 `검증 시나리오`가 아니라 별도 절로 둔다. B 트랙에서 계약을 바꿔도 되는지는 그 목록에 API 계약이 있느냐로 결정되며, 릴리즈 전 프로젝트는 목록에서 빼면 된다.

### 13. 실행 환경 검증 — `preflight`의 사전 모드

`preflight`는 완료를 선언하기 **전**에 도는 스킬이라 "다 짜고 보니 테스트 환경이 안 돌아감"을 잡지 못한다. 같은 스킬에 사전 모드를 둔다 — 새 스킬을 만들지 않는 것이 부품성 원칙 2번의 적용이다.

G2 승인 직후, 구현 첫 줄을 쓰기 전에 `{{빌드 명령}}`과 `{{테스트 명령}}`이 **현재 상태에서** 성공하는지 확인한다. 실패하면 그 실패가 이번 작업 때문이 아님을 먼저 확정한다. 명령이 `(없음)`이면 건너뛴다.

### 14. 규칙 로딩 하이브리드 — `inject-rules.sh` 하나

배지 판정의 알려진 약점은 꺼진 절도 상시 로드된다는 것이었다. 규칙을 상시 로드 대신 **파일을 건드린 뒤 주입**하면 그 문제가 사라진다.

단순하게 만드는 열쇠는 **새 매핑 파일을 만들지 않는 것**이다. 각 규칙 파일은 이미 `paths:` frontmatter로 자기 적용 범위를 선언하고 있으므로, 훅은 그 frontmatter를 읽어 방금 건드린 파일과 맞는 규칙의 **경로만** 출력한다. 규칙 본문을 복사하지 않으므로 중복도 동기화 부담도 생기지 않고, 에이전트가 필요하면 그 파일을 직접 읽는다.

| 상시 로드로 남기는 것 | 주입으로 옮기는 것 |
|---|---|
| `core-guardrails.md` (STOP) · `core-gates.md` (멈춤) · `harness-map.md` (축·슬롯) | 나머지 `core-*.md`와 모든 팩 규칙 |

**알려진 한계:** 주입이 실패하면 규칙이 조용히 사라진다. 그래서 멈춤과 관련된 것은 주입으로 옮기지 않는다.

### 15. 문서 강제 — 검사기와 리뷰어의 분담

`doc-writing.md`를 toss 가이드 원문과 대조한 결과, 정보 구조 6원칙 중 5개와 문장 5원칙 중 4개는 이미 담겨 있다. **빠진 것 4개**를 보강한다: 명사 대신 동사 쓰기 · 번역체와 불필요한 한자어 · 제목 깊이가 H4를 넘으면 문서 분할 · 제목은 30자 이내 평서문.

원칙과 구조만 가져오고 **원문 문장은 옮기지 않는다.** toss 가이드는 CC BY-NC-SA 4.0이라 문장을 복사하면 라이선스가 이 저장소로 전염된다.

강제는 둘로 나눈다. **패턴으로 잡히는 것은 `check-doc-style.sh`가 exit code로 판정**하고 `pre-commit`이 막는다: 제목 길이, H4 깊이, 약어 첫 등장, 번역투·메타 담화 상용구. **판단이 필요한 것은 `doc-reviewer`가 계속 advisory로** 맡는다: 유형이 내용과 맞는지, 개요가 실제로 요약인지, 근거 없는 단정.

검사 패턴은 스크립트가 아니라 `doc-style-patterns.txt`에 데이터로 둔다. 한국어가 아닌 프로젝트는 그 파일만 갈아끼우면 되므로, 스크립트 자체는 언어에 묶이지 않는다.

### 16. 스킬 문서 프레임 · 라우터 · `.out-of-scope/`

셋 다 작은 장치이고, 하네스가 커질수록 값이 커지는 것들이다.

**스킬 문서 프레임** — 각 `SKILL.md`에 두 가지를 넣는다. 하나는 **defining constraint**: 이 스킬이 기본 동작과 달라지는 단 하나의 사실을 한 줄로(`ask`라면 "프론티어 밖 질문은 묻지 않는다"). 다른 하나는 **`It's working if`**: 잘 돌아갈 때 무엇이 보이는지. 기준은 **`SKILL.md`를 열지 않고 확인 가능할 것** — 열어야 확인되는 항목은 이 절이 아니라 내부 규정이다.

**호출 주체 표시** — 지금 스킬 8개는 에이전트가 알아서 부를지 사용자가 타이핑해야 할지가 불분명하다. frontmatter 한 줄로 구분한다.

**라우터** — `core-tools.md`의 트랙×게이트 표를 라우터로 명시하고, **스킬·에이전트를 추가·삭제·개명하면 같은 턴에 갱신**을 `README.md` 유지보수 체크리스트에 넣는다. 새 스킬을 언급하지 않거나 없어진 스킬로 안내하는 라우터는 거짓말을 한다.

**`.out-of-scope/`** — "안 하기로 한 결정"을 이유와 함께 파일로 남긴다. 지금 `core-tools.md` 본문에 묻혀 있는 "OMC·Superpowers 미채택" 결론이 정확히 이 형태이고, 이 스펙의 `Out of Scope` 항목 중 오래 살 것들(모호성 점수 게이팅, 산출물 검증 훅)도 여기로 간다. 같은 논쟁이 반복되는 것을 막는 장치다.
