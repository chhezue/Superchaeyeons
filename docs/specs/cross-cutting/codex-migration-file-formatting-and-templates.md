# Codex 이전 보존·파일별 포맷·문서 양식

기존 프로젝트를 Codex 하네스로 옮길 때 개발자의 Git 작업 방식과 문서 양식을 보존한다. 적용 순서는 **이전 전후 대조 → 편집 파일만 포맷 → 프로젝트 양식으로 스펙·감사 작성**이다. 이 문서는 각 단계의 변경 범위와 통과 기준을 정한다.

> 상태: Approved (2026-11-24 사용자 승인)
> 제품 범위: Superchaeyeons의 Codex 설치·편집·문서 작성
> 관련 BR: 해당 없음

## 배경

TripFit의 전환 커밋은 Git 훅을 남기고, PR 템플릿 주석이 가리키는 문서 규칙을 보존했다. 스킬 폴더 안에 있던 프로젝트 양식 세 개를 옮기면서 양식 안의 상대 링크도 고쳤다. 당시 공통 포맷 훅은 파일명으로 실행 여부만 판단해서, TripFit은 자동 포맷을 끄고 파일별 명령을 프로젝트 지침에 적었다. [TripFit 전환 내역](https://github.com/Central-MakeUs/TripFit-server/commit/faba88e6a968026f292fe68fa5327e8eb8d33168)

Superchaeyeons의 설정 생성기는 새로 생성한 역할·명령 규칙의 수정을 감지한다. 예전에 복사한 훅·규칙의 출처나 PR 템플릿에서 참조하는 경로까지 판별하지는 않는다. Codex 편집 후처리는 성공한 패치의 경로를 이미 추출한다. 스펙과 감사 스킬은 플러그인 기본 양식을 직접 지정한다. [이전 안내](../../../plugin/skills/init-harness/references/migrate-copied-harness.md) · [Codex 편집 후처리](../../../plugin/hooks/codex-context.py) · [기존 Codex 지원 스펙](codex-harness-delivery.md)

## 요구사항

세 단계 모두 Superchaeyeons에서 구현한다. TripFit은 전환 사례이며, 수용 시험은 별도의 임시 저장소에서 수행한다.

### 1. 이전할 파일과 동작을 승인받는다

- [ ] **이전안.** `init-harness`의 Codex 이전 경로에서 프로젝트의 Git 훅 원본·실제 실행 위치·등록, 규칙과 양식, 이를 읽는 파일을 조사한다. 이미 설정된 `core.hooksPath`와 심볼릭 링크를 확인한다. 삭제·이동 후보의 옛 경로는 마크다운 링크뿐 아니라 지침·스크립트·PR 템플릿의 일반 텍스트와 주석에서도 찾는다.
- [ ] **보존과 대체.** 승인안의 각 행에 **경로와 출처 근거 / 사용하는 주체와 시점 / 보존·이동·대체·삭제할 내용 / 바꿀 참조 / 검증 방법**을 적는다. 설치 당시 원본 또는 Git 이력과 대조해 동일본·프로젝트 수정본·출처 불명을 구분한다. 이름이나 접두사만으로 삭제를 제안하지 않는다. 출처 불명은 보존하고, 동일본도 사람이 직접 커밋할 때 쓰이거나 다른 파일이 참조하면 그 용도를 먼저 해결한다.
- [ ] **승인 후 대조.** 제안 단계는 읽기 전용이다. 사용자가 선택한 항목만 적용하고, 실제 Git 훅의 실행 권한·동작과 이동 후 참조를 다시 확인한다. 기존 훅에서 이미 재현되는 문제는 전환으로 생긴 회귀와 따로 기록한다. 새 프로젝트에는 복사본 이전 점검을 추가하지 않는다.

주요 변경 위치는 [초기화 스킬](../../../plugin/skills/init-harness/SKILL.md)과 [이전 안내](../../../plugin/skills/init-harness/references/migrate-copied-harness.md)다. 기계로 수집할 사실은 기존 [읽기 전용 조사 스크립트](../../../plugin/scripts/init-harness-probe.sh)에 둔다. 프로젝트마다 다른 Git 훅을 설치하거나 고치는 기능은 범위 밖이다.

### 2. Codex가 편집한 파일만 포맷한다

- [ ] **파일별 호출.** 프로젝트가 기존 설정 파일 `.claude/harness.conf`에 선택 키 `FORMAT_FILE_EXEC`로 저장소 루트 기준 실행 파일 경로 하나를 지정할 수 있다. 성공한 `apply_patch`에서 `FORMAT_PATHS`에 맞는 기존 일반 파일의 절대경로를 실행 파일에 인자 하나로 넘긴다. 작업 디렉터리는 프로젝트 루트다. 경로를 셸 명령 문자열에 합치지 않는다. 한 패치의 동일 대상은 한 번만 실행하고, 이동은 새 경로, 삭제는 실행 0회로 처리한다.
- [ ] **실패와 호환.** 파일별 실행 파일을 설정했는데 없거나 실행할 수 없거나 실패하면 대상과 원인을 알린다. 편집은 유지하고 전체 포맷은 실행하지 않는다. 저장소 밖으로 이어지는 실행 파일·대상 파일은 실행 대상에서 제외하고 알린다. 프로젝트가 새 키를 쓰지 않을 때는 기존 자동 포맷 동작을 유지한다.

다음 표는 설정별 실행 결과다. `FORMAT_PATHS`는 자동 포맷 대상 패턴이고, `FORMAT_CMD`는 기존 포맷 명령이다.

| 프로젝트 설정 | Codex 편집 후 | 수동 전체 포맷 |
|---|---|---|
| 대상 패턴 + 파일별 실행 파일 | 일치한 파일마다 경로 인자 한 개. 전체 명령이 비어 있어도 동작 | 설정된 기존 전체 명령 |
| 대상 패턴 + 새 키 누락 또는 빈 값 | 기존 방식으로 일치 시 `FORMAT_CMD` 실행 | 설정된 기존 전체 명령 |
| 빈 대상 패턴 | 자동 실행 0회 | 설정된 기존 전체 명령 |

초기화 때는 확인한 파일별 실행 방법을 제안한다. 새 설치에서 전체 명령만 발견하면 수동 전체 포맷을 유지하고, 편집할 때마다 전체 포맷까지 켤지는 승인안에 표시한다. TypeScript·Python 등에서 필요한 고정 옵션은 프로젝트 실행 파일이 담당한다. [설정 키 목록](../../../plugin/scripts/harness-keys.txt) · [기존 포맷 훅](../../../plugin/hooks/auto-format.sh)

### 3. 프로젝트 양식을 실제 문서에 적용한다

- [ ] **양식 선택.** 스펙 양식, 감사 체크리스트, 감사 결과 양식을 각각 선택한다. 해당 작업에 적용되는 `AGENTS.md`의 직접 지정을 먼저 따르고, 직접 지정이 없으면 거기서 연결한 문서 등록부를 확인한다. 해당 종류의 지정이 없으면 플러그인 기본 양식을 사용한다. 명시한 링크가 깨졌거나 같은 우선순위에 지시가 둘이면, 해당 경로와 충돌을 보여주고 그 문서 작성만 멈춘다.
- [ ] **산출물.** `write-spec`은 선택한 양식의 고유 섹션을 실제 요구사항으로 채운다. `refactor-safely`는 선택한 체크리스트와 결과 양식의 경로를 감사 역할에 전달하고, 항목별 판정과 코드 근거를 결과에 남긴다. 프로젝트 양식에 빠진 필수 내용은 해당 절이나 보충 절에 적는다. 스펙은 승인 훅이 읽는 상태 줄·불변 조건·완료 기준·테스트 먼저 지점을, 감사는 A/B/C/D 분류·불변 조건 영향·승인 후 구현 결과를 보존한다.

초기화는 이미 연결된 양식을 재사용한다. 이전 중 보존할 양식이 발견되면 끊긴 연결만 승인안에 넣는다. 양식이 없는 프로젝트에는 새 설정 키·등록부·질문을 추가하지 않는다. [스펙 작성 단계](../../../plugin/skills/write-spec/SKILL.md) · [감사와 위임 단계](../../../plugin/skills/refactor-safely/SKILL.md)

## 설계 선택과 트레이드오프

**1. 이전할 때 확인하는 비용을 감수한다.** 출처와 사용처를 대조하면 사람이 터미널에서 쓰는 훅이나 PR 템플릿이 참조하는 규칙을 실수로 지울 가능성이 줄어든다. 대신 오래된 복사본이 많으면 조사할 이력과 사람이 검토할 승인안이 길어진다. 경로를 실행 중에 조합하는 스크립트는 텍스트 검색으로 놓칠 수도 있다. 출처가 불명확하면 보존하므로 중복 파일이나 기존 훅의 결함도 남을 수 있다. 이 비용은 복사 설치를 이전할 때 발생한다.

**2. 파일별 포맷의 경계는 파일 한 개다.** Codex와 개발자가 같은 파일의 서로 다른 줄을 고쳤다면 포매터는 개발자의 줄까지 다시 쓸 수 있다. 인덱스는 그대로여도 다음에 스테이징할 diff는 커질 수 있다. 또한 훅은 경로 하나를 인자로 넘길 뿐이므로 프로젝트 실행 파일이 그 인자를 무시하고 전체 포맷을 호출하면 다른 파일도 바뀐다. 다른 파일에 미커밋 변경을 두고 실행하는 수용 시험이 필요한 이유다.

기존 설치에는 호환 비용도 있다. 전체 자동 포맷을 켜 둔 프로젝트는 새 키를 설정하기 전까지 같은 위험을 안고 간다. 전환하면 프로젝트가 파일별 실행 방법을 관리해야 하고, 한 패치에 대상 파일이 10개면 포매터도 10번 호출한다. 시작이 느린 도구로 대량 수정할 때는 자동 포맷을 끄고 사용자가 원하는 시점에 전체 포맷을 실행하는 편이 나을 수 있다.

**3. 팀 양식의 유지보수는 팀이 맡는다.** 익숙한 섹션과 점검 항목을 재사용하면 작성 뒤 팀 양식에 맞춰 다시 정리하는 일이 줄어든다. 대신 양식을 이동하면 참조도 고쳐야 하고, 링크가 깨지면 해당 문서 작성이 멈춘다. 팀 양식에 공통 승인·검증 항목이 빠져 있으면 결과 문서가 팀의 원래 양식보다 길어진다. 양식이 큰 프로젝트는 그 스킬을 쓸 때 읽는 토큰도 늘 수 있다. 양식이 없는 저장소는 기본 양식을 그대로 쓴다.

실행 시간과 토큰의 순변화는 이번 검토에서 측정하지 않았다. 위 판단은 변경 범위와 보존할 동작을 기준으로 한다.

## 불변 조건

- Codex에서 스펙 구현과 설치 대상 프로젝트의 변경은 각각 해당 변경안에 대한 사용자 승인을 따른다.
- 이전 조사와 편집 후 포맷은 사용자의 Git 인덱스를 바꾸지 않는다. 파일별 포매터의 계약은 전달받은 파일 하나만 편집하는 것이다. 설치 시 검증한 실행 파일도 이후 프로젝트가 수정할 수 있다.
- 특정 언어, 빌드 도구, 문서 폴더, 필수 로컬 양식을 가정하지 않는다. 외부 서비스 API와 데이터 모델 변경은 없다.

| 요구사항 | 테스트 먼저 | 먼저 확인할 실패 또는 검수 근거 |

## 검증 시나리오와 완료 기준

| 순서 | 임시 저장소에서 수행할 시험 | 통과 기준 |
|---|---|---|
| 1 | 수정한 훅·출처 불명 파일·동일하지만 사람이 쓰는 훅·PR 주석의 경로를 넣고 Codex 이전안을 생성한다. 한 항목만 이동 승인한 뒤 다시 실행한다 | 제안 중 파일·인덱스 변화 0. 승인한 경로와 참조만 바뀌고 이동한 문서 내부의 상대 링크도 열린다. 두 번째 실행에 같은 변경이 없다 |
| 1 | 일부만 스테이징한 파일과 다른 미스테이징 파일을 두고 이전 전후에 실제 Git 훅을 실행한다. 포매터 성공·실패·스테이징된 줄을 다시 쓰는 세 경우를 비교한다 | 종료 코드, 인덱스의 내용·충돌 상태, 작업 파일 바이트, 남은 stash를 대조한다. 새 손실이 없고 이미 있던 충돌은 승인안과 결과에 드러난다 |
| 2 | TypeScript와 Python 예제에서 Codex 단일·다중 파일 패치를 실행한다. 공백·한글·따옴표가 있는 이름, 중복 경로, 이동·삭제, 패치 실패를 포함한다 | 기록된 인자 개수·값·호출 횟수가 편집 대상과 일치한다. 무관한 미커밋 파일과 인덱스가 그대로이며 실패한 패치에서는 포맷 실행 0회다 |
| 2 | 실행 파일 누락·오류·범위 밖 링크, 기존 키만 있는 설정, 빈 대상 패턴을 시험하고 수동 `dev.sh fmt`도 실행한다 | 오류에서는 경고가 남고 전체 명령 호출은 0회다. 기존 설정과 수동 실행 결과는 위 설정 표와 일치한다 |
| 3 | 프로젝트 양식 세 개, 일부만 지정, 지정 없음, 명시한 경로 오류를 각각 준비한다. Codex로 Draft 스펙과 감사 문서를 작성한다 | 생성 파일에서 로컬 전용 섹션의 실제 내용과 체크 항목의 판정·근거를 확인한다. 미지정 종류만 기본 양식을 쓴다. 깨진 경로를 보고한 경우 해당 결과물을 생성하지 않는다 |

- [ ] 위 시나리오를 단계 순서대로 검증하고, 실패한 항목과 재현 조건을 기록한다. 스킬의 파일 선택 발언만으로 문서 산출물 시험을 통과 처리하지 않는다.

## 승인 범위

승인 대상은 위 세 단계의 변경 범위와 수용 기준이다. 추가 선택 기능(Nice to Have)은 없다. 상태를 `Approved`로 바꾸고 구현을 시작하는 결정은 스펙을 검토한 사용자가 내린다.
