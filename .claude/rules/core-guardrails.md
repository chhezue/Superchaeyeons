# Core — 가드레일 (⛔ STOP)

**구현·기본값 변경·커밋 전에 반드시 멈춰야 하는 것**만 모았다. 여기 걸리면 다른 어떤 규칙·워크플로보다 먼저 중단하고 사용자에게 묻는다.

작업을 **어떤 순서로** 진행하는지(트랙 1개 선택 → 게이트 4개 통과)는 `core-workflow.md`가 담당한다.

스택에 묶인 STOP 절(에러코드 동시갱신 · 권한 게이트·활동 기록 동시갱신 · 마이그레이션 금지 · API 계약 보호 · 생성 문서 검증)은 **lang 팩 규칙**(`harness-map.md`의 "스택 팩 (= lang 팩)" 절이 가리키는 파일)에서 산다 — 어느 절인지는 능력 플래그 표

## 플래그 판정 — 절을 지우지 않는다

`[플래그: X]` 배지가 붙은 절은 `harness-map.md` 능력 플래그 표에서 X가 ❌면 **그 절 전체를 무시한다.** 절을 삭제하지 않는다 — 삭제하면 부품이 갈라져 이후 개선을 함께 받을 수 없다. ⬜(미결정)면 멈추고 사용자에게 묻는다 (`harness-map.md` 규칙 2).

## ⛔ STOP (모든 규칙보다 우선)

구현·기본값 변경·커밋 전 확인. **위반 시 중단·사용자 질문.**

### 1. 문서·구현 정합

1. **문서·스펙·결정 vs 구현** — `{{스펙 저장소}}`(Approved), `{{결정 기록}}`(확정), `{{제품 범위}}`, `{{아키텍처 개요}}`, `{{배포 SSOT}}`와 다른 TTL·API 계약·enum·한도·env 이름·패키지 경로를 **조용히 맞추지 않는다**.
2. **문서 vs 문서** — PRD vs 스펙, 스펙 vs 와이어프레임, decisions vs architecture, 스펙 vs `.env.example` 등 **서로 다른 값·용어·경로**면 한쪽을 임의 선택하지 말고 충돌을 짧게 목록화해 확인 요청.
3. **임의 개선 금지** — "더 나은 기본값", "업계 일반값", "코드가 간단해짐"만으로 문서와 다른 수치·구조를 바꾸지 않는다. 변경 시 **문서 amend 또는 사용자 명시 승인**.
4. **불확실하면 질문** — 가정을 숨기지 않는다. 질문 없이 진행한 선택은 **잘못된 작업**.
5. **구현 상태 보고 전 코드 우선 확인** — 스펙 Must Have 체크박스(`[ ]`/`[x]`)·"미구현"·"대기 중"·"`#n` 선행 필요" 같은 서술은 기능이 merge된 뒤 스펙 동기화가 누락되면 stale해진다. 사용자·프론트에게 "이 API·enum·이벤트가 아직 구현 안 됨/트리거 안 됨"이라고 **부정적으로 단정**해 답하기 전에, 관련 진입점·서비스(이벤트 발행부)·테스트를 직접 grep/Read로 확인한다. `{{스펙 저장소}}` 문구 하나만 근거로 구현 여부를 판단하지 않는다 — 필요하면 `gh issue view`로 실제 이슈 상태도 함께 확인.
6. **[플래그: 생성 문서 검증]** **"생성 문서에 있다"를 소스의 설명 표기만 보고 단정하지 않는다** — 소스에 설명 표기가 있어도 생성된 API 문서에는 스키마가 통째로 빠져 있을 수 있다. "프론트가 필요한 값이 이미 노출된다"고 답하기 전에 로컬·배포 서버의 생성 문서 또는 `{{API 문서}}`를 실제로 열어 해당 스키마·enum이 진짜 있는지 확인한다. 스택별로 스키마가 사라지는 함정은 lang 팩 규칙의 "생성 문서 검증" 절에 있다.
7. **계약에 닿는 변경은 같은 턴에 끝낸다** — 실패 케이스·에러 코드·권한 게이트·활동 시각 기록처럼 코드와 계약·문서·생성물이 **함께** 바뀌어야 하는 변경은 같은 PR·같은 턴에 enum·스펙 에러 표·응답 스키마·주석까지 전부 갱신한다. "다음 커밋에" 금지. 스택별 체크 표는 lang 팩 규칙의 **[플래그: 에러 코드 카탈로그 동시갱신]·[플래그: 권한 게이트·활동 기록 동시갱신]** 절.

**절대 금지:** 문서와 다른 TTL·API 필드·에러 코드·env 키를 임의 구현·커밋 · **에러 코드·권한·활동 처리를 "다음 커밋에" 미루기** · **스펙 문서만 보고 "미구현"이라고 보고 — 코드 미확인 상태로 구현 상태 단정** · **소스의 설명 표기만 보고 "생성 문서에 이미 있다"고 보고 — 실제 생성물 미확인**

### 2. 레거시·정책 불일치 코드 제거 (호환 레이어 금지 · **같은 변경에서 즉시**)

현행 Approved 스펙·BR·decisions·구현 계약과 다른 코드·경로·문서를 "호환용"으로 남기지 않는다.
**dev·상용 보존 데이터 없음** → 듀얼 패스·구 클라/DB 호환·orphan 유지 **불필요·금지**.

운영 보존 데이터가 있는 프로젝트는 `harness-map.md`에서 "DB 마이그레이션 금지" 플래그를 ❌로 둔다. 그 경우 아래 1번의 "구 스키마 매핑"과 4번의 "구 클라/DB 호환 어댑터·orphan 컬럼"은 이 절이 아니라 그 프로젝트의 마이그레이션 정책을 따른다. 나머지 항목은 그대로 적용된다.

1. **삭제 대상:** 폐기 API/path · 정책상 폐기 enum/에러 코드/필드 · 구 상수·검증 · 대체된 저장 계층 메서드·벌크 쿼리 · 구 스키마 매핑 · 호환 if · deprecated 표시만 하고 방치한 코드 · stale 스키마 설명·메시지 · "나중에 지울" TODO · 스펙·생성 API 문서의 **현행 계약으로 적힌** 구 수치·구 API명
2. **시점 (필수):** 정책 amend·경로 교체 구현과 **같은 커밋/같은 PR/같은 턴**. "다음 커밋에 정리"·"일단 새 경로만 추가" **금지**
3. **교체 = 구경로 삭제:** 새 구현을 넣으면 **호출되지 않는 구 메서드·상수·테스트 assert·문서 '현행' 문구**를 같은 변경에서 제거. "요청 밖 dead code라서 언급만"으로 **넘기지 않는다** — 이번 변경이 대체한 코드는 **요청 범위**
4. **하지 않음:** 구 클라/DB 호환 어댑터 · orphan 컬럼 · deprecated 방치 · soft/hard·live/snapshot 등 **정책상 폐기된 이중 분기**
5. **예외 — 진짜 요청 밖:** 이번 정책과 **무관한** 기존 dead code만 언급. **정책 불일치·이번 교체 잔존은 이 절이 우선 → 삭제**
6. **이력 문서:** 스펙 Changelog·과거 체크리스트의 "당시 값은 이랬다" 서술은 OK. **'현행 코드/계약'** 으로 적힌 구 값은 §1·본 절로 **즉시 amend**

### 3. 보안·아키텍처 성격 로직 변경 — `{{현재동작 요약}}` 같은 턴 갱신

인증·세션·토큰 저장 방식, 결제, 개인정보 저장·암호화, 그 외 "이게 바뀐 걸 사용자가 한참 뒤에야 알면 곤란한" 성격의 로직을 바꾸면, 그 작업과 **같은 턴**에 `{{현재동작 요약}}`의 해당 절도 쉬운 말로 고친다(없던 주제면 새 절 추가). "나중에 정리"·"스펙에 이미 적었으니 됐다" 금지 — §1.7과 동일한 패턴.

**대상(예):** 토큰·세션 저장 위치·전달 방식, 비밀번호·시크릿 처리, 결제 흐름, 대량 개인정보 접근·삭제 로직.

**금지:** `{{스펙 저장소}}`에만 적어두고 `{{현재동작 요약}}`은 방치 · "사소한 변경"이라며 임의로 갱신 생략 · 기술 용어를 그대로 옮겨적기(사용자가 다른 문서 없이도 읽히게 — `core-reporting.md` 준수).

**환경 금지 (훅이 차단):** `git push --force` · `rm -rf` 류 재귀 강제 삭제 · `git reset --hard` · 운영 DB 파괴 · `.env`·API 키 커밋.
