# Audit Template

`{{감사 로그}}/{unit}/{NNN}-{kebab-topic}.md`를 새로 작성할 때 이 구조를 그대로 복사해서 채운다. 문제 해결 유형의 작업 산출물이다(`{{문서 루트}}/templates/README.md` 등록부). 감사 단계는 **코드를 수정하지 않는다** — 이 문서만 산출한다. 승인 뒤 구현이 끝나면 맨 아래 "구현 결과" 절을 채운다.

---

```markdown
# {작업 단위} 아키텍처 감사 — {YYYY-MM-DD}

{개요 — 필수. 이 감사가 무엇을 대상으로 했고, A/B로 몇 건이 나왔으며, 지금 어떤 상태(승인 대기·반영 완료)인지 2~3문장. 처음 여는 사람이 이 문단만 읽고 문서의 정체를 알 수 있어야 한다.}

## 범위

- 대상: `{경로·패키지·모듈}`
- 감사자: 서브에이전트 (`Agent` 툴, 읽기 전용)
- 기준: `audit-checklist.md` 1~14 · lang 팩 규칙 `{파일}` · `core-guardrails.md` ⛔ STOP

## 불변 조건 (G2에서 확정)

| 불변 조건 | 검증 방법 |
|---|---|
| {예: 비즈니스 로직·정책 불변} | {`{{테스트 명령}}` 전부 통과} |
| {예: 관찰 가능한 최종 동작 불변} | {계약 diff 0 / 테스트 통과} |

## ✅ A. 반드시 수정해야 하는 사항

버그 · 잠재적 버그 · 성능 문제 · 메모리 낭비 · 보안 문제 · 불변 조건을 지키면서 개선 가능한 구조적 문제.

### A-1. {제목}

- **Priority**: Critical / High / Medium / Low
- **Category**: Performance / Readability / Framework / Data / Architecture / Security / Cleanup / Dead Code
- **문제**: 현재 어떤 문제가 있는지
- **왜 문제인가**: 유지보수 / 성능 / 가독성 관점
- **개선 방법**: 구체적인 리팩토링 방안
- **불변 조건 영향**: 없음 / {어느 조건에 닿는지 — 닿으면 승인 때 따로 묻는다}
- **승격 후보**: 아니오 / 예 — {새 의존성·기술·계약 변경이 필요한 이유}
- **예상 변경 파일**: 경로 나열
- **예상 변경 라인 수**: 대략치
- **위험도**: Low / Medium / High
- **테스트 영향도**: 기존 테스트 영향 여부, 커버리지 공백 여부
- **예상 효과**: 코드 감소 / 유지보수성 / 성능 / 테스트성

(A-2, A-3 ... 반복)

## ✅ B. 유지보수성 향상을 위한 리팩토링

중복 코드 제거 · 책임 분리 · 공통화 · 보일러플레이트 제거 · Dead Code 제거 · Legacy 코드 제거.

### B-1. {제목}

(A와 동일 포맷)

## 💡 C. 참고 사항 (권장하지만 이번엔 수정하지 않음)

- 각 항목마다 **왜 지금 안 하는지 이유**를 반드시 포함

## 🚫 D. 수정하지 않는 것이 더 좋은 사항

- 각 항목마다 **왜 현재 구조가 더 나은지 이유**를 반드시 포함

## 참고 — 외부 사례 (조사했을 때만)

`researcher`로 확인한 외부 문서·사례. `## 근거`가 아니다 — A/B 판정 근거는 코드에서 확인한 사실만이다.

## 승인 대기

사용자 승인 후 A/B 항목만 우선순위 순으로 구현한다. C/D는 이번 라운드에서 수정하지 않는다. 승격 후보는 승인되면 `specify`로 넘어간다.

## 구현 결과 (YYYY-MM-DD)

{승인 뒤 채운다. 반영한 항목(A-1, B-2 …) · 불변 조건별 검증 결과(실행한 명령 → 결과) · 미룬 항목과 이유 · 검증하지 못한 것과 이유.}
```
