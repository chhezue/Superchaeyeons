# 이슈 우선순위 라벨 — 채운 예 (TripFit)

`priority: must / could` 라벨 체계를 운영하는 프로젝트가 `.claude/rules/local-priority.md`로 두는 규칙의 견본이다. 부품(`core-scope.md`)에는 이 정책이 없다 — `{{우선순위 SSOT}}`가 `(없음)`인 프로젝트에는 라벨이라는 개념 자체가 없기 때문이다. 이 파일은 `local-` 층이라 이식성 검사 대상이 아니다.

## 판단 기준 (작업 성격 기준)

성능 개선·폴더/패키지 구조 정리·리팩터·최적화 = `priority: could`. 그 외 **기능 구현 자체·버그 수정은 전부** `priority: must`. 현재 어떤 이슈가 could인지는 `{{우선순위 SSOT}}`가 갖는다 — 이 파일에 이슈 번호를 적지 않는다.

**⛔ 에이전트가 스스로 must/could를 판단해 라벨을 부여·변경하지 않는다 — 반드시 사용자에게 먼저 확인.** 2026-08-26 사고 계기: 외부 저장소 미러링·외부 캘린더 동기화 방식 변경 이슈 두 건을 에이전트가 "기능 구현/신뢰성 우선"으로 자체 판단해 must로 분류했다가 사용자가 could로 정정했다. "새 기능 태그가 붙어 있다"는 표면적 신호만으로 must를 단정하지 말고, 실제 작업 성격(안정성·효율 개선인지)을 봐야 한다. 신규 이슈 생성 시에도 같다.

## 용어

| 용어 | 의미 | SSOT |
|------|------|------|
| **이슈 `## 완료 조건`** (구 `## Must Have`) | **그 이슈**를 끝내는 체크리스트. `priority: must`와 이름이 겹쳐 개명 | 해당 이슈 |
| **Must** | 기능 구현 자체·버그 수정 | 이슈의 `priority: must` 라벨 |
| **Could** | 성능 개선·구조 정리·리팩터·최적화 (MoSCoW Could have) | 이슈의 `priority: could` 라벨 |
| **스펙 `MVP: In scope`** | 제품 범위에 들어감 — `priority: must`와 **별개 축** (범위 vs 작업 성격) | 혼동 금지 |

## 금지

- 근거(라벨) 없이 이슈를 Must/Could라고 말함
- 사용자 확인 없이 priority 라벨을 부여·변경 (신규 이슈 포함)
- Milestone·`priority:` 라벨 없이 이슈 방치
